# Chapter 9 The Type System

## 9.1 Referring back: that `%struct.Point = type { i32, i32 }` from Chapter 6

In Chapter 6 we saw:

```llvm
%struct.Point = type { i32, i32 }
```

At the time we only said "this is a type definition". This chapter covers the type system in full, and explains:

- Why does C's `int` become `i32` instead of keeping the name `int`?
- Why does `struct Mixed { char c; int i; double d; }` become `{ i8, i32, double }`, with **no** padding bytes in between?
- What is that long `e-m:e-p270:32:32-...` string in `target datalayout` actually saying?

## 9.2 The three kinds of types

LLVM's types fall into three big groups:

### 1. Primitive types

| Category | Type | Notes |
|---|---|---|
| Integer | `i1`, `i8`, `i16`, `i32`, `i64`, `i128`, `iN` | **Any bit width**! `i3`, `i17`, `i100` are all legal |
| Floating point | `half` (16-bit), `float` (32-bit), `double` (64-bit), `fp128` (128-bit), `x86_fp80` (x86 80-bit), `ppc_fp128` | |
| Pointer | `ptr` | In LLVM 18 this is the only pointer type |
| Label | `label` | Basic block label, usable only with `br`/`switch` |
| Token | `token` | Used for `gc.statepoint` and the like |
| Metadata | `metadata` | |
| void | `void` | Can only be a return type |

**Integer bit widths are arbitrary**, which is very different from C. You can write `i3` (a three-bit integer from 0 to 7) or `i24`. When the optimizer promotes `i8` arithmetic to `i32`, it temporarily creates types like `i33`. In the `-O2` output of the `sum_to` example in [Appendix B.6](22-appendix-b-optimization-primer.md#b6-watching-pass-by-pass-a-complete-experiment) we see exactly that:

```llvm
  %6 = zext nneg i32 %5 to i33
  %9 = mul i33 %6, %8
  %10 = lshr i33 %9, 1
  %11 = trunc i33 %10 to i32
```

`i33` is there so that a single multiplication can hold both the 32-bit operands and the possible overflow bit. **This is a direct demonstration that IR is more flexible than C.**

### 2. Aggregate types

| Type | Syntax | Corresponding C |
|---|---|---|
| Array | `[10 x i32]` | `int[10]` |
| Struct | `{ i32, i8 }` | `struct` |
| Packed struct | `<{ i32, i8 }>` | `__attribute__((packed))` (no padding) |
| Vector | `<4 x i32>` | SIMD types |

**Structs have padding by default.** Consider the example from Chapter 6:

```c
struct Mixed { char c; int i; double d; };
```

```llvm
%struct.Mixed = type { i8, i32, double }
```

You might ask: shouldn't there be 3 bytes of padding after the `i8`?

**The answer: padding is not written into the type; it is computed from the alignment rules in `datalayout`.** That way the same type definition can have a different physical layout on 32-bit and 64-bit platforms, while the IR itself stays target independent.

You can verify the actual size with `llvm-config` or with a small test program:

```bash
$ cat > size.c <<'EOF'
#include <stdio.h>
struct Mixed { char c; int i; double d; };
int main(void) {
    printf("sizeof(struct Mixed) = %zu\n", sizeof(struct Mixed));
    printf("  c offset = %zu\n", offsetof(struct Mixed, c));
    printf("  i offset = %zu\n", offsetof(struct Mixed, i));
    printf("  d offset = %zu\n", offsetof(struct Mixed, d));
    return 0;
}
EOF
$ clang-18 -w size.c -o size && ./size
sizeof(struct Mixed) = 16
  c offset = 0
  i offset = 4
  d offset = 8
```

So the actual layout is: `c` at 0, 3 bytes of padding, `i` at 4, `d` at 8, 16 bytes in total. **That padding comes from the alignment rules of datalayout, not from the type `{ i8, i32, double }` itself.**

### 3. Type aliases

```llvm
%struct.Point = type { i32, i32 }
%MyInt = type i32
```

What `type` defines is a **name**, not a new type. `%MyInt` and `i32` are completely equivalent. So the following code is legal:

```llvm
%MyInt = type i32

define %MyInt @f(i32 %x) {
  %r = add i32 %x, 1
  ret i32 %r            ; returns i32, whose type is an alias of %MyInt, OK
}
```

## 9.3 The complete mapping from C types to IR types

This is a table you can consult at any time. It was generated by measurement:

```c
void f_char(char a) {}
void f_schar(signed char a) {}
void f_uchar(unsigned char a) {}
void f_short(short a) {}
void f_ushort(unsigned short a) {}
void f_int(int a) {}
void f_uint(unsigned a) {}
void f_long(long a) {}
void f_ulong(unsigned long a) {}
void f_ll(long long a) {}
void f_bool(_Bool a) {}
void f_float(float a) {}
void f_double(double a) {}
void f_ld(long double a) {}
void f_ptr(void *a) {}
void f_arr(int a[10]) {}
```

The actual output of `clang-18 -S -emit-llvm -O0`:

```llvm
define dso_local void @f_char(i8 noundef signext %0) #0 {
define dso_local void @f_schar(i8 noundef signext %0) #0 {
define dso_local void @f_uchar(i8 noundef zeroext %0) #0 {
define dso_local void @f_short(i16 noundef signext %0) #0 {
define dso_local void @f_ushort(i16 noundef zeroext %0) #0 {
define dso_local void @f_int(i32 noundef %0) #0 {
define dso_local void @f_uint(i32 noundef %0) #0 {
define dso_local void @f_long(i64 noundef %0) #0 {
define dso_local void @f_ulong(i64 noundef %0) #0 {
define dso_local void @f_ll(i64 noundef %0) #0 {
define dso_local void @f_bool(i1 noundef zeroext %0) #0 {
define dso_local void @f_float(float noundef %0) #0 {
define dso_local void @f_double(double noundef %0) #0 {
define dso_local void @f_ld(x86_fp80 noundef %0) #0 {
define dso_local void @f_ptr(ptr noundef %0) #0 {
define dso_local void @f_arr(ptr noundef %0) #0 {
```

Collected into a table:

| C type | IR type | Parameter attribute | Notes |
|---|---|---|---|
| `char`, `signed char` | `i8` | `signext` | |
| `unsigned char` | `i8` | `zeroext` | |
| `short` | `i16` | `signext` | |
| `unsigned short` | `i16` | `zeroext` | |
| `int` | `i32` | none | |
| `unsigned` | `i32` | none | **Note: no `zeroext`** |
| `long` (Linux x86-64) | `i64` | none | |
| `long long` | `i64` | none | |
| `_Bool` | `i1` | `zeroext` | |
| `float` | `float` | | |
| `double` | `double` | | |
| `long double` (x86-64) | `x86_fp80` | | Target dependent! |
| `void *` | `ptr` | | |
| `int[10]` (as a parameter) | `ptr` | | Arrays decay to pointers |

### Key observation one: signedness shows up in `signext`/`zeroext`

`char` and `unsigned char` are both `i8`. The difference is the parameter attribute:

- `signext`: the caller/callee guarantees **sign extension** to the register width;
- `zeroext`: guarantees **zero extension**.

This is an ABI-level requirement. The x86-64 calling convention only specifies that values of 32 bits and below go in the low part of the register; whether the high bits are valid has to be stated explicitly by an attribute.

### Key observation two: `unsigned` has no `zeroext`, but `unsigned char` does

This looks inconsistent, but there is a reason: an `i32` argument **exactly fills** a 32-bit register, so there is no question of "the high bits are undefined" and no extension attribute is needed. `i8`/`i16` are narrower than a register, so how the high bits are handled has to be spelled out.

### Key observation three: array parameters decay to `ptr`

For a parameter `int a[10]`, the IR type is `ptr`, not `[10 x i32]`. This corresponds exactly to the C rule: **an array used as a parameter decays to a pointer**.

The type `[10 x i32]` still exists; it just appears on **local variables** and **global variables**:

```llvm
@global_arr = global [10 x i32] zeroinitializer
```

### Key observation four: `long double` is target dependent

`x86_fp80` is x86's specific 80-bit extended precision format. On ARM, `long double` may be `fp128` or `double`.

**This is a reminder that IR is not completely target independent.** A few types (`long double`, `va_list`, some intrinsics) leak target details.

## 9.4 The actual layout of a struct: how `getelementptr` relates to padding

Chapter 6 covered field indexing in `getelementptr`. Now the role of padding becomes clear:

```llvm
%struct.Mixed = type { i8, i32, double }

; access the d field
%p = getelementptr inbounds %struct.Mixed, ptr %base, i32 0, i32 2
```

GEP needs to know that `d` sits at offset 8. Where does that 8 come from?

```
i8 is at offset 0, occupying 1 byte
    the next field, i32, needs 4-byte alignment → pad to offset 4
i32 is at offset 4, occupying 4 bytes → ends at 8
    the next field, double, needs 8-byte alignment → already at 8, no padding needed
double is at offset 8, occupying 8 bytes → ends at 16
total struct alignment = max(1,4,8) = 8 → 16 is a multiple of 8, no tail padding needed
```

**So converting GEP's "field index" into a "byte offset" depends on the alignment rules of datalayout.** This is why `datalayout` has to be written in the module — without it, GEP cannot compute the correct address.

## 9.5 Breaking down `target datalayout`

Now let's look at that long string:

```
target datalayout = "e-m:e-p270:32:32-p271:32:32-p272:64:64-i64:64-i128:128-f80:128-n8:16:32:64-S128"
```

It is separated by `-`; here is a piece-by-piece reading:

| Segment | Meaning |
|---|---|
| `e` | **Little endian**. `E` is big endian. |
| `m:e` | **Name mangling**: ELF style (`e`), with no leading underscore. |
| `p270:32:32` | **Pointer address space 270**: ABI alignment 32, preferred alignment 32. |
| `p271:32:32` | Address space 271, same as above. |
| `p272:64:64` | Address space 272, 64-bit alignment. |
| `i64:64` | **The ABI alignment of `i64` is 64 bits** (8 bytes). |
| `i128:128` | `i128` is aligned to 128 bits (16 bytes). |
| `f80:128` | `x86_fp80` is aligned to 128 bits. |
| `n8:16:32:64` | **Native integer widths**: 8, 16, 32, 64. |
| `S128` | **Stack alignment**: 128 bits (16 bytes). |

What are those `p270`, `p271`, `p272`? They are special **address spaces** on x86-64:

- **270**: `__ptr32` (32-bit pointers, used by the x32 ABI)
- **271**: `__ptr64`
- **272**: `__ptr128`

These are Windows-style optional pointer width extensions, which also get written into datalayout on Linux.

**There are only a few you need to remember:**

- **`e` or `E`**: byte order. This decides whether an `i32` in memory is `01 00 00 00` or `00 00 00 01`.
- **`iN:align`**: the alignment of each kind of integer.
- **`S128`**: stack alignment.

### Why datalayout matters

Because **the same `getelementptr` computes different addresses under different datalayouts**. Consider:

```llvm
%struct.Mixed = type { i8, i32, double }
%p = getelementptr inbounds %struct.Mixed, ptr %base, i32 0, i32 2
```

If the alignment of `i32` is 4 (x86), `d` is at offset 8.
If the alignment of `i32` is 8 (on some platforms), `d` may be at offset 16.

**This is why `llc` needs datalayout and `lli` needs it too.** If you do not write datalayout, LLVM uses the target default (inferred from `target triple`); if you write one that does not match the actual target, the generated code reads and writes the wrong addresses.

### A common trap

When hand-writing a `.ll` file, if you omit `target datalayout` and `target triple`, LLVM will:

1. use the default layout of the **host** target (if you use `llc`/`lli`, that is the target LLVM was compiled for);
2. print a warning when needed.

`llvm-as-18` is lenient about the omission. But if you link `.bc` with C code using `clang-18`, you will see:

```
warning: overriding the module target triple with x86_64-pc-linux-gnu
```

**So: when hand-writing IR, either write `target triple` and `target datalayout` explicitly, or know explicitly that you are relying on the defaults.**

## 9.6 The rules of type equality

There is an easy place here to make a wrong assumption. First look at two named types with completely identical fields:

```llvm
%A = type { i32, i32 }
%B = type { i32, i32 }

define %A @f(%B %x) {     ; ← does this work?
  ret %A %x
}
```

Measured:

```bash
$ llvm-as-18 structeq.ll -o /dev/null
llvm-as-18: structeq.ll:4:10: error: '%x' defined with type '%B = type { i32, i32 }' but expected '%A = type { i32, i32 }'
  ret %A %x
         ^
```

**It does not work.** `%A` and `%B` are **two different types**, even though their fields are exactly the same.

### The rule

> **Every `= type` definition creates a distinct named type. A named type is equal only to "the same name". Only literal types (writing `{ i32, i32 }` directly without giving it a name) are compared structurally.**

Therefore:

```llvm
; between literals: structurally equal, the same type
define { i32, i32 } @f({ i32, i32 } %x) {
  ret { i32, i32 } %x           ; ✓ legal
}
```

```llvm
; named type vs. a literal of the same shape: not equal
%A = type { i32, i32 }
define %A @f({ i32, i32 } %x) {
  ret %A %x                     ; ✗ error
}
```

```llvm
; the same named type: equal
%A = type { i32, i32 }
define %A @f(%A %x) {
  ret %A %x                     ; ✓ legal
}
```

**Why is it designed this way?** Because named types provide "opaqueness". In C, `struct Foo` and `struct Bar` are different types even when their layout is the same, and mixing them is rejected by the compiler. LLVM's named types preserve that distinction, which is valuable for debug information, type safety checks, and alias analysis.

> **Practical advice**: once you give a struct a name, use that same name **everywhere**. Do not write `%struct.Point` in some places and `{ i32, i32 }` in others — those are treated as two types.

### Recursive types

In the opaque pointer world of LLVM 18, recursive structs are very simple:

```llvm
%struct.Node = type { i32, ptr }        ; linked list node: value + pointer to the next one
```

Because a pointer does not carry the type it points to, `ptr` breaks the cycle naturally (as covered in Chapter 6).

In LLVM ≤14, by contrast, you had to write:

```llvm
%struct.Node = type { i32, %struct.Node* }   ; older versions: had to refer to it by name
```

**This is a genuine simplification brought by opaque pointers.** In older versions, creating a linked list node type required careful handling of "referring to yourself before the type definition is finished"; now all you need is `ptr`.

## 9.7 `void`, `label`, and special types

```llvm
define void @no_return_value() {
  ret void
}

define i32 @has_label(i1 %c) {
  br i1 %c, label %a, label %b
a:
  ret i32 1
b:
  ret i32 2
}
```

- **`void`** can only be used as a return type, never as a parameter type or a variable type.
- **`label`** is the type of a basic block label. You see the `label` keyword in `br i1 %c, label %a, label %b`, but **a variable cannot have type `label`**.
- **`token`** is used for special instructions such as `gc.statepoint` and is almost never needed in everyday work.
- The **`metadata`** type is used for metadata arguments to `call`, as in `call void @llvm.dbg.value(metadata i32 %x, ...)`.

## 9.9 Summary

- Primitive types: `iN` of arbitrary bit width, several floating point types, the unified `ptr`, `label`, `void`, `token`, `metadata`.
- Aggregate types: `[N x T]` (array), `{ ... }` (struct), `<{ ... }>` (packed), `<N x T>` (vector).
- **Padding is not written in the struct type**; it is determined by the alignment rules of `datalayout`, and GEP relies on those rules to compute addresses.
- C type mapping: `char`→`i8`, `short`→`i16`, `int`→`i32`, `long`→`i64`, `_Bool`→`i1`, `long double`→`x86_fp80` (target dependent).
- **Signedness is not carried by the integer type but by the `signext`/`zeroext` attributes**.
- The key fields of `datalayout`: byte order (`e`/`E`), integer alignment (`iN:align`), stack alignment (`S`).
- **Type equality is not structural equality**: every `= type` definition is a distinct named type, equal only to the same name; only literal types are compared structurally.
- Opaque pointers make recursive type definitions (linked lists and the like) very simple.
