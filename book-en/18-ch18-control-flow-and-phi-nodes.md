# Chapter 18 Control Flow and `phi` Nodes

## 18.1 Refer back: the `phi` that appeared "out of nowhere" in Chapter 5

In Chapter 5 you looked at the `pick` function:

```c
int pick(int c, int a, int b) { return c ? a : b; }
```

```llvm
  br i1 %8, label %9, label %11
9:
  %10 = load i32, ptr %5, align 4
  br label %13
11:
  %12 = load i32, ptr %6, align 4
  br label %13
13:                                               ; preds = %11, %9
  %14 = phi i32 [ %10, %9 ], [ %12, %11 ]
  ret i32 %14
```

The conclusion drawn there was:

> **`phi` is a necessity of SSA.** When control flow merges and the same C variable has different values on different paths, the merge point needs a `phi` to "choose".

**In this chapter you will generate that `phi` yourself.** And you will see that this is far harder than it looks: take one wrong step and the error the LLVM verifier gives is very hard to understand.

That section was titled "**`phi` does not 'execute' at run time**"; this chapter's title could be "**`phi` is hard to generate at compile time**".

## 18.2 Compiling `if`

```python
def op_if(self, fn, env, expr):
    """(if c t e) -- conditional expression, produces a value."""
    if len(expr) != 4:
        raise IRError("if takes exactly a condition, a then and an else")
    _, cond_expr, then_expr, else_expr = expr
    cond = self.to_i1(fn, self.compile_expr(fn, env, cond_expr))

    then_block = fn.new_block("then")
    else_block = fn.new_block("else")
    merge_ref = fn.reserve_block("merge")

    fn.cond_branch(cond, then_block, else_block)

    fn.start(then_block)
    then_val = self.compile_expr(fn, env, then_expr)
    then_end = fn.current
    fn.branch_placeholder(merge_ref)

    fn.start(else_block)
    else_val = self.compile_expr(fn, env, else_expr)
    else_end = fn.current
    fn.branch_placeholder(merge_ref)

    fn.start(merge_ref)
    if then_val.name == else_val.name:
        return then_val
    return fn.emit_value(
        then_val.ty,
        f"phi {then_val.ty} [ {then_val.name}, %{then_end.label} ], "
        f"[ {else_val.name}, %{else_end.label} ]",
    )
```

The code is not long, but it contains **three crucial design decisions that were hard to get right**. Take them one at a time.

### Decision 1: the condition must be reduced to `i1`

```python
cond = self.to_i1(fn, self.compile_expr(fn, env, cond_expr))
```

Chapter 4 described the "tyranny" of `i1`: `br i1` accepts only `i1`. In this language the comparison operators (`<` and friends) produce `i1`, but arithmetic produces `i32`. So `(if x a b)` (where `x` is an `i32`) needs a conversion:

```python
def to_i1(self, fn, val):
    """Reduce an i32 to i1, because `br` requires i1."""
    if val.ty == I1:
        return val
    return fn.emit_value(I1, f"icmp ne {val.ty} {val.name}, 0")
```

Measured:

```lisp
(defn f (x) (if x 1 2))
```

```llvm
%t1 = icmp ne i32 %x, 0        ; ← generated by to_i1
br i1 %t1, label %then1, label %else2
```

**This is the "C condition -> IR conversion" table from Chapter 4 landing in this compiler.**

### Decision 2: the merge block must be "reserved", not "created first"

```python
merge_ref = fn.reserve_block("merge")
```

Compare with the naive version:

```python
then_block = fn.new_block("then")
else_block = fn.new_block("else")
merge_block = fn.new_block("merge")     # ← created immediately
```

The two look similar, but **the difference is large**. Consider a nested `if`:

```lisp
(defn classify (x)
  (if (< x 0) 0
      (if (= x 0) 1 2)))
```

The block order produced by the **naive version** is:

```
entry0
then1
else2
merge3        ← the outer merge is created early
then4         ← but the inner if's blocks come after it
else5
merge6
```

And the inner if's `merge6` **needs to jump back to the outer `merge3`**. So the IR looks like this:

```llvm
merge3:                          ; ← appears before its predecessors
  %t4 = phi i32 [ 0, %then1 ], [ %t3, %merge6 ]
  ret i32 %t4
then4:
  br label %merge6
else5:
  br label %merge6
merge6:
  %t3 = phi i32 [ 1, %then4 ], [ 2, %else5 ]
  br label %merge3               ; ← jumps backwards
```

**This is legal LLVM IR** (block order does not affect semantics), but it has two problems:

1. **Poor readability**: the order of blocks does not match reading order, and seeing `merge3` reference a `%merge6` that has not appeared yet is confusing;
2. **A conflict with the position of `phi`**: `phi` must be at the **very beginning** of a block. The naive version emits the `phi` in `merge3` immediately, but if something else has to be added to `merge3` later, the invariant "phi must come first" has to be maintained very carefully.

**`reserve_block` solves both problems**: for now it only **claims a name**, and the block is appended to the end of the list when it is actually filled in. The block order therefore becomes:

```
entry0
then1
else2
then4          ← the inner if's blocks, because they are filled in first
else5
merge6
merge3         ← the outer merge is filled in last, so it comes last
```

Measured (this is exactly what this compiler generates):

```llvm
define i32 @l_classify(i32 %x) {
entry0:
  %t1 = icmp slt i32 %x, 0
  br i1 %t1, label %then1, label %else2
then1:
  br label %merge3
else2:
  %t2 = icmp eq i32 %x, 0
  br i1 %t2, label %then4, label %else5
then4:
  br label %merge6
else5:
  br label %merge6
merge6:
  %t3 = phi i32 [ 1, %then4 ], [ 2, %else5 ]
  br label %merge3
merge3:
  %t4 = phi i32 [ 0, %then1 ], [ %t3, %merge6 ]
  ret i32 %t4
}
```

**Blocks are ordered by "fill order", which reads consistently with the source structure.** And the `phi` in `merge3` correctly references `%merge6` and `%then1`.

### Decision 3: the `phi` operand must be "the block the branch is in"

This is the easiest one to get wrong, and it is the core of the chapter. First the correct version:

```python
fn.start(then_block)
then_val = self.compile_expr(fn, env, then_expr)
then_end = fn.current                  # ← the key!
fn.branch_placeholder(merge_ref)
```

**Note `then_end = fn.current` -- it is not necessarily equal to `then_block`!**

Why? Because `then_expr` may itself contain control flow. Take the nested `if` example:

```
then_block = then1                      ← start here
compile then_expr = 0                   ← no control flow
then_end = then1                        ← still then1
```

But if instead:

```lisp
(if c1
    (if c2 1 2)      ; ← the then branch has control flow of its own
    3)
```

then:

```
then_block = then1                      ← start at then1
compile then_expr = (if c2 1 2)         ← this generates then4, else5, merge6
                                        ← when it finishes, current is at merge6!
then_end = merge6                       ← not then1!
```

**`then1` now contains nothing; it `br`s to `then4`/`else5`. The block that is really "about to jump to the outer merge" is `merge6`.**

So the `phi` must be written as:

```llvm
phi i32 [ %inner_val, %merge6 ], [ ... ]     ; ← the operand is merge6, not then1
```

### The step most likely to go wrong: emit the branch first, or compile the expression first

Consider the following **incorrect** version (the order is reversed):

```python
fn.start(then_block)
fn.branch_placeholder(merge_ref)         # ← emit the branch first
then_val = self.compile_expr(fn, env, then_expr)   # ← then compile the expression
```

It looks "tidier" (finish the block, then compile its contents), but it **is wrong**. Because `compile_expr` will:
1. move `current` to a new block (the nested if's `merge6`);
2. leave `current` after the `phi` there.

So `branch_placeholder` is applied to `then1`, while `then_val` is computed in `merge6` -- and `merge6` can never jump to the outer `merge3`. LLVM gives this error:

```
llvm-as-18: assembly parsed, but does not verify as correct!
PHI node entries do not match predecessors!
  %t5 = phi i32 [ %t2, %then1 ], [ %t4, %else2 ]
label %else2
label %merge6
Instruction does not dominate all uses!
  %t4 = phi i32 [ 0, %then4 ], [ 1, %else5 ]
  %t5 = phi i32 [ %t2, %then1 ], [ %t4, %else2 ]
```

### Reading this error line by line

**First part:**

```
PHI node entries do not match predecessors!
  %t5 = phi i32 [ %t2, %then1 ], [ %t4, %else2 ]
label %else2
label %merge6
```

How to read it:

- the `phi` `%t5` claims its predecessors are `%then1` and `%else2`;
- the verifier says: "no, the real predecessors of the block are `%else2` and `%merge6`";
- that is: **`%then1` does not jump to the block containing `%t5` at all** (the one that jumps there is `%merge6`).

**Second part:**

```
Instruction does not dominate all uses!
  %t4 = phi i32 [ 0, %then4 ], [ 1, %else5 ]
  %t5 = phi i32 [ %t2, %then1 ], [ %t4, %else2 ]
```

How to read it: `%t4` is defined in block `%merge6`, but `%t5` claims it can get `%t4` from `%else2`. **A path starting at `%else2` does not pass through `%merge6`, so `%t4` is not defined there at all.** This violates "a definition must dominate its uses" (Chapter 14).

### The fix

The fix is to **move the `branch` after the expression is compiled**, and to use `fn.current` rather than `then_block` as the `phi` operand:

```python
fn.start(then_block)
then_val = self.compile_expr(fn, env, then_expr)
then_end = fn.current                  # ← only after compiling do you know which block you landed in
fn.branch_placeholder(merge_ref)       # ← now emit the branch
```

```python
return fn.emit_value(
    then_val.ty,
    f"phi {then_val.ty} [ {then_val.name}, %{then_end.label} ], "
    f"[ {else_val.name}, %{else_end.label} ]",
)
```

The fixed output (the one at the start of this section) passes verification.

### The lesson of this trap

> **The "current block" is implicit state that sub-compilations modify.**

Compiling an expression **does not guarantee** returning to the block you started in. Any assumption that attempts to "keep the block unchanged" around compiling a subexpression is wrong.

**The general form of this problem** shows up in many compilers. There are two classic solutions:

1. **Pass and return the "current block" explicitly** (the approach here: read it back with `fn.current` instead of assuming);
2. **Do not share mutable state**: have `compile_expr` return `(value, end_block)`.

Approach 1 is used here because it is smaller. But **either way, you must be aware that "compiling a subexpression moves the insertion point"** -- this is why Chapter 14 lists the insertion point as the first principle.

## 18.3 Compiling `while`

```python
def op_while(self, fn, env, expr):
    """(while c body...) -- loop; produces 0.

    Because every mutable local variable lives in a stack slot, the loop
    needs no phi at all: the stack slot is the phi. This is exactly the
    trade-off clang -O0 makes, and the reason -O0 output is full of
    load/store.
    """
    if len(expr) < 2:
        raise IRError("while needs a condition")
    _, cond_expr, *body = expr
    cond_block = fn.new_block("while.cond")
    body_block = fn.new_block("while.body")
    end_block = fn.new_block("while.end")

    fn.branch(cond_block)

    fn.start(cond_block)
    cond = self.to_i1(fn, self.compile_expr(fn, env, cond_expr))
    fn.cond_branch(cond, body_block, end_block)

    fn.start(body_block)
    for form in body:
        self.compile_expr(fn, env, form)
    fn.branch(cond_block)

    fn.seal_block(cond_block)
    fn.start(end_block)
    return Value(I32, "0")
```

**Much simpler than `op_if`**, because it **needs no `phi`**!

Why? Because the variables in the condition (`i`, `s`) live in **stack slots**. The loop body `store`s new values, and the `load` in the next iteration naturally reads the new ones.

Measured:

```lisp
(defn sum_to (n)
  (let ((i 1) (s 0))
    (while (<= i n)
      (set s (+ s i))
      (set i (+ i 1)))
    s))
```

```llvm
define i32 @l_sum_to(i32 %n) {
entry0:
  %i.addr = alloca i32, align 4
  %s.addr = alloca i32, align 4
  store i32 1, ptr %i.addr, align 4
  store i32 0, ptr %s.addr, align 4
  br label %while.cond1
while.cond1:
  %t1 = load i32, ptr %i.addr, align 4
  %t2 = icmp sle i32 %t1, %n
  br i1 %t2, label %while.body2, label %while.end3
while.body2:
  %t3 = load i32, ptr %s.addr, align 4
  %t4 = load i32, ptr %i.addr, align 4
  %t5 = add i32 %t3, %t4
  store i32 %t5, ptr %s.addr, align 4
  %t6 = load i32, ptr %i.addr, align 4
  %t7 = add i32 %t6, 1
  store i32 %t7, ptr %i.addr, align 4
  br label %while.cond1
while.end3:
  %t8 = load i32, ptr %s.addr, align 4
  ret i32 %t8
}
```

**Zero `phi`s.** The loop structure is complete, but state carried across iterations travels entirely through memory.

### An interesting comparison

Look at the code generated for `set i (+ i 1)` inside the loop body:

```llvm
  %t6 = load i32, ptr %i.addr, align 4
  %t7 = add i32 %t6, 1
  store i32 %t7, ptr %i.addr, align 4
```

Read -> compute -> write. And in the pure SSA version (the `mem2reg` output in Chapter 5):

```llvm
  %7 = add nsw i32 %.0, 1     ; use the phi value directly
```

**One instruction versus three.** That is the value of `mem2reg`. Chapter 20 runs through the whole process.

### What `seal_block` is for

```python
fn.seal_block(cond_block)
```

`ir.py` implements a simplified version of the "sealed block" algorithm. Its purpose is: **once a block's set of predecessors is fixed, tell the SSA constructor that the `phi` can be completed.**

In this compiler, because **all mutable variables live in memory**, `seal_block` in fact does almost nothing -- because `_read_variable` is only ever called on SSA values (parameters), and a parameter never has multiple versions.

**So why keep it?** Because `ir.py` is a **general** IR builder (Chapter 15 noted that it does not know Lisp exists). If someone later wants to use it for pure SSA code generation, `seal_block` is required. It is **an interface kept for the future**.

**To be honest about it**: in the current compiler, the `phi`/`seal_block`/`_read_variable` machinery in `ir.py` is **essentially unused** (`op_if` emits `phi` by hand). This is a real engineering phenomenon: **a framework offers more capability than the current requirement**. Chapter 20 explains which parts are "live code" and which are "standby machinery".


### Test two: nested `if`

```lisp
(defn classify (x)
  (if (< x 0) (- 0 1)
      (if (= x 0) 0 1)))
```

```c
printf("%d %d %d\n", classify(-9), classify(0), classify(4));
```

Actual output:

```

```

**This test is especially important**, because it is the reproduction case for that `phi` bug. Before the fix it is rejected by `llvm-as-18`.

### Test three: a loop

```lisp
(defn sum_to (n)
  (let ((i 1) (s 0))
    (while (<= i n)
      (set s (+ s i))
      (set i (+ i 1)))
    s))
```

```c
printf("%d %d %d\n", sum_to(0), sum_to(10), sum_to(1000));
```

Actual output:

```

```

**Note that `sum_to(0)` is 0** -- the loop body never runs and `s` keeps its initial value. This validates the loop condition.

## 18.5 Nested loops

```lisp
(defn mult_table (n)
  (let ((i 1) (total 0))
    (while (<= i n)
      (let ((j 1))
        (while (<= j n)
          (set total (+ total (* i j)))
          (set j (+ j 1))))
      (set i (+ i 1)))
    total))
```

```c
printf("%d\n", mult_table(4));
```

Actual output:

```
100
```

(1x1+1x2+1x3+1x4 + 2x1+...+4x4 = 100.)

The IR generated for the nested `while` has **7 basic blocks**: `entry0` / `while.cond1` / `while.body2` / `while.end3` for the outer loop, and `while.cond4` / `while.body5` / `while.end6` for the inner loop.

**But the number of `phi`s is 0** -- because the inner and outer loop variables (`i`, `total`, `j`) all live in memory; state is carried across iterations through `load`/`store`, and no `phi` is needed. This is exactly the trade-off described in [Appendix C.2](23-appendix-c-compiler-implementation-notes.md#c2-why-if-can-emit-phi-by-hand-and-while-cannot): **once variables live in stack slots, loops need no `phi`.**

## 18.6 A counterexample: when `phi` **is** required

In this language, **only `if` needs `phi`, because only `if` is a "branch that produces a value"**.

Compare:

| Construct | Does it have a value? | Does it need `phi`? |
|---|---|---|
| `if` | yes (one of the two branch values) | **yes** |
| `while` | no (defined here to return 0) | no |
| `let` | yes (the value of the last body expression) | no (there is no branch) |
| `set` | yes (the value assigned) | no (it does not branch) |

**If `while` were to return a value** (say "the accumulator at the end of the loop"), then the loop's exit would need a `phi`:

```llvm
while.end:
  %result = phi i32 [ %s, %while.cond ]    ; the value of s when the loop ends
  ret i32 %result
```

Exercise 15.4 in Chapter 15 asked you to think about this. **Defining it to return 0 avoids that complexity** -- another example of "subtraction".

## 18.8 Summary

- `if` needs `phi`, because it **produces a value** and **has branches**.
- The condition must be reduced to `i1` with `to_i1` (the "`i1` tyranny" of Chapter 4).
- **The merge block should be "reserved" rather than "created first"** -- that keeps block order consistent with the source structure and makes the position of `phi` easy to maintain.
- **The `phi` operand must be "the block the branch is actually in"**, and that is not necessarily the block you `start`ed -- because compiling a subexpression moves the insertion point.
- The **side effect of compiling an expression is moving the insertion point**. This is the sharpest expression of the "insertion point" principle from Chapter 14.
- `while` **needs no `phi`**, because the variables are in memory.
- `phi` is emitted by hand only inside `if`; the general SSA construction machinery in `ir.py` is standby equipment for a future pure SSA front end.
