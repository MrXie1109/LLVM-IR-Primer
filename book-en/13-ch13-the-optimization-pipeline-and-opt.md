# Chapter 13 The Optimization Pipeline and `opt`

## 13.1 Referring back: that "nothing happened" experiment from Chapter 2

In Chapter 2 we ran this experiment:

```bash
clang-18 -S -emit-llvm -O0 mul_add.c -o mul_add.O0.ll
opt-18 -passes=mem2reg -S mul_add.O0.ll -o -
```

**Nothing changed at all.** At the time we found the reason: the function header carries `optnone`, and any pass that sees it skips the function.

This chapter pushes that experiment to the end: we will see clearly the **real pipelines** behind `-O0`/`-O1`/`-O2`/`-O3`, learn to debug pass by pass with `opt`, and understand why "the output of `clang -O2`" and "running `opt -O2` on the output of `clang -O0`" **are not the same thing**.

## 13.2 The old and new syntax of `opt`

**LLVM 18 has removed the old pass syntax.** If you follow an old tutorial and write:

```bash
$ opt-18 -mem2reg -S input.ll
The `opt -passname` syntax for the new pass manager is not supported, please use `opt -passes=<pipeline>` (or the `-p` alias for a more concise version).
See https://llvm.org/docs/NewPassManager.html#invoking-opt for more details on the pass pipeline syntax.
```

You must use `-passes=` (or the short `-p`):

```bash
$ opt-18 -passes=mem2reg -S input.ll -o output.ll
$ opt-18 -p mem2reg -S input.ll -o output.ll          # equivalent
```

**This is one of the places where LLVM 18 clashes most often with old tutorials.**

## 13.3 The pipeline syntax

`-passes=` takes a **pipeline string**, and the syntax is quite flexible:

### A single pass

```bash
opt-18 -passes=mem2reg -S in.ll -o -              # one pass
opt-18 -passes=instcombine -S in.ll -o -          # another
```

### A comma-separated sequence

```bash
opt-18 -passes='instcombine,simplifycfg' -S in.ll -o -
```

**Note the quotes**, because the shell interprets certain characters.

### Nesting: specifying a scope

```bash
opt-18 -passes='function(instcombine,mem2reg)' -S in.ll -o -
opt-18 -passes='module(function(instcombine))' -S in.ll -o -
opt-18 -passes='cgscc(inline)' -S in.ll -o -
opt-18 -passes='loop(licm)' -S in.ll -o -
```

| Scope | Meaning |
|---|---|
| `module(...)` | module-level passes (can see the whole module) |
| `cgscc(...)` | call graph SCC level (inlining and the like) |
| `function(...)` | function level |
| `loop(...)` | loop level |
| `loop-mssa(...)` | loop passes that need MemorySSA |

**Understanding scopes matters**: `mem2reg` is a **function-level** pass and cannot see other functions; `inline` is **SCC level**, because it needs call graph information.

### Predefined pipelines: `default<Ox>`

```bash
opt-18 -passes='default<O2>' -S in.ll -o out.ll
opt-18 -passes='default<O3>' -S in.ll -o out.ll
opt-18 -passes='default<O1>' -S in.ll -o out.ll
```

This is the pipeline (the backend part of it) that `clang -O2` uses.

## 13.4 Seeing the real pipeline

To find out exactly which passes `-O2` contains:

```bash
opt-18 -passes='default<O2>' --print-pipeline-passes /dev/null
```

The output is long, but it is **the optimizer's complete work list**. Two observations are the most valuable:

1. **`default<O0>` contains no `mem2reg`, while `default<O1>` does.** This explains why `-O0` output is full of `alloca`s — they are not left over by the optimizer but actively generated by the clang front end.
2. **The first half of `-O1`/`-O2`/`-O3` is nearly identical**, and the differences are mainly in loop optimization and vectorization (`-O3` adds `loop-unroll<O3>` and `loop-vectorize`).

For the full pipeline comparison, the list of differences between levels, and the scope syntax of pipeline strings (`function(...)`, `cgscc(...)`, and so on), see [Appendix B.5](22-appendix-b-optimization-primer.md#b5-seeing-the-optimization-pipeline-clearly).

> **A practical reminder**: if you run `opt` on `-O0` IR and nothing changes, look for `optnone` first — it **silently** disables every pass. The reason is in [Appendix B.2](22-appendix-b-optimization-primer.md#b2-why-running-opt-does-nothing-optnone).

## 13.5 A misconception that has to be cleared up

**"The output of `clang -O2`" ≠ "running `opt -O2` on the output of `clang -O0`".**

Measured:

```bash
clang-18 -S -emit-llvm -O0 abs_v.c -o abs_v.O0.ll
opt-18 -passes='default<O2>' -S abs_v.O0.ll -o -
```

```llvm
define dso_local i32 @abs_v(i32 noundef %0) local_unnamed_addr #0 {
  %2 = alloca i32, align 4
  %3 = alloca i32, align 4
  store i32 %0, ptr %3, align 4
  %4 = load i32, ptr %3, align 4
  %5 = icmp slt i32 %4, 0
  br i1 %5, label %6, label %9
  ...
```

**No optimization at all!** Because `optnone` is still there, and the whole `default<O2>` pipeline ignores that function.

Remove `optnone`:

```bash
sed 's/ optnone//' abs_v.O0.ll > abs_v.nooptnone.ll
opt-18 -passes='default<O2>' -S abs_v.nooptnone.ll -o -
```

```llvm
define dso_local i32 @abs_v(i32 noundef %0) local_unnamed_addr #0 {
  %.0 = tail call i32 @llvm.abs.i32(i32 %0, i1 true)
  ret i32 %.0
}
```

This time it worked, and the result matches what `clang -O2` produces directly (both become the `llvm.abs` intrinsic).

### The three levels of this misconception

1. **`optnone` silently disables the entire pipeline.** Not an error, not a warning — it simply does nothing.
2. **`clang -O2` is not just "the front end plus the opt pipeline".** clang does some optimization in the front end itself (constant folding, simple pattern matching), and those are not in the `opt` pipeline.
3. **Order matters.** Some optimizations do not work well on `-O0`-style IR (inlining decisions, for instance), because they depend on the cleanup results of earlier passes.

**So: if you want to study optimization, start from the `-O0` IR, remove `optnone` by hand, and then add passes step by step.** This is the most controllable way, and it is the workflow this chapter recommends.

## 13.6 A debugging technique: `-print-after-all`

When you want to know "which pass actually changed my code":

```bash
opt-18 -passes='default<O2>' -print-after-all -S in.ll -o /dev/null 2> trace.txt
```

`trace.txt` contains **the complete IR after every pass has run**, each section preceded by a label line. The format is `; *** IR Dump After <class name>Pass on <function name or [module]> ***`:

```
; *** IR Dump After PromotePass on sum_to ***
define dso_local i32 @sum_to(i32 noundef %0) #0 {
...
; *** IR Dump After InstCombinePass on sum_to ***
define dso_local i32 @sum_to(i32 noundef %0) #0 {
...
```

**Note two things**:

1. What is labelled is the **pass class name**, which is not necessarily the name you wrote in `-passes=`. For example, the class name of `mem2reg` is **`PromotePass`**;
2. Module-level passes show `on [module]`, while function-level ones show the specific function name.

So when grepping, locate by "function name" or "`IR Dump`" rather than by the pass name you typed:

```bash
grep -n "IR Dump After" trace.txt | head -40      # see which passes ran
grep -n "PromotePass on sum_to" trace.txt         # locate the state after mem2reg
```

To see the complete IR after that pass:

```bash
grep -A 30 "PromotePass on sum_to" trace.txt
```

Related options:

| Option | Effect |
|---|---|
| `-print-after-all` | print after every pass |
| `-print-before-all` | print before every pass |
| `-print-after=<passname>` | print after the specified pass |
| `-print-changed` | print only when the IR **changes** (far less output) |
| `-print-module-scope` | always print the whole module rather than the current function |
| `-verify-each` | run the verifier after every pass |

**`-print-changed` is especially useful**, because `-print-after-all` produces several megabytes of output under `-O2`, while most passes change nothing at all.

## 13.7 Using `opt` for validation

`opt` can also be used purely to validate IR:

```bash
opt-18 -passes=verify -S in.ll -o /dev/null && echo "IR is valid"
```

Or have it validate and normalize the output (some details get rewritten):

```bash
opt-18 -passes=verify -S in.ll -o -
```

**This is not redundant**: `llvm-as` does validate, but if you only want to check and do not want to produce a `.bc`, `opt -passes=verify` is more direct.

## 13.8 Other common tools

| Tool | Purpose |
|---|---|
| `llvm-as-18` | `.ll` → `.bc`, **and validates** |
| `llvm-dis-18` | `.bc` → `.ll` |
| `opt-18` | run an optimization pipeline |
| `llc-18` | `.ll`/`.bc` → target assembly |
| `lli-18` | interpret and run a `.bc` directly |
| `llvm-link-18` | link several modules |
| `llvm-nm-18` | inspect the symbol table |
| `llvm-objdump-18` | disassemble |
| `llc-18 -filetype=asm` | generate assembly |
| `llc-18 -filetype=obj` | generate an object file |

A complete flow:

```bash
# Lisp/C → IR text
clang-18 -S -emit-llvm -O2 prog.c -o prog.ll

# IR → assembly
llc-18 prog.ll -o prog.s

# IR → object file
llc-18 -filetype=obj prog.ll -o prog.o

# run the IR directly (needs a main)
lli-18 prog.ll

# see what assembly the IR compiles into
llc-18 -O2 prog.ll -o - | head -30
```

### A practical `llc` technique

To find out "what assembly a given IR construct turns into", write a small piece of IR and let `llc` compile it directly:

```bash
$ cat > t.ll <<'EOF'
define i32 @f(i32 %a, i32 %b) {
  %r = mul i32 %a, %b
  ret i32 %r
}
EOF
$ llc-18 -O2 t.ll -o - | grep -v "^\s*\."
f:                                      # @f
	movl	%edi, %eax
	imull	%esi, %eax
	retq
```

Reading this assembly: the x86-64 System V calling convention puts the first argument in `%edi` and the second in `%esi`.

- `movl %edi, %eax` — copy `a` into the return value register `%eax`;
- `imull %esi, %eax` — compute `%eax = %eax * %esi`, that is `a * b`;
- `retq` — return, with the result already in `%eax`.

**Note that `imul` is a two-operand instruction**: `imull %esi, %eax` means "`%eax = %eax * %esi`", so the result has to be written back into one of the operands. This is why the backend first has to move `a` into `%eax`.

This also explains why the operand order of `mul_add` under `-O2` in Chapter 2 seems to be "reversed":

```llvm
%4 = mul nsw i32 %1, %0
```

**The instruction selection stage is already taking the encoding constraints of `imul` into account**, so the optimizer arranged the operands in an order that is friendlier to the backend.

## 13.10 Summary

- LLVM 18 **requires** `opt -passes=...`; the old syntax reports an error.
- The pipeline syntax supports comma-separated sequences and scope nesting such as `function(...)`/`module(...)`/`loop(...)`.
- `default<O0|O1|O2|O3>` are predefined pipelines; `--print-pipeline-passes` shows the complete list.
- **The `-O0` pipeline is almost empty**, but it still needs "cleanup" passes (coroutines, for example).
- **`optnone` silently disables the entire pipeline** — this is the single most important point when reading `-O0` output.
- **"`clang -O2`" ≠ "running `opt -O2` on the output of `clang -O0`"**, because both `optnone` and the front end's own optimizations create differences.
- To debug optimization, use `-print-after-all`, `-print-changed`, `-print-after=<pass>`.
- `opt -passes=verify` can be used purely for validation.
