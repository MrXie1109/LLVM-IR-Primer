# 第 12 章 属性、元数据与内建函数

## 12.1 回指：第 2 章那一行又长又密的 `attributes`

第 2 章第一次看到 `mul_add` 的完整输出时，有这么一行，当时标注为「与教学无关，省略了」：

```llvm
attributes #0 = { noinline nounwind optnone uwtable "frame-pointer"="all" "min-legal-vector-width"="0" "no-trapping-math"="true" "stack-protector-buffer-size"="8" "target-cpu"="x86-64" "target-features"="+cmov,+cx8,+fxsr,+mmx,+sse,+sse2,+x87" "tune-cpu"="generic" }
```

以及文件末尾这些：

```llvm
!llvm.module.flags = !{!0, !1, !2, !3, !4}
!llvm.ident = !{!5}

!0 = !{i32 1, !"wchar_size", i32 4}
!1 = !{i32 8, !"PIC Level", i32 2}
...
```

第 3 章我们又见过 `nsw`，第 6 章见过 `inbounds`，第 7 章见过 `noreturn`、`returned`、`nocapture`。

**这些东西都不是装饰。** 它们是前端给优化器的**承诺**和**提示**，直接决定了优化器能做什么。本章把它们系统化。

## 12.2 三种「额外信息」的载体

IR 里有三个不同的地方可以放额外信息，它们的用途不同：

| 载体 | 语法 | 作用域 | 例子 |
|---|---|---|---|
| **指令标志** | 跟在指令名后 | 单条指令 | `add nsw`、`getelementptr inbounds` |
| **属性** | `#0` 或直接写 | 函数 / 参数 / 返回值 / 调用点 | `noinline`、`noundef`、`readonly` |
| **元数据** | `!` 开头 | 模块 / 函数 / 指令 | `!dbg`、`!tbaa`、`!llvm.module.flags` |

**关键区别**：

- **指令标志**影响这一条指令的语义（`nsw` 改变了溢出的定义）；
- **属性**是「关于这个函数/参数的事实」，优化器可以依赖它们；
- **元数据**是「附注」，**默认不影响正确性** —— 丢掉元数据不会让程序出错，只会让优化变差（调试信息除外，它影响可调试性）。

## 12.3 函数属性

### 常见的函数属性

```llvm
define i32 @f(i32 %x) #0 {
  ret i32 %x
}
attributes #0 = { noinline nounwind }
```

| 属性 | 含义 |
|---|---|
| `noinline` | 禁止内联 |
| `alwaysinline` | 强制内联 |
| `inlinehint` | 建议内联 |
| `optnone` | **禁止一切优化**（`-O0` 用） |
| `optsize` | 优化体积 |
| `optforfuzzing` | 为模糊测试优化（保留更多行为） |
| `noreturn` | 永不返回 |
| `nounwind` | 不会抛异常 |
| `willreturn` | 一定会返回（不进入死循环） |
| `norecurse` | 这个函数不直接递归调用自己 |
| `nofree` | 不释放内存 |
| `nosync` | 不同步（不用原子操作/内存栅栏） |
| `cold` | 很少执行（放到冷路径） |
| `hot` | 经常执行 |
| `mustprogress` | 循环必须在有限步内结束（C11 的 forward progress） |
| `uwtable` | 生成栈展开表 |
| `ssp` / `sspstrong` | 栈保护 |
| `readnone` | 不读也不写内存（纯函数） |
| `readonly` | 只读内存，不写 |
| `writeonly` | 只写内存 |
| `argmemonly` | 只通过参数访问内存 |
| `inaccessiblememonly` | 只访问不可达的内存 |
| `memory(...)` | 细粒度的内存行为描述 |

### `memory(...)`：LLVM 最新一代的内存属性

从 LLVM 16 起，`readnone`/`readonly`/`argmemonly` 这些老属性逐渐被统一的 `memory(...)` 取代：

```llvm
attributes #0 = { memory(none) }                      ; 不访问任何内存
attributes #1 = { memory(read) }                      ; 只读
attributes #2 = { memory(write) }                     ; 只写
attributes #3 = { memory(readwrite) }                 ; 读写
attributes #4 = { memory(argmem: read) }              ; 只读参数指向的内存
attributes #5 = { memory(inaccessiblemem: write) }    ; 只写不可达内存
attributes #6 = { memory(argmem: readwrite, inaccessiblemem: readwrite) }
```

实测：第 7 章那个 `noreturn` 的函数：

```llvm
; Function Attrs: noreturn nounwind memory(inaccessiblemem: write) uwtable
define dso_local void @die() local_unnamed_addr #1 {
  tail call void @llvm.trap()
  unreachable
}
```

`memory(inaccessiblemem: write)` 的意思是「这个函数只写那些通过正常手段无法访问的内存」。`llvm.trap()` 会触发陷阱，可能被调试器记录到某些不可达的内存区域，所以 clang 这样描述它。

### 属性组

```llvm
attributes #0 = { noinline nounwind }
attributes #1 = { alwaysinline nounwind }
```

属性组出现在文件末尾，函数通过 `#0` 引用。这是为了**去重** —— 多个函数共享属性时只写一份。

你也可以把属性**直接内联**写在函数上：

```llvm
define i32 @g(i32 %x) noinline nounwind {
  ret i32 %x
}
```

两种写法等价。clang 总是用属性组。

## 12.4 参数与返回值属性

这是你看 clang 输出时最常见到的：

```llvm
define dso_local i32 @mul_add(i32 noundef %0, i32 noundef %1, i32 noundef %2) #0 {
```

| 属性 | 位置 | 含义 |
|---|---|---|
| `noundef` | 参数/返回值 | 不会是 `undef` 或 `poison` |
| `zeroext` | 参数/返回值 | 零扩展到寄存器宽度 |
| `signext` | 参数/返回值 | 符号扩展到寄存器宽度 |
| `noalias` | 参数/返回值 | 不与任何其他指针别名 |
| `nocapture` | 参数 | 不会被存到别处 |
| `readonly` | 参数 | 函数不通过它写内存 |
| `writeonly` | 参数 | 函数不通过它读内存 |
| `readnone` | 参数 | 函数既不通过它读也不写 |
| `dereferenceable(N)` | 参数 | 至少指向 N 字节的有效内存 |
| `dereferenceable_or_null(N)` | 参数 | 要么是 null，要么可解引用 N 字节 |
| `align N` | 参数 | 指针对齐到 N |
| `byval` / `byref` | 参数 | 按值/按引用传递聚合类型 |
| `sret` | 参数 | 结构体返回值地址 |
| `returned` | 参数 | 返回值就是这个参数 |

### `noundef` 为什么到处都是？

第 2 章起，clang 的输出里每个参数都带 `noundef`。原因：

C 里**传一个未初始化的值是 UB**（对大多数类型）。既然程序员保证不会，clang 就可以标注「这个参数不会是 `undef`」。

**这给了优化器很大的权力。** 比如：

```llvm
%cond = icmp eq i32 %x, %x    ; 如果 %x 可能是 undef，结果不确定
```

有了 `noundef`，优化器知道 `%x` 是一个确定的值，所以 `%x == %x` 恒为真（除了浮点 NaN）。没有 `noundef` 的话，`undef != undef` 是可能的，这个折叠就不合法。

### `returned`

```llvm
define dso_local noundef i32 @sitofp_it(i32 noundef returned %0) local_unnamed_addr #0 {
```

第 7 章见过 `noinline_f` 也带 `returned`。

`returned` 的意思是「返回值就是 `%0`」。有了它，调用者可以省掉一次拷贝：

```llvm
; 有 returned：
%r = call i32 @f(i32 %x)
; 可以直接把 %x 当作 %r 使用

; 没有 returned：
%r = call i32 @f(i32 %x)
; 必须真的接收返回值
```

**注意 `returned` 是 clang 推断出来的**，你写 C 时不需要（也无法）指定它。

### `noalias` 与 C 的 `restrict`

```c
void add_arrays(int *restrict dst, const int *restrict a, int n) {
    for (int i = 0; i < n; i++) dst[i] += a[i];
}
```

```llvm
define dso_local void @add_arrays(ptr noalias nocapture noundef %0, ptr noalias nocapture noundef readonly %1, i32 noundef %2) local_unnamed_addr #0 {
```

`restrict` → `noalias`。它告诉优化器「这两个指针不指向同一块内存」，于是可以安全地向量化。

**如果没有 `noalias`**，优化器必须假设 `dst` 和 `a` 可能重叠，于是不能把循环重排。**这是 C 里 `restrict` 最有价值的用途。**

## 12.5 元数据

### 模块级元数据

你在每个 clang 输出文件末尾都能看到：

```llvm
!llvm.module.flags = !{!0, !1, !2, !3, !4}
!llvm.ident = !{!5}

!0 = !{i32 1, !"wchar_size", i32 4}
!1 = !{i32 8, !"PIC Level", i32 2}
!2 = !{i32 7, !"PIE Level", i32 2}
!3 = !{i32 7, !"uwtable", i32 2}
!4 = !{i32 7, !"frame-pointer", i32 2}
!5 = !{!"Ubuntu clang version 18.1.3 (1ubuntu1)"}
```

`!llvm.module.flags` 的每一项格式是 `!{行为, "名字", 值}`，其中**行为**是：

| 值 | 含义 |
|---|---|
| 1 | **Error**：如果不认识这个 flag，报错 |
| 2 | **Warning**：如果不认识，警告 |
| 3 | **Require**：如果工具不实现它，拒绝处理 |
| 4 | **Override**：后出现的同一个 flag 覆盖前面的 |
| 5 | **Append**：追加到已有的值列表 |
| 6 | **AppendUnique**：追加并去重（两个值都必须是元数据节点） |
| 7 | **Max**：取最大值 |
| 8 | **Min**：取最小值 |

（合法值只有 1–8，且**没有**「Modulo」这一行为 —— 有的资料会写错。完整对照与来源见 [附录 A.3.1](21-附录A-与常见说法的差异.md#a31-模块标志的行为值)。）

实测中我们看到的：

- `!0 = !{i32 1, !"wchar_size", i32 4}` —— 行为 1（Error），`wchar_t` 是 4 字节；
- `!1 = !{i32 8, !"PIC Level", i32 2}` —— 行为 8（Min），位置无关代码级别是 2；
- `!4 = !{i32 7, !"frame-pointer", i32 2}` —— 行为 7（Max），帧指针模式是 2（`all`）。

**这些 flag 的存在意义是「跨工具链的一致性校验」。** 如果两个模块的 `wchar_size` 不同，链接时会报错，而不是产生微妙的错误。

### 调试元数据

加上 `-g` 后，会出现大量调试信息：

```llvm
!0 = distinct !DICompileUnit(language: DW_LANG_C11, file: !1, producer: "Ubuntu clang version 18.1.3 (1ubuntu1)", isOptimized: true, runtimeVersion: 0, emissionKind: FullDebug, splitDebugInlining: false, nameTableKind: None)
!10 = distinct !DISubprogram(name: "add", scope: !1, file: !1, line: 1, type: !11, scopeLine: 1, flags: DIFlagPrototyped | DIFlagAllCallsDescribed, spFlags: DISPFlagDefinition | DISPFlagOptimized, unit: !0, retainedNodes: !14)
!13 = !DIBasicType(name: "int", size: 32, encoding: DW_ATE_signed)
!15 = !DILocalVariable(name: "a", arg: 1, scope: !10, file: !1, line: 1, type: !13)
```

`DI*` 前缀表示 **D**ebug **I**nformation。这些元数据最终会被翻译成 DWARF 调试信息，让 gdb 能显示变量名和类型。

**注意 `!DIBasicType(name: "int", size: 32, encoding: DW_ATE_signed)`** —— 这里保留了 C 的 `int` 名字和**有符号性**！这正是第 3 章说的「符号性不在 IR 类型里」的一个补偿：类型系统里丢了，调试元数据里补回来。

指令上则挂着 `!dbg`：

```llvm
%3 = add nsw i32 %1, %2, !dbg !17
```

### `!tbaa`：别名分析提示

第 4 章见过：

```llvm
%4 = load i32, ptr %0, align 4, !tbaa !5
```

`tbaa` = **T**ype-**B**ased **A**lias **A**nalysis。它告诉优化器「这次访问是通过什么类型的」，于是优化器可以推断「一个 `int` 访问不会和 `float` 访问别名」。

```llvm
!5 = !{!"int", !6, i64 0}
!6 = !{!"omnipotent char", !7, i64 0}
```

这是 C 的**严格别名规则**（strict aliasing）的 IR 表达。它让优化器能够做更多重排，代价是「用不同类型指针访问同一内存」成为 UB。

### 循环元数据

第 5 章见过：

```llvm
br label %5, !llvm.loop !6
```

```llvm
!6 = distinct !{!6, !7}
!7 = !{!"llvm.loop.mustprogress"}
```

`!llvm.loop` 把循环的信息（如「这个循环有 mustprogress 保证」）附着在回边上。优化器用它来决定能否做循环变换。

## 12.6 内建函数（intrinsics）

内建函数的名字都以 `llvm.` 开头。**它们的函数体不由 IR 定义，而是由后端直接生成代码。**

### 常见内建函数分类

| 类别 | 例子 |
|---|---|
| 内存 | `llvm.memcpy`、`llvm.memmove`、`llvm.memset` |
| 位操作 | `llvm.ctpop`、`llvm.ctlz`、`llvm.cttz`、`llvm.bitreverse`、`llvm.bswap` |
| 数学 | `llvm.abs`、`llvm.smax`、`llvm.smin`、`llvm.umax`、`llvm.umin`、`llvm.fabs`、`llvm.sqrt` |
| 饱和运算 | `llvm.sadd.sat`、`llvm.uadd.sat`、`llvm.ssub.sat` |
| 溢出检查 | `llvm.sadd.with.overflow`、`llvm.umul.with.overflow` |
| 浮点环境 | `llvm.fma`、`llvm.floor`、`llvm.ceil`、`llvm.round` |
| 异常/调试 | `llvm.trap`、`llvm.debugtrap`、`llvm.dbg.value` |
| 变参 | `llvm.va_start`、`llvm.va_end`、`llvm.va_copy` |
| 栈/帧 | `llvm.frameaddress`、`llvm.returnaddress`、`llvm.stacksave`、`llvm.stackrestore` |
| 协程 | `llvm.coro.*` |
| 向量 | `llvm.vector.reduce.add`、`llvm.masked.load` |

### 实测：内建函数的调用与执行

```llvm
declare i32 @llvm.ctpop.i32(i32)
declare i32 @llvm.smax.i32(i32, i32)

define i32 @ctpop_test(i32 %x) {
  %p = call i32 @llvm.ctpop.i32(i32 %x)
  ret i32 %p
}
define i32 @smax_test(i32 %a, i32 %b) {
  %m = call i32 @llvm.smax.i32(i32 %a, i32 %b)
  ret i32 %m
}
```

用 C 驱动测试：

```c
#include <stdio.h>
int ctpop_test(int);
int smax_test(int,int);
int main(void){
  printf("ctpop(255)=%d smax(3,9)=%d\n", ctpop_test(255), smax_test(3,9));
  return 0;
}
```

```bash
$ llvm-as-18 intr2.ll -o intr2.bc
$ clang-18 -w intr_main.c intr2.bc -o intrtest && ./intrtest
ctpop(255)=8 smax(3,9)=9
```

**`llvm.ctpop.i32(255) = 8`** —— 数出 255 的二进制里有 8 个 1。后端把它编译成一条 `popcnt` 指令（如果 CPU 支持）或一段位技巧代码。

### 命名规则：类型后缀

内建函数的类型编码在名字里：

- `llvm.ctpop.i32` —— 操作 `i32`；
- `llvm.memcpy.p0.p0.i64` —— 目标地址空间 0 的指针、源地址空间 0 的指针、`i64` 长度；
- `llvm.smax.i32` —— `i32` 版本。

**为什么编码在名字里？** 因为内建函数需要**重载**，而 LLVM 的函数名不支持参数类型重载。所以用命名约定绕开：`llvm.ctpop.i8` 和 `llvm.ctpop.i32` 是两个不同的函数。

### 溢出检查内建函数

这组内建函数特别有意思，因为它们返回**结构体**：

```llvm
declare { i32, i1 } @llvm.sadd.with.overflow.i32(i32, i32)

define i32 @safe_add(i32 %a, i32 %b) {
  %r = call { i32, i1 } @llvm.sadd.with.overflow.i32(i32 %a, i32 %b)
  %sum = extractvalue { i32, i1 } %r, 0
  %ovf = extractvalue { i32, i1 } %r, 1
  br i1 %ovf, label %overflow, label %ok
overflow:
  ret i32 0
ok:
  ret i32 %sum
}
```

`{ i32, i1 }` —— 第一个字段是和，第二个是「是否溢出」。这条指令直接对应 CPU 的溢出标志位，`__builtin_add_overflow` 就编译成它。

**这是 IR「比 C 更强大」的一个例子**：C 没法在一次运算里同时拿到结果和溢出标志，但 IR 可以。

## 12.8 小结

- 三种额外信息载体：**指令标志**（影响单条指令语义）、**属性**（函数/参数的事实）、**元数据**（附注，不影响正确性）。
- 属性组 `#0` 用于去重；`optnone` 是 `-O0` 的关键属性。
- `memory(...)` 是新一代的内存行为描述，正在取代 `readnone`/`readonly`/`argmemonly`。
- `noundef` 来自「C 里传未初始化值是 UB」，给了优化器很大权力。
- 调试元数据保留 C 的类型名和符号性 —— 补偿了 IR 类型系统丢失的信息。
- `!tbaa` 表达严格别名规则。
- 内建函数以 `llvm.` 开头，类型编码在名字里，由后端直接生成代码。
- `llvm.*.with.overflow` 返回 `{ 结果, 溢出标志 }`，是 IR 能力的体现。
