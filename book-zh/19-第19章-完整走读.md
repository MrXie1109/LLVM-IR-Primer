## 19.2 全景图

```
                    源码文本
                       │
        ┌──────────────┴──────────────┐
        │  lexer.py                    │  字符 → token
        │  tokenize(text) -> [Token]   │
        └──────────────┬──────────────┘
                       │  token 流
        ┌──────────────┴──────────────┐
        │  reader.py                   │  token → S-表达式
        │  read_all(text) -> [list]    │
        └──────────────┬──────────────┘
                       │  S-表达式（Python list / int / Sym）
        ┌──────────────┴──────────────┐
        │  compiler.py                 │  S-表达式 → IR
        │  Compiler.compile_program()  │
        │    ├─ collect()   第一遍：签名 │
        │    └─ emit_top()  第二遍：函数体│
        └──────────────┬──────────────┘
                       │  调用 ir.py 的 API
        ┌──────────────┴──────────────┐
        │  ir.py                       │  IR 结构 → 文本
        │  Module / Function / Block   │
        │  Value / Phi                 │
        └──────────────┬──────────────┘
                       │
                   LLVM IR 文本
```

**注意 `ir.py` 在图的底部，而且它不知道 Lisp 的存在。** 这是第 15 章强调的分层。

验证的时候要小心措辞，因为 Python 自己有关键字 `while`，而文档字符串里也会出现一些词。更精确的检查是「有没有 Lisp 特有的构造名」：

```bash
$ grep -n '"defn"\|"let"\|"set"\|"if"\|"while"\|Sym\|read_all' ir.py
（无输出）
```

**没有任何匹配。** `ir.py` 里出现的 `while`（第 152、220、342 行等）全是 **Python 的 `while` 语句**，`let` 出现在英文注释里（"let the block body be filled in later"）—— 都不是对 Lisp 的引用。

唯一的痕迹是 `Module.__init__` 的默认名字：

```python
def __init__(self, name="lisp_module"):
```

这是个无关紧要的默认字符串，我们的编译器渲染时根本不使用它。

**结论成立**：`ir.py` 不依赖源语言，可以被任何前端复用。

## 19.3 各模块的结构清单

### `ir.py`：IR 构建器

```
IRError                 异常
Value(ty, name)         SSA 值（可以是常量！）
Phi(ty, name, block)    未完成的 phi 节点
Block(label)            基本块
  add(text)             追加指令（终结后禁止）
  terminate(text)       设置终结指令
  render(prefix)        渲染成文本

Function(name, ret_ty, param_types, param_names)
  new_block(hint)       创建块
  start(block)          移动插入点
  reserve_block(hint)   预留标签（第 18 章）
  branch_placeholder()  跳到一个预留块
  realize(placeholder)  把预留块变成真实块
  new_temp()            分配命名临时值 %tN
  emit(text)            发射指令
  emit_value(ty, text)  发射产生值的指令
  set_term(text)        设置终结指令
  branch(target)        无条件跳转
  cond_branch(c,t,e)    条件跳转
  alloca_slot(ty, hint) 在入口块分配栈槽
  var(name, ty)         读变量（SSA 构造）
  set_var(name, ty, v)  写变量
  seal_block(block)     密封块（完成 phi）
  materialize_phis()    把 phi 插到块开头
  render()              渲染整个函数

Module(name)
  add_global / declare / add_function / render
```

### `compiler.py`：代码生成

```
Var(ir_name, ty, slot, mutable)      变量（SSA 值 或 栈槽）
Frame(parent)                        词法作用域链
FunctionSig(name, ret_ty, param_types) 函数签名

SYMBOL_PREFIX = "l_"                 符号修饰前缀
mangle(name)                         Lisp 名 → IR 符号名
OPERATOR_METHODS                     运算符 → 方法名字典

Compiler
  compile_program(text)   入口：两遍扫描
  collect(form)           第一遍：收集签名
  emit_top(form)          第二遍：生成
  compile_function(form)  编译一个函数
  compile_expr(fn, env, e) 核心分派
  read_var(fn, var)       读变量
  op_let / op_set / op_if / op_while   特殊形式
  compile_call            函数调用
  _binary + op_add..op_ne 算术与比较
  to_i1(fn, val)          规约到 i1

compile_text(text)      便捷入口
main(argv)              命令行入口
```

### 运算符分派表

第 17 章提到过 `OPERATOR_METHODS`，这里是它的完整内容：

```python
OPERATOR_METHODS = {
    "let": "op_let",
    "if": "op_if",
    "while": "op_while",
    "set": "op_set",
    "+": "op_add",
    "-": "op_sub",
    "*": "op_mul",
    "/": "op_div",
    "%": "op_mod",
    "<": "op_lt",
    "<=": "op_le",
    ">": "op_gt",
    ">=": "op_ge",
    "=": "op_eq",
    "==": "op_eq",
    "!=": "op_ne",
}
```

**为什么用一张显式的表，而不是机械地把符号名转成方法名？**

有一种看起来更「聪明」的做法是靠符号名机械地拼出方法名：

```python
handler = getattr(self, f"op_{head.name.replace('-', '_')}", None)
```

然后 `read_one('(< a b)')` 编译失败：

```
IRError: unknown operator or function '<'
```

**原因**：`<` 会被转成 `op_<`，而 `op_<` **不是合法的 Python 标识符**。同样的问题也会出现在 `=`, `/`, `*`, `+` 上（这些符号不能出现在 Python 名字里）。

教训：

> **源语言的标识符集合和目标语言的标识符集合不一样，中间需要一个显式映射。**

这与 `mangle` 是同一类问题的两个层面：

- `mangle` 解决「Lisp 函数名 → IR 符号名」；
- `OPERATOR_METHODS` 解决「Lisp 运算符名 → Python 方法名」。

## 19.4 完整流程：编译 `fib`

我们把一个真实的例子从头到尾走一遍。

### 第 0 步：源码

```lisp
; Recursive Fibonacci: the classic first LLVM IR program.
(defn fib (n)
  (if (< n 2)
      n
      (+ (fib (- n 1)) (fib (- n 2)))))
```

### 第 1 步：词法分析

```python
>>> from lexer import tokenize
>>> toks = tokenize(open('examples/fib.lisp').read())
>>> [(t.kind, t.value) for t in toks[:12]]
[('punct', '('), ('sym', 'defn'), ('sym', 'fib'), ('punct', '('),
 ('sym', 'n'), ('punct', ')'), ('punct', '('), ('sym', 'if'),
 ('punct', '('), ('sym', '<'), ('sym', 'n'), ('int', 2)]
```

**注意 `;` 注释那行没有产生任何 token** —— 词法分析器直接跳过了。

注意 `-` 的处理：在 `(- n 1)` 里，`-` 后面是空格，所以是符号；而 `-3` 会被识别成整数（第 16 章）。

### 第 2 步：语法分析

```python
>>> from reader import read_all
>>> forms = read_all(open('examples/fib.lisp').read())
>>> forms[0]
[defn, fib, [n], [if, [<, n, 2], n, [+, [fib, [-, n, 1]], [fib, [-, n, 2]]]]]
```

一个嵌套列表。`defn`、`fib`、`n`、`if` 等是 `Sym` 对象，`2` 和 `1` 是 Python `int`。

### 第 3 步：第一遍扫描（收集签名）

```python
>>> from compiler import Compiler
>>> c = Compiler()
>>> c.collect(forms[0])
>>> c.sigs
{'fib': <FunctionSig fib -> i32(i32)>}
```

此时 `fib` 的签名已经登记，**所以函数体里的递归调用能找到它**。这就是两遍扫描的意义。

### 第 4 步：第二遍扫描（生成函数体）

```python
>>> c.emit_top(forms[0])
>>> print(c.module.render())
```

```llvm
define i32 @l_fib(i32 %n) {
entry0:
  %t1 = icmp slt i32 %n, 2
  br i1 %t1, label %then1, label %else2
then1:
  br label %merge3
else2:
  %t2 = sub i32 %n, 1
  %t3 = call i32 @l_fib(i32 %t2)
  %t4 = sub i32 %n, 2
  %t5 = call i32 @l_fib(i32 %t4)
  %t6 = add i32 %t3, %t5
  br label %merge3
merge3:
  %t7 = phi i32 [ %n, %then1 ], [ %t6, %else2 ]
  ret i32 %t7
}
```

**这就是全部。** 一个 20 行的 Lisp 函数变成了 12 行 IR。

### 第 5 步：逐行对照

| Lisp | IR | 说明 |
|---|---|---|
| `(defn fib (n) ...)` | `define i32 @l_fib(i32 %n)` | 符号修饰（第 17 章） |
| `(< n 2)` | `%t1 = icmp slt i32 %n, 2` | 比较产出 `i1`（第 4 章） |
| `(if ...)` | `br i1 %t1, label %then1, label %else2` | 条件跳转 |
| `n`（then 分支） | `br label %merge3` | `n` 是参数，**不需要 load** |
| `(- n 1)` | `%t2 = sub i32 %n, 1` | 算术 |
| `(fib ...)` | `%t3 = call i32 @l_fib(i32 %t2)` | 递归调用 |
| `(+ (fib..) (fib..))` | `%t6 = add i32 %t3, %t5` | |
| 汇合 | `%t7 = phi i32 [ %n, %then1 ], [ %t6, %else2 ]` | **第 18 章的核心** |
| 返回 | `ret i32 %t7` | |

### 第 6 步：验证

```bash
$ python3 compiler.py examples/fib.lisp > fib.ll
$ llvm-as-18 fib.ll -o fib.bc && echo VERIFIED
VERIFIED
```

### 第 7 步：链接并执行

```c
#include <stdio.h>
int l_fib(int);
int main(void) {
    for (int i = 0; i < 10; i++) printf("fib(%d)=%d\n", i, l_fib(i));
    return 0;
}
```

```bash
$ clang-18 -w main.c fib.bc -o fibtest && ./fibtest
fib(0)=0
fib(1)=1
fib(2)=1
fib(3)=2
fib(4)=3
fib(5)=5
fib(6)=8
fib(7)=13
fib(8)=21
fib(9)=34
```

**fib(9)=34。正确。**

## 19.5 诚实说明：哪些代码是「活」的

这是本章最重要的一节。第 15 章承诺过要诚实地说明边界。

### 完全用到的

| 模块 | 状态 |
|---|---|
| `lexer.py` | 全部用到 |
| `reader.py` | 全部用到（`'` 引号形式除外，编译器不认识 `quote`） |
| `compiler.py` 的 `Var`、`Frame`、`compile_expr`、`op_let`、`op_set`、`op_if`、`op_while`、`compile_call`、算术/比较、`to_i1` | 全部用到 |
| `ir.py` 的 `Block`、`Function` 的 `new_block`/`start`/`emit`/`emit_value`/`branch`/`cond_branch`/`reserve_block`/`branch_placeholder`/`realize`/`alloca_slot`/`render`、`Module` | 全部用到 |

### 备用机制（当前没有被调用）

`ir.py` 里有一套**完整的 SSA 构造机制**，是我们**没有用到**的：

| 代码 | 为什么没用到 |
|---|---|
| `Function.var(name, ty)` | 我们的编译器直接用 `read_var`，不经过 SSA 变量表 |
| `Function.set_var(name, ty, v)` | 同上 |
| `Function._read_variable` | 只被 `var` 调用 |
| `Function._add_phi_operand` | 同上 |
| `Function._complete_phi` | 只被 `seal_block` 调用 |
| `Function.seal_block` | `op_while` 里调用了，但因为变量都在内存里，它无事可做 |
| `Function.materialize_phis` | 被 `render` 调用，但块里没有通过这套机制产生的 `phi` |
| `Phi` 类 | 同上 |

**这是一个真实的工程现象。** `ir.py` 被设计成一个**通用**的 IR 构建器，能够支持「把可变变量提升为 SSA 值」这种更高级的代码生成策略（就是 Braun 等人的 sealed-block 算法）。但本书的编译器**选择了「变量放内存」这条更简单的路**，于是这套机制闲置了。

### 为什么保留它

三个理由：

1. **它展示了完整的 SSA 构造算法。** 第 18 章那个 `phi` bug 的根源就是「前驱未知时如何构造 SSA」——这套代码正是那个问题的系统化解法。读者如果要做纯 SSA 的前端，这里是起点。
2. **`op_if` 本来是可以用它的。** 如果我们把 `if` 的两个分支值也纳入变量表，就不用手工发射 `phi` 了。手工发射让我们**看得更清楚**，但通用机制更可扩展。
3. **诚实的架构应该允许未使用的抽象。** 一个把所有代码都用上的设计，往往意味着抽象层次被压得太低。

**但重要的是：本书明确告诉你这件事。** 否则你读代码时会以为 `seal_block` 是关键路径，然后花时间去理解一套其实没跑起来的逻辑 —— 那是浪费时间。

> **这也是「避免描述与实际不符」的一部分**：不只是「书里的 IR 输出要和实际一致」，还包括「书里对代码结构的描述要和实际一致」。

### 一个小实验：证明那套机制确实闲置

在 `ir.py` 的 `materialize_phis` 里加一行打印：

```python
def materialize_phis(self):
    for block in self.blocks:
        phis = [
            (name, entry)
            for name, entry in block.bindings.items()
            if isinstance(entry, Phi)
        ]
        if not phis:
            continue
```

如果你在 `if not phis: continue` 之前加 `print("phi found", block.label)`，然后编译 `fib`，你会发现**没有任何输出** —— 因为 `l_fib` 里唯一的 `phi` 是 `op_if` 手工发射的文本，不在 `bindings` 里。

**这验证了我们的说法。**

## 19.6 几个实现的细节说明

### 为什么 `emit_top` 和 `collect` 要分开写

因为它们处理的**阶段**不同：

```python
def collect(self, form):
    """第一遍：只登记签名，不生成代码。"""
    if is_sym(head, "defn"):
        self._check_defn_shape(form)          # ← 形状检查在这里
        name = form[1].name
        params = [p.name for p in form[2]]
        self.sigs[name] = FunctionSig(mangle(name), I32, [I32] * len(params))
```

**形状检查（`_check_defn_shape`）放在第一遍**，因为：

- 如果 `defn` 写错了，我们希望**在生成任何 IR 之前**就报错；
- 否则用户会得到「半个模块 + 一个异常」，难以判断哪部分可信。

这是第 16.6 节讲的「尽早断言」原则。

### 为什么 `compile_expr` 用 `getattr` 分派

```python
handler_name = OPERATOR_METHODS.get(head.name)
handler = getattr(self, handler_name, None) if handler_name else None
if handler is None:
    if head.name in self.sigs:
        return self.compile_call(fn, env, expr)
    raise IRError(f"unknown operator or function {head.name!r}")
return handler(fn, env, expr)
```

**分派顺序**：特殊形式/运算符 → 用户函数 → 报错。

这意味着：**用户不能定义一个叫做 `if` 的函数来覆盖特殊形式**。这是一个有意的设计选择（和大多数 Lisp 不同，Scheme 允许 `if` 被遮蔽）。我们选简单。

### 为什么 `_binary` 这么短

```python
def _binary(self, fn, env, expr, opname, ret_ty=I32):
    _, a, b = expr
    va = self.compile_expr(fn, env, a)
    vb = self.compile_expr(fn, env, b)
    return fn.emit_value(ret_ty, f"{opname} {va.ty} {va.name}, {vb.name}")

def op_add(self, fn, env, expr):
    return self._binary(fn, env, expr, "add")
```

因为**LLVM 的指令语法高度规整**：所有二元运算都是 `<op> <type> <lhs>, <rhs>`。所以十个运算符（`add`/`sub`/`mul`/`sdiv`/`srem`/`icmp slt`/...）共用同一个辅助函数。

**这是 LLVM IR 设计良好的一个体现**：规整的语法让代码生成器可以很短。对比一下 x86 汇编 —— 那个后端就需要几百个模式匹配规则。

比较运算只是多传一个 `ret_ty=I1`：

```python
def op_lt(self, fn, env, expr):
    return self._binary(fn, env, expr, "icmp slt", ret_ty=I1)
```

于是 `(< a b)` 生成 `icmp slt i32 %a, %b`，类型是 `i1`。

## 19.8 小结

- 四层架构：`lexer` → `reader` → `compiler` → `ir`，依赖单向。
- **`ir.py` 不知道 Lisp 的存在**，可以被任何前端复用 —— 这是 LLVM「前后端通过 IR 通信」思想的小尺度体现。
- `fib` 的完整流程：源码 → token → S-表达式 → 签名 → IR → 验证 → 链接 → 执行，得到 `fib(9)=34`。
- **诚实说明**：`ir.py` 里有一套完整的通用 SSA 构造机制（`var`/`set_var`/`seal_block`/`Phi`）是**闲置的备用设施**。我们的实际策略是**混合的**（第 17.6 节）：参数用 SSA 值、`let` 变量用栈槽、`if` 的结果用**手工发射的 `phi`**。
- 运算符分派用**显式字典**，因为 `<`、`=`、`/` 不能直接做 Python 方法名（第 17 章的编号值 bug 之后的第二个真实教训）。
- LLVM 指令语法规整，所以十个二元运算符能共用一个 `_binary` 辅助函数。
