# 第 14 章 从读 IR 到写 IR：构建顺序与生命周期

## 14.1 回指：第 2 章那段 IR 是怎么「长出来」的

先回到第 2 章。当时你看到：

```llvm
define dso_local i32 @mul_add(i32 noundef %0, i32 noundef %1, i32 noundef %2) #0 {
  %4 = alloca i32, align 4
  %5 = alloca i32, align 4
  %6 = alloca i32, align 4
  store i32 %0, ptr %4, align 4
  ...
  %9 = mul nsw i32 %7, %8
  %10 = load i32, ptr %6, align 4
  %11 = add nsw i32 %9, %10
  ret i32 %11
}
```

当时的解释是「`alloca` 服务于调试器」。那是**为什么**。本章要回答的是**怎么**：一个程序要按什么顺序做事，才能产出上面这段文本？

答案的关键在于：**这段文本是有顺序的，而这个顺序不是随便排的。**

`%9 = mul nsw i32 %7, %8` 这一行，必须出现在 `%7` 和 `%8` 被定义**之后**。`ret i32 %11` 必须出现在 `%11` 被定义之后。而三条 `alloca` 挤在开头，`store` 紧跟其后 —— 这个顺序是生成器**刻意**安排的结果，不是巧合。

所以写 IR 生成器的核心问题是：

> **「我当前应该把新指令写在哪里？」**

这个「当前位置」有个正式名字：**插入点**（insertion point）。

本章还有第二重回指。第 5 章我们说过：

> **`-O0` 下变量住在内存里，所以 `phi` 很少。**

本章会从**生成器的角度**解释这个设计决定 —— 它不是偷懒，而是把「支配分析」这个难题换成了「多几次内存访问」。第 17 章你会看到这个权衡如何让我们的编译器变得简单可靠。

## 14.2 插入点：一个游标

想象你在编辑一个文本文件。你没有「追加到末尾」式的写入，而是有一个**游标**，新输入的文字插在游标处，插入后游标前进。

IR 生成器的插入点稍微复杂一点，因为它有两层结构：

```
函数
├── 基本块 A   ← 插入点可以指向「A 的末尾」
│   ├── 指令 1
│   └── 指令 2
├── 基本块 B
│   └── 指令 3
└── 基本块 C
```

插入点由**「哪个基本块」+「块内哪个位置」**共同决定。绝大多数时候位置就是「块的末尾」（因为我们是顺序生成指令的），所以实践中插入点常常被简化为「当前基本块」。

**这就是为什么生成器里通常有个 `current` 字段。**

```python
class Function:
    def __init__(self, ...):
        self.current = None      # ← 插入点

    def start(self, block):
        """把插入点移到 block 的末尾。"""
        self.current = block
        return block

    def emit(self, text):
        """在当前插入点插入一条指令。"""
        self.current.add(text)
```

`emit` 只有一行，但它是整个生成器的中枢：**所有指令的产生最终都要经过它，因此所有指令都自动落在正确的块里。**

## 14.3 第一原则：先创建基本块，再往里填指令

这里有一个新手最容易踩的坑，而且它导致的错误信息非常难懂。

### 错误示范

```python
# 我想生成一个函数，它的第一条指令是 ret
fn = Function("f", I32, [I32, I32])
fn.emit("ret i32 0")          # ← 插入点还没设置！
```

如果你在 `current` 是 `None` 的时候 `emit`，会得到一个 `AttributeError` —— 这个错误还算友好。但如果你的实现是「自动创建块」，你会得到更糟的结果：

```llvm
define i32 @f(i32, i32) {
  ret i32 0
}
```

这**看起来**没问题，`llvm-as-18` 甚至会接受它！但它在语义上是错的：一个没有标签的块是「匿名入口块」，而你后面想往里面加东西时，你会发现自己拿不到那个块了。

### 正确做法

```python
fn = Function("f", I32, [I32, I32])
entry = fn.new_block("entry")   # 1. 先创建块
fn.start(entry)                 # 2. 把插入点移进去
fn.emit("ret i32 0")            # 3. 现在才填指令
```

**顺序不能颠倒。** 记住这个三步式：

> **new_block → start → emit**

把 `merge_block` 的产生和填充混在一起，就会踩到这个顺序问题。LLVM 验证器给出的报错非常绕：

```
PHI node entries do not match predecessors!
  %t5 = phi i32 [ %t2, %then1 ], [ %t4, %else2 ]
label %else2
label %merge6
```

这个报错的意思是：「你的 `phi` 声称 `%else2` 会跳到我这里，但 `%else2` 实际上跳到了 `%merge6`。」—— 根因就是插入点跑偏了。第 18 章会完整复盘这个 bug。

### 为什么基本块必须先创建

因为**前向引用**。看这个 IR：

```llvm
entry:
  %c = icmp slt i32 %x, 0
  br i1 %c, label %then, label %else
then:
  br label %merge        ; ← 引用 %merge
else:
  br label %merge        ; ← 引用 %merge
merge:                   ; ← %merge 在这里才「定义」
  ret i32 0
```

`then` 块里的 `br` 引用了 `%merge`，但 `%merge` 的**内容**要到后面才写。这在文本上是前向引用。

一个纯文本生成器会怎么做？它可能先把 `br label %merge` 写成字符串，等 `%merge` 有内容了再替换。但这很脆弱。

更好的做法是：**「名字」和「内容」分离**。先创建块对象（名字定下来），内容留空；等真正要填内容的时候再填。这就是为什么我们的 `Block` 有个 `instructions` 列表，而不是直接持有文本。

```python
def new_block(self, label):
    block = Block(label)          # 名字现在就有
    self.blocks.append(block)
    return block
    # 注意：block.instructions 此刻是空的
```

**创建 ≠ 填充。** 这是本章最重要的一句话。

## 14.4 第二原则：定义必须支配使用

SSA 形式有一条铁律：

> **一个值的定义必须支配它的所有使用。**

「支配」（dominate）的意思是：**从函数入口出发，到达任意一个使用点的每一条路径，都必然经过定义点。**

举个反例。这段 IR 是**非法**的：

```llvm
define i32 @f(i32 %a, i1 %cond) {
entry:
  br i1 %cond, label %t, label %f
t:
  %x = add i32 %a, 1        ; %x 只在 t 里定义
  br label %m
f:
  br label %m
m:
  %y = add i32 %x, 1        ; ← 非法！从 f 走到 m 时 %x 根本没定义
  ret i32 %y
}
```

`llvm-as-18` 会拒绝它：

```bash
$ llvm-as-18 bad_dom.ll -o /dev/null
llvm-as-18: assembly parsed, but does not verify as correct!
Instruction does not dominate all uses!
  %x = add i32 %a, 1
  %y = add i32 %x, 1
```

**这条规则对生成器的设计要求是巨大的。** 它意味着：你在生成 `%y = add i32 %x, 1` 的时候，必须**已经**保证了「无论走哪条路，`%x` 都是确定的」。

这就是为什么本书的编译器最终选择了「可变变量放 `alloca`」的策略（第 17 章）。因为一旦变量住在内存里，`load` 出来的值就是**当前块里新定义的值**，它天然支配自己的使用点 —— 你不需要做任何支配分析。

**用内存换取 SSA 构造的简单性**，这是 clang `-O0` 的做法，也是我们的做法。等 `mem2reg` 把这些内存操作提升为 SSA 时，它会**替我们**做支配分析并插入 `phi`（第 5 章、第 20 章都实测过）。

> 在第 2 章你看到 `-O0` 的 IR 臃肿而困惑；在第 14 章你看到了这个臃肿的**工程理由**：它让生成器的复杂度从「需要完整支配树」降到「顺序发射指令」。这不是 clang 偷懒，是一个深思熟虑的权衡。

## 14.5 第三原则：每个基本块必须以终结指令结尾

基本块的定义就是「一段只有一个入口、一个出口的指令序列」。终结指令（`ret`、`br`、`switch`、`unreachable`）就是那个出口。

**终结指令之后不能再有指令。** LLVM 在文本解析阶段就会报错：

```llvm
define i32 @f() {
entry:
  ret i32 0
  %x = add i32 1, 2      ; ← 解析错误
}
```

```bash
$ llvm-as-18 bad_after_term.ll -o /dev/null
llvm-as-18: bad_after_term.ll:5:1: error: expected instruction opcode
}
^
```

报错信息 `expected instruction opcode` 的意思是「这里应该开始一个新基本块了」—— 因为解析器认为 `ret` 已经结束了当前块，接下来必须是标签或新的 `define`。

**如果块没有终结指令呢？** 结果**完全一样**：

```llvm
define i32 @f(i32 %a) {
entry:
  %x = add i32 %a, 1
}
```

```bash
$ llvm-as-18 no_term.ll -o /dev/null
llvm-as-18: no_term.ll:4:1: error: expected instruction opcode
}
^
```

**两条不同的错误，同一个报错信息。** 这初看令人困惑，其实很合理：解析器读到 `}` 时，两种情况都表现为「我还在期待下一条指令，却遇到了函数的结尾」。

> **这正是一个教训**：LLVM 的报错指向**文本**，而你要诊断的是**生成逻辑**。看到 `expected instruction opcode`，你要同时怀疑「多余指令」和「缺少终结指令」两种可能 —— 而生成器自己的断言（14.7 节）能把这两者区分开。

**所以在生成器里，这两条约束都应该提前断言。**

## 14.6 最小骨架：生成一个 `add` 函数

现在把以上原则落成一个能跑的程序。它只做一件事：生成

```llvm
define i32 @add(i32 %a, i32 %b) {
entry:
  %t1 = add i32 %a, %b
  ret i32 %t1
}
```

代码如下。它只有约 100 行，而且**几乎没有超出前面几节讲的规则**。

```python
#!/usr/bin/env python3
"""minimal_codegen.py -- 生成一个 add 函数，仅此而已。

这个文件是第 14 章的产物，也是第 15 章项目骨架的雏形。
它存在的唯一目的是让「插入点」和「创建/填充分离」这两个概念
变成可以运行、可以验证的东西。
"""


class Block:
    """一个基本块：有名字，有指令列表，可以有终结指令。"""

    def __init__(self, label):
        self.label = label
        self.instructions = []
        self.terminator = None

    def add(self, text):
        """在当前块末尾追加一条指令。"""
        if self.terminator is not None:
            # 终结指令之后不能再有指令：这是基本块的定义。
            raise RuntimeError(
                f"block %{self.label} already terminated; cannot add: {text}"
            )
        self.instructions.append("  " + text)

    def terminate(self, text):
        """设置终结指令。一个块只能有一条。"""
        if self.terminator is not None:
            raise RuntimeError(f"block %{self.label} already has a terminator")
        self.terminator = "  " + text

    def render(self):
        if self.terminator is None:
            raise RuntimeError(f"block %{self.label} has no terminator")
        lines = [f"{self.label}:"] + self.instructions + [self.terminator]
        return "\n".join(lines)


class Function:
    """一个函数：若干个基本块，加上一个「插入点」。"""

    def __init__(self, name, ret_ty, param_types, param_names):
        self.name = name
        self.ret_ty = ret_ty
        self.param_types = param_types
        self.param_names = param_names
        self.blocks = []
        self.current = None          # 插入点
        self.temp = 0

    def new_block(self, label):
        """只创建，不填充。"""
        block = Block(label)
        self.blocks.append(block)
        return block

    def start(self, block):
        """把插入点移到这个块的末尾。"""
        self.current = block
        return block

    def new_temp(self):
        self.temp += 1
        return f"%t{self.temp}"

    def emit(self, text):
        """在当前插入点插入一条指令。"""
        if self.current is None:
            raise RuntimeError(
                "insertion point is not set; call start(new_block(...)) first"
            )
        self.current.add(text)

    def emit_value(self, ty, text):
        """插入一条产生值的指令，返回它的名字。"""
        name = self.new_temp()
        self.emit(f"{name} = {text}")
        return name

    def terminate(self, text):
        """在当前块的末尾设置终结指令。"""
        if self.current is None:
            raise RuntimeError(
                "insertion point is not set; call start(new_block(...)) first"
            )
        self.current.terminate(text)

    def render(self):
        params = ", ".join(
            f"{ty} {n}" for ty, n in zip(self.param_types, self.param_names)
        )
        out = [f"define {self.ret_ty} @{self.name}({params}) {{"]
        for block in self.blocks:
            out.append(block.render())
        out.append("}")
        return "\n".join(out)


def generate_add():
    """生成 define i32 @add(i32 %a, i32 %b)。"""
    fn = Function("add", "i32", ["i32", "i32"], ["%a", "%b"])

    # ---- 三步式：new_block → start → emit ----
    entry = fn.new_block("entry")
    fn.start(entry)

    r = fn.emit_value("i32", "add i32 %a, %b")
    fn.terminate(f"ret i32 {r}")

    return fn.render()


if __name__ == "__main__":
    print(generate_add())
```

运行它：

```bash
$ python3 minimal_codegen.py
define i32 @add(i32 %a, i32 %b) {
entry:
  %t1 = add i32 %a, %b
  ret i32 %t1
}
```

**注意这里用的是命名值 `%t1`，不是编号值。** 第 8 章讲过原因：命名值完全绕开 LLVM 那套「参数 + 匿名块 + 有结果的指令共享计数器」的规则。第 17 章会看到不自量力地去模拟编号规则会出什么事。

### 验证它

**永远不要相信自己生成的 IR。** 用 `llvm-as-18` 验证：

```bash
$ python3 minimal_codegen.py > add.ll
$ llvm-as-18 add.ll -o add.bc && echo "VERIFIED"
VERIFIED
```

再把函数名换成 `main` 直接执行：

```bash
$ python3 - <<'EOF' > addmain.ll
import sys; sys.path.insert(0, '.')
from minimal_codegen import Function
fn = Function("main", "i32", [], [])
e = fn.new_block("entry"); fn.start(e)
r = fn.emit_value("i32", "add i32 40, 2")
fn.terminate(f"ret i32 {r}")
print(fn.render())
EOF

$ llvm-as-18 addmain.ll -o addmain.bc
$ lli-18 addmain.bc; echo "exit=$?"
exit=42
```

`exit=42` —— 你刚刚用约 100 行 Python **生成并执行**了一段 LLVM IR。这是第三部分的起点。

## 14.7 骨架的自我防护

回头看那个骨架，有三处断言是特意加的。它们会在后面救你很多次。

**断言一：终结指令之后不能再加指令。**

```python
def add(self, text):
    if self.terminator is not None:
        raise RuntimeError(
            f"block %{self.label} already terminated; cannot add: {text}"
        )
```

这条断言把「指令发射到了终结指令之后」这个错误**在发生的那一行**就抓住。

**断言二：插入点未设置时 `emit` 报错。**

实测：

```bash
$ python3 -c "
import sys; sys.path.insert(0, '.')
from minimal_codegen import Function
fn = Function('f','i32',[],[])
fn.emit('ret i32 0')
"
RuntimeError: insertion point is not set; call start(new_block(...)) first
```

这条把「忘记 `start`」这个错误在发生的那一行抓住，而不是等到文件生成完、`llvm-as` 报出一个指向别处的错误。

**断言三：块必须有终结指令。**

```python
def render(self):
    if self.terminator is None:
        raise RuntimeError(f"block %{self.label} has no terminator")
```

这条在**输出**时检查，因为「块是否终结」只有在块写完之后才能判断。

> **这个模式的普适性**：生成器应该在自己的抽象层次上维护不变量，并在违反时立刻报错。如果你放任非法状态流到输出文本里，你就把调试工作外包给了 LLVM 解析器 —— 而它的错误信息是针对**文本**的，不是针对**你的生成逻辑**的。第 16 章我们会用同样的思路设计 AST 校验。

## 14.8 从骨架到完整编译器：还缺什么

这个骨架已经能生成直线代码了。要变成第三部分那个完整的编译器，还需要补上四块：

| 缺口 | 补在哪一章 |
|---|---|
| 词法与语法分析（把 Lisp 文本变成 AST） | 第 16 章 |
| 表达式、变量、函数调用 | 第 17 章 |
| 控制流：`br`、`phi`、循环 | 第 18 章 |
| 测试、验证与 `mem2reg` 配合 | 第 20 章 |

其中**控制流是最难的一块**，因为它同时牵动本章讲的两个原则：

- 分支意味着你要生成**多条路径**，每条路径都要独立维护插入点；
- 汇合意味着你需要 `phi`，而 `phi` 的操作数是**基本块**，所以你必须保证那些块**已经创建**（哪怕还没填充）。

而且还有一个更阴险的坑：**嵌套控制流会让「当前块」在编译子表达式时被悄悄换掉**。第 18 章会详细分析这个坑，以及它产生的报错。

## 14.9 小结

- 生成 IR 的核心概念是**插入点**：新指令插在哪里。
- 生成的顺序不是自由的：**定义必须在使用之前**（文本顺序），**定义必须支配使用**（SSA 语义）。
- 基本块**先创建、后填充**。创建带来名字，填充带来内容，两者分离才能支持前向引用。
- 三步式：**`new_block` → `start` → `emit`**。
- 每个基本块**必须以终结指令结尾**，且终结指令之后不能有指令。
- 「可变变量放 `alloca`」不是偷懒，而是**用内存换掉支配分析** —— 这正是 clang `-O0` 的策略，也是我们编译器的策略。
- 生成器应该在自己的层次上断言不变量（「插入点已设置」「块未终结」「块已终结」），而不是把非法文本交给 LLVM 去发现。
- **生成临时值时用命名值而非编号值**，可以完全绕开第 8 章那套计数器规则。
