# 第 7 章 函数、调用约定与链接

## 7.1 定义与声明

IR 里函数有两种形态：

```llvm
define i32 @defined_here(i32 %x) {    ; 有函数体 —— 定义
  ret i32 %x
}

declare i32 @defined_elsewhere(i32)   ; 没有函数体 —— 声明
```

| | `define` | `declare` |
|---|---|---|
| 有函数体 | 是 | 否 |
| 参数名 | 需要（函数体里要用） | 通常省略 |
| 相当于 C 的 | 函数定义 | `extern` 声明 / `#include` 里的原型 |

实测。先看调用外部函数：

```c
int add(int, int);                      /* 声明 */
int call_add(int a, int b) { return add(a, b); }
```

`-O0`：

```llvm
define dso_local i32 @call_add(i32 noundef %0, i32 noundef %1) #0 {
  %3 = alloca i32, align 4
  %4 = alloca i32, align 4
  store i32 %0, ptr %3, align 4
  store i32 %1, ptr %4, align 4
  %5 = load i32, ptr %3, align 4
  %6 = load i32, ptr %4, align 4
  %7 = call i32 @add(i32 noundef %5, i32 noundef %6)
  ret i32 %7
}

declare i32 @add(i32 noundef, i32 noundef) #1
```

两件事值得注意：

1. **`call i32 @add(i32 noundef %5, i32 noundef %6)`** —— 注意实参也带着 `noundef`。这是参数属性，表示「这个实参不会是 `undef`」。
2. **`declare` 语句出现在函数体之后**。IR 文件里 `declare` 和 `define` 的相对位置是自由的，但习惯上 clang 把未定义的符号放在后面。

**`declare` 的参数没有名字**（`i32 noundef` 而不是 `i32 noundef %x`），因为它没有函数体，不需要引用参数。

## 7.2 递归与相互递归

递归在 IR 里没有任何特殊之处 —— 函数调用自己就是普通的 `call`：

```c
int fact(int n) { return n <= 1 ? 1 : n * fact(n - 1); }
```

`-O0`：

```llvm
define dso_local i32 @fact(i32 noundef %0) #0 {
  %2 = alloca i32, align 4
  store i32 %0, ptr %2, align 4
  %3 = load i32, ptr %2, align 4
  %4 = icmp sle i32 %3, 1
  br i1 %4, label %5, label %6

5:                                                ; preds = %1
  br label %12

6:                                                ; preds = %1
  %7 = load i32, ptr %2, align 4
  %8 = load i32, ptr %2, align 4
  %9 = sub nsw i32 %8, 1
  %10 = call i32 @fact(i32 noundef %9)
  %11 = mul nsw i32 %7, %10
  br label %12

12:                                               ; preds = %6, %5
  %13 = phi i32 [ 1, %5 ], [ %11, %6 ]
  ret i32 %13
}
```

**这里有 `phi`！** 而且它是本章最好的教学样本：

```llvm
12:                                               ; preds = %6, %5
  %13 = phi i32 [ 1, %5 ], [ %11, %6 ]
```

读作：从 `%5`（递归基）来，结果是 `1`；从 `%6`（递归步）来，结果是 `%11`（`n * fact(n-1)`）。

注意 `%5` 块里**没有 `load`** —— 它直接用了常量 `1`。这就是为什么这里 clang 选择了 `phi` 而不是「存储返回值到内存槽位」：三目运算符的结果是一个**纯表达式**，clang 在 `-O0` 下也愿意为它生成 SSA 形式。

**相互递归**也没有特殊性：

```c
static int helper(int x) { return x * 3; }
int use_helper(int x) { return helper(x); }
```

```llvm
define dso_local i32 @use_helper(i32 noundef %0) #0 {
  ...
  %4 = call i32 @helper(i32 noundef %3)
  ret i32 %4
}

define internal i32 @helper(i32 noundef %0) #0 {
  ...
  %4 = mul nsw i32 %3, 3
  ret i32 %4
}
```

注意 `define internal i32 @helper` —— `static` 变成了 `internal`，和全局变量一样。

## 7.3 间接调用：函数指针

```c
int apply(int (*f)(int,int), int a, int b) { return f(a, b); }
```

```llvm
define dso_local i32 @apply(ptr noundef %0, i32 noundef %1, i32 noundef %2) #0 {
  ...
  %7 = load ptr, ptr %4, align 8
  %8 = load i32, ptr %5, align 4
  %9 = load i32, ptr %6, align 4
  %10 = call i32 %7(i32 noundef %8, i32 noundef %9)
  ret i32 %10
}
```

**`call i32 %7(...)`** —— 被调用者是个**值**（`%7`），不是一个函数名。这就是间接调用。

在 LLVM 18 里，函数指针就是普通的 `ptr`（因为 opaque pointer）。在老版本 LLVM（≤14）里你会看到 `call i32 %7(...)` 但 `%7` 的类型是 `i32 (i32, i32)*` —— 一个**函数指针类型**。opaque pointer 把这一切统一成了 `ptr`。

**类型信息去哪了？** 它挪到了 `call` 指令里。`call i32 %7(i32 noundef %8, i32 noundef %9)` 完整地说明了返回值类型和参数类型。这就是 opaque pointer 的设计要点：**类型信息不再是「指针的一部分」，而是「使用它的指令的一部分」。**

## 7.4 变参函数

```c
#include <stdarg.h>
int sum_n(int n, ...) {
    va_list ap;
    va_start(ap, n);
    int s = 0;
    for (int i = 0; i < n; i++) s += va_arg(ap, int);
    va_end(ap);
    return s;
}
```

`-O0` 开头：

```llvm
%struct.__va_list_tag = type { i32, i32, ptr, ptr }

define dso_local i32 @sum_n(i32 noundef %0, ...) #0 {
  %2 = alloca i32, align 4
  %3 = alloca [1 x %struct.__va_list_tag], align 16
  %4 = alloca i32, align 4
  %5 = alloca i32, align 4
  store i32 %0, ptr %2, align 4
  %6 = getelementptr inbounds [1 x %struct.__va_list_tag], ptr %3, i64 0, i64 0
  call void @llvm.va_start(ptr %6)
  ...
```

要点：

1. **`define dso_local i32 @sum_n(i32 noundef %0, ...)`** —— 参数列表末尾的 `...` 就是变参标记。这是 IR 里唯一表示「参数个数不定」的方式。
2. **`va_list` 是一个具体类型** `%struct.__va_list_tag`，实现细节由目标平台决定。x86-64 SysV 的 `va_list` 包含寄存器保存区偏移、溢出区指针等，所以是 `{ i32, i32, ptr, ptr }`。
3. **`llvm.va_start` / `llvm.va_arg` / `llvm.va_end` 是内建函数**，不是普通库函数。它们直接用 `call` 调用，但名字以 `llvm.` 开头。

**变参函数是「目标相关」的典型例子。** 上面这段 IR 只在 x86-64 SysV 上有意义。换一个目标平台，`%struct.__va_list_tag` 的定义会完全不同。这是 IR 少数几个不完全目标无关的地方。

调用变参函数时，需要在 `call` 里声明参数类型：

```llvm
%r = call i32 (ptr, ...) @printf(ptr @fmt, i32 %v)
```

注意 `call i32 (ptr, ...) @printf(...)` —— 函数**类型**被显式写在被调用者前面，因为 `@printf` 是变参的，光看实参推不出完整签名。

## 7.5 内联与函数属性

```c
__attribute__((noinline)) int noinline_f(int x) { return x; }
__attribute__((always_inline)) static inline int always_f(int x) { return x + 1; }
__attribute__((noreturn)) void die(void) { __builtin_trap(); }
int use_inline(int x) { return always_f(x); }
```

`-O2`：

```llvm
; Function Attrs: mustprogress nofree noinline norecurse nosync nounwind willreturn memory(none) uwtable
define dso_local noundef i32 @noinline_f(i32 noundef returned %0) local_unnamed_addr #0 {
  ret i32 %0
}

; Function Attrs: noreturn nounwind memory(inaccessiblemem: write) uwtable
define dso_local void @die() local_unnamed_addr #1 {
  tail call void @llvm.trap()
  unreachable
}

; Function Attrs: cold noreturn nounwind memory(inaccessiblemem: write)
declare void @llvm.trap() #2

; Function Attrs: mustprogress nofree norecurse nosync nounwind willreturn memory(none) uwtable
define dso_local i32 @use_inline(i32 noundef %0) local_unnamed_addr #3 {
  %2 = add nsw i32 %0, 1
  ret i32 %2
}
```

四个观察：

1. **`noinline_f` 保留了 `noinline` 属性**，而且出现了 `returned %0` —— 这是一个参数属性，表示「返回值就是 `%0`」，让调用者可以省掉一次拷贝。

2. **`always_f` 完全消失了！** 没有 `define`，也没有 `declare`。它的函数体被**内联**进了 `use_inline`：`%2 = add nsw i32 %0, 1`。`always_inline` 生效了，而且因为它是 `static`（`internal`）且没有其他使用者，LLVM 把它整个删掉了。

3. **`die` 以 `unreachable` 结尾**，而不是 `ret void`。因为它是 `noreturn`，永远不会返回：

   ```llvm
   tail call void @llvm.trap()
   unreachable
   ```

   `unreachable` 是一条**终结指令**，它告诉优化器：「执行到这里是不可能的」。如果真到了，行为未定义 —— 这给了优化器极大的自由（它可以把 `unreachable` 之后的代码当作死代码删掉）。

4. **`tail call void @llvm.trap()`** —— `tail` 标记表示这是一个尾调用，可以被优化成跳转而不是调用。`llvm.trap()` 会触发一个陷阱指令（x86 上是 `ud2`），所以它确实不返回。

### 属性组

注意 `#0`、`#1`、`#2`、`#3` 这些引用，它们指向文件末尾的属性组：

```llvm
attributes #0 = { mustprogress nofree noinline norecurse nosync nounwind willreturn memory(none) uwtable "min-legal-vector-width"="0" ... }
```

属性组是用来**去重**的：多个函数共享同一组属性时，只需要写一份。第 12 章会详细讲这些属性的含义。

## 7.6 调用约定

`define` 和 `call` 都可以带**调用约定**：

```llvm
define fastcc i32 @fast_fn(i32 %x) {
  ret i32 %x
}

define i32 @caller(i32 %x) {
  %r = call fastcc i32 @fast_fn(i32 %x)
  ret i32 %r
}
```

常见的调用约定：

| 关键字 | 含义 |
|---|---|
| （省略） | C 调用约定（`ccc`），目标平台默认 |
| `fastcc` | 尽量把参数放在寄存器里，内部函数用 |
| `coldcc` | 用于很少执行的路径 |
| `cc 10` | GHC 约定；`cc 11` 是 HiPE；具体数字是平台特定的 |

`fastcc` 是 LLVM 内部使用的约定：它不遵循平台的 ABI，因此参数传递可以更灵活。**代价是它不能被外部代码调用。** 所以 clang 只会给 `internal` 函数用它。

实测（注意要加 `-fno-inline`，否则这个函数会被内联掉，我们就看不到它了）：

```c
static int helper(int x) { return x * 2; }
int pub(int x) { return helper(x) + 1; }
```

```bash
clang-18 -S -emit-llvm -O2 -fno-inline fastc.c -o -
```

```llvm
define dso_local i32 @pub(i32 noundef %0) local_unnamed_addr #0 {
  ...
}

define internal fastcc i32 @helper(i32 noundef %0) unnamed_addr #0 {
  ...
}
```

`@helper` 是 `internal`（C 的 `static`），所以 clang 放心地给它用了 `fastcc`。而 `@pub` 对外可见，必须遵循平台 ABI，所以用默认调用约定。

在 `-O0` 下你几乎不会看到 `fastcc`，因为 `-O0` 要保持 ABI 兼容以便调试。这也是**另一个 `-O0` 输出「啰嗦」的原因**：它必须严格遵循平台的调用约定。

（顺便注意：`@helper` 用的是 `unnamed_addr`，`@pub` 用的是 `local_unnamed_addr`。前者表示「这个函数的地址不重要」，后者表示「地址在模块内不重要但对外可能重要」。这类细微差别完全是优化器推断的结果，不必记忆。）

## 7.7 链接属性一览

函数的链接属性决定它在链接期的可见性：

| IR | C 对应 | 含义 |
|---|---|---|
| （默认） | 普通函数 | 外部可见，本模块定义 |
| `internal` | `static` | 只在模块内可见 |
| `private` | 无直接对应 | 只在模块内可见，且不出现在符号表 |
| `external` | `extern` 声明 | 定义在别处 |
| `linkonce_odr` | 模板/内联函数 | 可以重复定义，链接器保留一份 |
| `weak` | `__attribute__((weak))` | 可以被更强的定义覆盖 |
| `available_externally` | — | 只用于内联，不生成代码 |

一个 `dso_local` **不是**链接属性，它是「符号绑定」信息：表示这个符号可以在当前共享库内部解析，不需要走 GOT。

## 7.8 动手练习

**练习 7.1** 生成 `int fact(int n)` 的 `-O0` IR，找到那个 `phi`，逐字解释它的每个操作数。然后跑 `mem2reg`，看看 `phi` 有没有变化。

**练习 7.2** 手写一个 `.ll` 文件，定义 `@square(i32) -> i32`，再定义 `@main()` 调用它并返回 `square(7)`。用 `llvm-as-18` 验证，`lli-18` 执行，确认退出码是 49。

**练习 7.3** 生成一个含 `printf` 调用的 C 程序的 IR。找到 `call i32 (ptr, ...) @printf(...)`，解释为什么类型要写两遍。

**练习 7.4** 编译 `__attribute__((noreturn))` 的函数，确认它以 `unreachable` 结尾。然后手写一个用 `ret void` 结尾的版本，想想语义上有什么差别。

**练习 7.5** 把 `apply`（函数指针）的 IR 改成手写版本，用 `llvm-as-18` 验证，并用 C 驱动调用一个真实的函数指针。

**练习 7.6（思考题）** 在 LLVM 14 里，`apply` 的 `%7` 类型是 `i32 (i32, i32)*`。在 LLVM 18 里它是 `ptr`。类型信息从一个地方搬到了另一个地方 —— 说明搬到哪里，以及为什么这个设计更好。

## 7.9 小结

- `define` 是定义，`declare` 是声明。
- 递归和相互递归在 IR 里没有特殊性，就是普通的 `call`。
- 间接调用写成 `call <ret> %ptr(args...)`；LLVM 18 里函数指针是 `ptr`，类型信息在 `call` 指令上。
- 变参用 `...`，靠 `llvm.va_start` 等内建函数实现，且是目标相关的。
- `unreachable` 是终结指令，用于 `noreturn` 函数。
- 属性组 `#0`、`#1` 用于去重。
- 调用约定（`fastcc` 等）允许 LLVM 使用非 ABI 的参数传递，但只对内部函数安全。

**第一部分到此结束。** 你现在应该能够：看到一个 C 函数，大致想象出它的 IR 形状；看到一段 IR，说清楚它在干什么。
