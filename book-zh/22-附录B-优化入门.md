## B.1 `alloca` 为什么会消失：`mem2reg`

正文第 2 章讲过：`-O0` 下 C 的每个局部变量都有自己的 `alloca` 槽位。优化后的 IR 里这些槽位全都不见了。

做这件事的 pass 叫 **`mem2reg`**（memory to register）。它的判断条件是：

> **如果一个 `alloca` 出来的槽位从不被「取地址」（没有 `&x` 这类操作），并且所有读写都能被分析清楚，就把这个槽位提升为 SSA 值** —— 需要时自动插入 `phi` 节点。

看一个最小例子：

```c
int mul_add(int x, int y, int z) {
    return x * y + z;
}
```

`-O0`（函数体 12 条指令）：

```llvm
define dso_local i32 @mul_add(i32 noundef %0, i32 noundef %1, i32 noundef %2) #0 {
  %4 = alloca i32, align 4
  %5 = alloca i32, align 4
  %6 = alloca i32, align 4
  store i32 %0, ptr %4, align 4
  store i32 %1, ptr %5, align 4
  store i32 %2, ptr %6, align 4
  %7 = load i32, ptr %4, align 4
  %8 = load i32, ptr %5, align 4
  %9 = mul nsw i32 %7, %8
  %10 = load i32, ptr %6, align 4
  %11 = add nsw i32 %9, %10
  ret i32 %11
}
```

跑一次 `mem2reg`（注意要先把 `optnone` 去掉，见 [B.2](#b2-为什么跑-opt-没反应optnone)）：

```bash
clang-18 -S -emit-llvm -O0 mul_add.c -o mul_add.O0.ll
sed 's/ optnone//' mul_add.O0.ll > mul_add.nooptnone.ll
opt-18 -passes=mem2reg -S mul_add.nooptnone.ll -o -
```

```llvm
define dso_local i32 @mul_add(i32 noundef %0, i32 noundef %1, i32 noundef %2) #0 {
  %4 = mul nsw i32 %0, %1
  %5 = add nsw i32 %4, %2
  ret i32 %5
}
```

**12 条 → 3 条。** 所有 `alloca`/`store`/`load` 都消失了，参数直接参与运算。

**这就是 `-O2` 那「三行 IR」的来源。** 正文第 2 章强调过：宣称「`mul_add` 就是三行」的教程省略了前提 —— 那是 `-O2` 的样子。

### 为什么 `-O0` 不直接生成这三行？

因为两个要求：

1. **调试体验** —— 参数存进栈里，gdb 才能在函数执行的任意时刻显示它们；
2. **生成器简单** —— 把可变变量放内存，代码生成器就不需要做支配分析（详见 [B.3](#b3-见证-phi-的诞生)）。

代价是运行时的多余读写，而 `mem2reg` 会免费把它们消掉。这是 clang `-O0` 的策略，也是本书第三部分编译器的策略。

## B.2 为什么跑 `opt` 没反应：`optnone`

**这是初学者最容易困惑的一点。** 你按教程跑了：

```bash
opt-18 -passes=mem2reg -S mul_add.O0.ll -o -
```

**输出和输入一模一样。** 不是 `mem2reg` 坏了，而是函数头上有 `optnone`：

```llvm
; Function Attrs: noinline nounwind optnone uwtable
define dso_local i32 @mul_add(...) #0 {
```

`optnone` 的意思是「**不要优化这个函数**」。它是 `-O0` 明确要求的，目的是让调试体验可预测。**任何 pass 见到它都会直接跳过，而且不会给出任何提示。**

把 `optnone` 去掉就正常了：

```bash
sed 's/ optnone//' mul_add.O0.ll > mul_add.nooptnone.ll
opt-18 -passes=mem2reg -S mul_add.nooptnone.ll -o -
```

**排查清单**：如果你对 `-O0` 生成的 IR 跑 `opt` 却毫无变化，按顺序检查：

1. 函数附近有没有 `optnone`？（`grep optnone file.ll`）
2. 整个模块是不是用 `-O0` 编译的？
3. 如果是自己生成的 IR，生成器有没有加上不必要的属性？

## B.3 见证 `phi` 的诞生

正文第 5 章讲过 `phi` 是什么。这里回答一个后续问题：**`-O0` 的循环里明明没有 `phi`，它们是什么时候冒出来的？**

```c
int sum_to(int n) {
    int s = 0;
    for (int i = 1; i <= n; i++)
        s += i;
    return s;
}
```

把 `-O0` 的 IR 去掉 `optnone` 后跑 `mem2reg`：

```bash
sed 's/ optnone//' sum_to.O0.ll > sum_to.nooptnone.ll
opt-18 -passes=mem2reg -S sum_to.nooptnone.ll -o -
```

```llvm
define dso_local i32 @sum_to(i32 noundef %0) #0 {
  br label %2

2:                                                ; preds = %6, %1
  %.01 = phi i32 [ 0, %1 ], [ %5, %6 ]
  %.0 = phi i32 [ 1, %1 ], [ %7, %6 ]
  %3 = icmp sle i32 %.0, %0
  br i1 %3, label %4, label %8

4:                                                ; preds = %2
  %5 = add nsw i32 %.01, %.0
  br label %6

6:                                                ; preds = %4
  %7 = add nsw i32 %.0, 1
  br label %2

8:                                                ; preds = %2
  ret i32 %.01
}
```

**两个 `phi` 出现了。**

```llvm
2:                                                ; preds = %6, %1
  %.01 = phi i32 [ 0, %1 ], [ %5, %6 ]
  %.0 = phi i32 [ 1, %1 ], [ %7, %6 ]
```

逐字解读第一条：`s`（累加器）在块 `%2` 的值是 ——

- 从 `%1`（入口）来：`0`（初始值）；
- 从 `%6`（自增块）来：`%5`（这一轮新算出的和）。

第二条同理：`i` 从入口来是 `1`，从 `%6` 来是 `%7`（`i + 1`）。

**这就是 `phi` 存在的全部理由。** 一个在循环中被反复修改的变量，在 SSA 里必须被「重命名」成多条路径上的多个值，而汇合点需要一个机制决定取哪个 —— `phi` 就是这个机制。

而且整个过程是**自动的**：你不需要手写支配树分析，只要变量「地址没被取过」且读写模式可分析，`mem2reg` 就替你做。

**这也解释了本书第三部分编译器的两难**：手工发射 `phi` 在循环上很困难，因为循环的**回边是未来才出现的**（详见 [附录 C.2](23-附录C-编译器实现笔记.md#c2-为什么-if-能手工发射-phiwhile-不能)）。把变量放内存，就完全绕开了这个问题。

## B.4 `nsw` 与 `nuw`：给了优化器什么权力

正文第 3 章讲过 `nsw` 是「有符号溢出即 poison」的承诺。这里看看它**具体值多少**。

### 例子一：把条件判断整个消掉

```c
int f(int x) {
    if (x + 1 > x) return 1;
    return 0;
}
```

数学上 `x + 1 > x` 恒成立，但 `x = INT_MAX` 时 `x + 1` 在 C 里是 UB。既然程序员保证不会发生，编译器就可以认为它永不发生：

```bash
clang-18 -S -emit-llvm -O2 f.c -o -
```

```llvm
define dso_local noundef i32 @f(i32 noundef %0) local_unnamed_addr #0 {
  ret i32 1
}
```

**整个函数折叠成 `ret i32 1`。** 这个优化之所以合法，正是因为 `add nsw` 告诉优化器「溢出时结果是 poison，我不在乎」。

### 用 `-fwrapv` 关掉这个假设

`-fwrapv` 告诉 clang「有符号溢出要回绕，不是 UB」：

```bash
clang-18 -S -emit-llvm -O2 -fwrapv f.c -o -
```

```llvm
define dso_local noundef i32 @f(i32 noundef %0) local_unnamed_addr #0 {
  %2 = icmp ne i32 %0, 2147483647
  %3 = zext i1 %2 to i32
  ret i32 %3
}
```

函数不再恒返回 1，而是变成「`x != INT_MAX` 则返回 1，否则返回 0」—— 回绕语义下的正确答案。

**同一份 C 源码，一个编译选项，两种截然不同的 IR 和语义。**

### 例子二：强度削弱

```c
int p2(int a) { return a * 2; }
int p3(int a) { return a * 3; }
int p4(int a) { return a * 4; }
```

`-O2`：

```llvm
%2 = shl nsw i32 %0, 1        ; p2：乘法换成左移
%2 = mul nsw i32 %0, 3        ; p3：不是 2 的幂，保持乘法
%2 = shl nsw i32 %0, 2        ; p4
```

**注意 `shl` 里也带着 `nsw`。** 左移一位确实可能溢出，而溢出语义必须和原来的 `mul` 保持一致，否则优化就改变了语义。这个 `nsw` 是从 `mul nsw` 继承下来的 —— **它必须被诚实传递**。

### 例子三：无符号除法变成移位，有符号的不行

```c
int div4(int a) { return a / 4; }
unsigned div4u(unsigned a) { return a / 4; }
```

`-O2` 实测：

```llvm
define dso_local noundef i32 @div4(i32 noundef %0) local_unnamed_addr #0 {
  %2 = sdiv i32 %0, 4          ; 有符号：保持除法
  ret i32 %2
}

define dso_local noundef i32 @div4u(i32 noundef %0) local_unnamed_addr #0 {
  %2 = lshr i32 %0, 2          ; 无符号：变成逻辑右移
  ret i32 %2
}
```

**为什么有符号的不能换？** 因为**有符号除法向零取整，而算术右移向下取整**，两者对负数的结果不同：

```
-7 / 4  = -1     （向零取整）
-7 >> 2 = -2     （向下取整，补符号位）
```

既然结果不同，优化器就不能把 `sdiv` 换成 `ashr`。而无符号除法**就是**向下取整，和 `lshr` 完全一致，所以可以放心替换。

这解释了为什么 `nsw`/`nuw`/`exact` 这些标志如此有价值：**它们让优化器知道「什么时候可以换」。** 例如，如果我们能证明 `%0` 非负（有 `nneg` 或范围元数据），有符号的 `sdiv` 也能变成移位。

## B.5 看清优化管线

### `-O0` 到 `-O3` 各是什么

用 `--print-pipeline-passes` 可以把某个优化级别的完整 pass 列表打出来：

```bash
opt-18 -passes='default<O2>' --print-pipeline-passes /dev/null
```

（`default<O0>` 会在 **stderr** 上多打一行 `Could not parse dumped pass pipeline: unknown module pass 'BitcodeWriterPass'`，因为那条管线末尾的 `BitcodeWriterPass` 无法被重新解析。这是无害的提示，管线本身照常打印在 stdout。要消掉它就把 stderr 重定向掉，如 `2>/dev/null`。）

输出很长，但对比开头就很有信息量。

**`default<O0>`：**

```
always-inline,coro-cond(coro-early,cgscc(coro-split),coro-cleanup,globaldce),function(annotation-remarks),verify,BitcodeWriterPass
```

**`default<O1>` / `default<O2>` / `default<O3>`：**

```
annotation2metadata,forceattrs,inferattrs,coro-early,function<eager-inv>(
  lower-expect,simplifycfg<...>,sroa<modify-cfg>,early-cse<>),openmp-opt,
  ipsccp,called-value-propagation,globalopt,function<eager-inv>(
  mem2reg,instcombine<...>,simplifycfg<...>),always-inline,...
```

**关键对比**：`default<O0>` 里**没有 `mem2reg`**，`default<O1>` 里有。

这也澄清了一个常见误解：**`-O0` 输出里的 `alloca` 不是「优化器留下的」，而是 clang 前端主动生成的。** `-O0` 的优化管线几乎是空的 —— 它只做必须做的事（协程清理、验证）。

### `-O1` / `-O2` / `-O3` 的差别

三个级别的前半部分几乎一样，差别主要在后半部分：

| 级别 | 典型增量 |
|---|---|
| `-O1` | `mem2reg`、`instcombine`、`simplifycfg`、部分内联 |
| `-O2` | 循环优化（`licm`、`loop-rotate`、`indvars`）、向量化尝试、更激进的内联 |
| `-O3` | `loop-unroll<O3>`、更多向量化、更高的内联阈值 |

实测 `-O3` 相对 `-O1` 多出的 pass（节选）：

```bash
opt-18 -passes='default<O1>' --print-pipeline-passes /dev/null | tr ',' '\n' | sort -u > o1.txt
opt-18 -passes='default<O3>' --print-pipeline-passes /dev/null | tr ',' '\n' | sort -u > o3.txt
comm -13 o1.txt o3.txt
```

```
aggressive-instcombine
argpromotion
constraint-elimination
correlated-propagation
dse
early-cse<>
gvn<>
jump-threading
loop-unroll<O3>
loop-vectorize<no-interleave-forced-only;no-vectorize-forced-only;>
```

**`loop-unroll<O3>` 和 `loop-vectorize` 是 `-O3` 的核心增量**：更激进的循环展开和自动向量化。这也解释了为什么 `-O3` 有时反而更慢 —— 它为吞吐量牺牲了代码体积和指令缓存命中率。

### 管线字符串的语法

```bash
opt-18 -passes=mem2reg -S in.ll -o -                  # 单个 pass
opt-18 -passes='instcombine,simplifycfg' -S in.ll -o -  # 逗号分隔的序列
opt-18 -passes='function(mem2reg)' -S in.ll -o -       # 指定作用域
opt-18 -passes='default<O2>' -S in.ll -o -             # 预定义管线
```

| 作用域 | 含义 |
|---|---|
| `module(...)` | 模块级（能看到整个模块） |
| `cgscc(...)` | 调用图 SCC 级（内联等） |
| `function(...)` | 函数级（`mem2reg` 是这一级） |
| `loop(...)` | 循环级 |
| `loop-mssa(...)` | 需要 MemorySSA 的循环 pass |

## B.6 逐 pass 观察：一个完整实验

拿 `sum_to` 做实验，逐步看它如何变形。

### 第 0 步：原始 `-O0`（含内存操作）

见 [B.1](#b1-alloca-为什么会消失mem2reg) 的例子。此时是 `alloca` + `load`/`store`，**零个 `phi`**。

### 第 1 步：`mem2reg`

见 [B.3](#b3-见证-phi-的诞生)。所有内存操作消失，**出现两个 `phi`**。

### 第 2 步：再加 `instcombine`

```bash
opt-18 -passes='mem2reg,instcombine' -S sum_to.nooptnone.ll -o -
```

`instcombine` 做局部代数化简。对这个例子改动不大，但对别的代码效果显著。

### 第 3 步：完整 `-O2`

```bash
opt-18 -passes='default<O2>' -S sum_to.nooptnone.ll -o -
```

```llvm
define dso_local i32 @sum_to(i32 noundef %0) local_unnamed_addr #0 {
  %.not7 = icmp slt i32 %0, 1
  br i1 %.not7, label %._crit_edge, label %.lr.ph.preheader

.lr.ph.preheader:                                 ; preds = %1
  %2 = shl nuw i32 %0, 1
  %3 = add nsw i32 %0, -1
  %4 = zext nneg i32 %3 to i33
  %5 = add nsw i32 %0, -2
  %6 = zext i32 %5 to i33
  %7 = mul i33 %4, %6
  %8 = lshr i33 %7, 1
  %9 = trunc i33 %8 to i32
  %10 = add i32 %2, %9
  %11 = add i32 %10, -1
  br label %._crit_edge

._crit_edge:                                      ; preds = %.lr.ph.preheader, %1
  %.06.lcssa = phi i32 [ 0, %1 ], [ %11, %.lr.ph.preheader ]
  ret i32 %.06.lcssa
}
```

注意那些块名：`%.lr.ph.preheader`、`%._crit_edge`、`%.06.lcssa`。**`lr.ph` 是 "loop rotate, preheader" 的缩写，`_crit_edge` 是 "critical edge"，`lcssa` 是 "loop-closed SSA form"。** 优化器给块起的名字泄露了它做了哪些变换 —— 看到这类名字，你就知道这个循环被 `loop-rotate` 处理过。

**循环没了！** 整个求和被替换成了闭式公式 `n*(n+1)/2`。

**注意那些 `i33`。** 为什么是 33 位而不是 32 位？因为要在一次 `mul` 里同时装下 32 位操作数相乘的结果而不溢出。**C 里你无法声明一个 33 位整数，但 IR 可以。** 这是 IR 比 C 更灵活的直接体现 —— 优化器能造出恰好够宽的中间类型。

这个实验的教学价值在于：你能亲眼看到「代码 → 内存操作 → SSA → 数学公式」的完整演化链，而且每一步都可以单独验证。

## B.7 一个必须澄清的误区

**「`clang -O2` 的输出」≠「对 `clang -O0` 的输出跑 `opt -O2`」。**

实测：

```bash
clang-18 -S -emit-llvm -O0 abs_v.c -o abs_v.O0.ll
opt-18 -passes='default<O2>' -S abs_v.O0.ll -o -
```

**完全没有优化。** 因为 `optnone` 还在（见 [B.2](#b2-为什么跑-opt-没反应optnone)），整条 `default<O2>` 管线对这个函数视而不见。

去掉 `optnone` 再试：

```bash
sed 's/ optnone//' abs_v.O0.ll > abs_v.nooptnone.ll
opt-18 -passes='default<O2>' -S abs_v.nooptnone.ll -o -
```

```llvm
define dso_local i32 @abs_v(i32 noundef %0) local_unnamed_addr #0 {
  %.0 = tail call i32 @llvm.abs.i32(i32 %0, i1 true)
  ret i32 %.0
}
```

这次成功了，结果和 `clang -O2` 直接生成的一致（都变成 `llvm.abs` 内建）。

### 这个误区的三个层次

1. **`optnone` 会静默地让整条管线失效** —— 不报错，不警告，什么都不做。
2. **`clang -O2` 不只是「前端 + opt 管线」。** clang 在前端就会做一些优化（常量折叠、模式匹配），这些不在 `opt` 管线里。
3. **顺序有关系。** 有些优化在 `-O0` 风格的 IR 上效果不好（比如内联决策），因为它们依赖前面 pass 的清理结果。

**所以：想研究优化，请从 `-O0` IR 出发、手动去掉 `optnone`、然后逐步加 pass。** 这是最可控的工作流。

## B.8 调试优化过程中的 IR

想知道「到底是哪个 pass 改变了我的代码」：

```bash
opt-18 -passes='default<O2>' -print-after-all -S in.ll -o /dev/null 2> trace.txt
```

`trace.txt` 包含**每个 pass 执行后的完整 IR**：

```
*** IR Dump After PromotePass on sum_to ***
define ...
*** IR Dump After InstCombinePass on sum_to ***
define ...
```

注意 LLVM 18 的格式**带 pass 的类名**（`mem2reg` 的类名是 `PromotePass`）。

相关选项：

| 选项 | 作用 |
|---|---|
| `-print-after-all` | 每个 pass 之后打印 |
| `-print-before-all` | 每个 pass 之前打印 |
| `-print-changed` | **只在 IR 真的变化时**打印（输出量小得多） |
| `-print-module-scope` | 总是打印整个模块，而不是当前函数 |
| `-verify-each` | 每个 pass 之后都运行验证器 |

**`-print-changed` 特别有用**，因为 `-print-after-all` 在 `-O2` 下会产生几 MB 的输出，而大部分 pass 什么都没改。

其他常用工具：

| 工具 | 用途 |
|---|---|
| `llvm-as-18` | `.ll` → `.bc`，**并验证** |
| `llvm-dis-18` | `.bc` → `.ll` |
| `opt-18` | 跑优化管线 |
| `llc-18` | `.ll`/`.bc` → 目标汇编或目标文件 |
| `lli-18` | 直接解释执行 `.bc` |
| `llvm-link-18` | 链接多个模块 |
| `llvm-nm-18` | 查看符号表 |
| `opt-18 -passes=verify` | 单纯验证 IR |

一个完整的流程：

```bash
clang-18 -S -emit-llvm -O2 prog.c -o prog.ll   # C → IR
llc-18 prog.ll -o prog.s                       # IR → 汇编
llc-18 -filetype=obj prog.ll -o prog.o         # IR → 目标文件
lli-18 prog.ll                                 # 直接执行（需要 main）
```

**一个实用技巧**：想知道「某个 IR 构造会变成什么汇编」，写一小段 IR 直接让 `llc` 编译：

```bash
$ cat > t.ll <<'EOF'
define i32 @f(i32 %a, i32 %b) {
  %r = mul i32 %a, %b
  ret i32 %r
}
EOF
$ llc-18 -O2 t.ll -o - | grep -v "^\s*\."
f:                                      # @f
	movl	%edi, %eax
	imull	%esi, %eax
	retq
```

x86-64 的 System V 约定把第一个参数放在 `%edi`，第二个放在 `%esi`。`imull %esi, %eax` 是两操作数指令（`%eax = %eax * %esi`），结果必须写回其中一个操作数 —— 这就是为什么后端要先把 `a` 挪到 `%eax`。它也解释了正文第 2 章 `mul_add` 在 `-O2` 下操作数顺序为什么会「反过来」：**指令选择阶段已经在考虑 `imul` 的编码约束了。**
