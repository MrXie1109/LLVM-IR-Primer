# 第 18 章 控制流与 `phi` 节点

## 18.1 回指：第 5 章那个「凭空出现」的 `phi`

第 5 章我们看 `pick` 函数：

```c
int pick(int c, int a, int b) { return c ? a : b; }
```

```llvm
  br i1 %8, label %9, label %11
9:
  %10 = load i32, ptr %5, align 4
  br label %13
11:
  %12 = load i32, ptr %6, align 4
  br label %13
13:                                               ; preds = %11, %9
  %14 = phi i32 [ %10, %9 ], [ %12, %11 ]
  ret i32 %14
```

当时给出的结论是：

> **`phi` 是 SSA 的必需品。** 当控制流汇合、同一个 C 变量在不同路径上有不同值时，汇合点需要 `phi` 来「选择」。

**本章我们要亲手生成这个 `phi`。** 而且你会看到：这件事比看起来难得多，一步走错，LLVM 验证器给出的报错会非常难懂。

那一节的标题是「**`phi` 在运行时『不执行』**」；本章的标题可以是「**`phi` 在编译期很难生成**」。

## 18.2 编译 `if`

```python
def op_if(self, fn, env, expr):
    """(if c t e) -- 条件表达式，产出一个值。"""
    if len(expr) != 4:
        raise IRError("if takes exactly a condition, a then and an else")
    _, cond_expr, then_expr, else_expr = expr
    cond = self.to_i1(fn, self.compile_expr(fn, env, cond_expr))

    then_block = fn.new_block("then")
    else_block = fn.new_block("else")
    merge_ref = fn.reserve_block("merge")

    fn.cond_branch(cond, then_block, else_block)

    fn.start(then_block)
    then_val = self.compile_expr(fn, env, then_expr)
    then_end = fn.current
    fn.branch_placeholder(merge_ref)

    fn.start(else_block)
    else_val = self.compile_expr(fn, env, else_expr)
    else_end = fn.current
    fn.branch_placeholder(merge_ref)

    fn.start(merge_ref)
    if then_val.name == else_val.name:
        return then_val
    return fn.emit_value(
        then_val.ty,
        f"phi {then_val.ty} [ {then_val.name}, %{then_end.label} ], "
        f"[ {else_val.name}, %{else_end.label} ]",
    )
```

这段代码不长，但里面有**三个关键的、来之不易的设计决定**。我们一个一个说。

### 决定一：条件必须规约成 `i1`

```python
cond = self.to_i1(fn, self.compile_expr(fn, env, cond_expr))
```

第 4 章讲过 `i1` 的「暴政」：`br i1` 只接受 `i1`。我们的语言里比较运算符（`<` 等）产出 `i1`，但算术产出 `i32`。所以 `(if x a b)`（`x` 是 `i32`）需要转换：

```python
def to_i1(self, fn, val):
    """把一个 i32 规约成 i1，因为 `br` 要求 i1。"""
    if val.ty == I1:
        return val
    return fn.emit_value(I1, f"icmp ne {val.ty} {val.name}, 0")
```

实测：

```lisp
(defn f (x) (if x 1 2))
```

```llvm
%t1 = icmp ne i32 %x, 0        ; ← to_i1 生成的
br i1 %t1, label %then1, label %else2
```

**这就是第 4 章那张「C 条件 → IR 转换」表在我们编译器里的落地。**

### 决定二：merge 块要「预留」，而不是「先创建」

```python
merge_ref = fn.reserve_block("merge")
```

对比天真的写法：

```python
then_block = fn.new_block("then")
else_block = fn.new_block("else")
merge_block = fn.new_block("merge")     # ← 立刻创建
```

两者看起来差不多，但**差别很大**。看一个嵌套 `if`：

```lisp
(defn classify (x)
  (if (< x 0) 0
      (if (= x 0) 1 2)))
```

**天真版本**生成的块顺序是：

```
entry0
then1
else2
merge3        ← 外层 merge 被提前创建了
then4         ← 但内层 if 的块在它后面
else5
merge6
```

而**内层 if 的 `merge6` 需要跳回外层的 `merge3`**。于是 IR 长这样：

```llvm
merge3:                          ; ← 出现在它的前驱之前
  %t4 = phi i32 [ 0, %then1 ], [ %t3, %merge6 ]
  ret i32 %t4
then4:
  br label %merge6
else5:
  br label %merge6
merge6:
  %t3 = phi i32 [ 1, %then4 ], [ 2, %else5 ]
  br label %merge3               ; ← 跳回前面
```

**这是合法的 LLVM IR**（块顺序不影响语义），但有两个问题：

1. **可读性差**：块的排列顺序和阅读顺序不一致，看到 `merge3` 里引用了还没出现的 `%merge6` 会很困惑；
2. **和 `phi` 的位置冲突**：`phi` 必须在一个块的**最开头**。天真版本在 `merge3` 里立刻发射了 `phi`，但如果后面还要给 `merge3` 加东西，就得小心翼翼地维护「phi 必须在前」这个不变量。

**`reserve_block` 解决这两个问题**：它现在只**占一个名字**，等真正要填充时才把块追加到列表末尾。于是块顺序变成：

```
entry0
then1
else2
then4          ← 内层 if 的块，因为它们是先被填充的
else5
merge6
merge3         ← 外层 merge 最后才填充，所以排在最后
```

实测（这正是我们的编译器生成的）：

```llvm
define i32 @l_classify(i32 %x) {
entry0:
  %t1 = icmp slt i32 %x, 0
  br i1 %t1, label %then1, label %else2
then1:
  br label %merge3
else2:
  %t2 = icmp eq i32 %x, 0
  br i1 %t2, label %then4, label %else5
then4:
  br label %merge6
else5:
  br label %merge6
merge6:
  %t3 = phi i32 [ 1, %then4 ], [ 2, %else5 ]
  br label %merge3
merge3:
  %t4 = phi i32 [ 0, %then1 ], [ %t3, %merge6 ]
  ret i32 %t4
}
```

**块按「填充顺序」排列，读起来和源码结构一致。** 而且 `merge3` 的 `phi` 正确引用了 `%merge6` 和 `%then1`。

### 决定三：`phi` 的操作数必须是「分支所在的块」

这一条最容易写错，也是本章的核心。先看正确版本：

```python
fn.start(then_block)
then_val = self.compile_expr(fn, env, then_expr)
then_end = fn.current                  # ← 关键！
fn.branch_placeholder(merge_ref)
```

**注意 `then_end = fn.current` —— 它不一定等于 `then_block`！**

为什么？因为 `then_expr` 本身可能包含控制流。看嵌套 `if` 的例子：

```
then_block = then1                      ← 我们 start 到这里
编译 then_expr = 0                      ← 没有控制流
then_end = then1                        ← 还是 then1
```

但如果是：

```lisp
(if c1
    (if c2 1 2)      ; ← then 分支自己有控制流
    3)
```

那么：

```
then_block = then1                      ← start 到 then1
编译 then_expr = (if c2 1 2)            ← 这会生成 then4、else5、merge6
                                        ← 编译完时 current 停在 merge6！
then_end = merge6                       ← 不是 then1！
```

**`then1` 里现在什么都没有，它 `br` 到 `then4`/`else5`。真正「准备跳到外层 merge」的块是 `merge6`。**

所以 `phi` 必须写：

```llvm
phi i32 [ %内层结果, %merge6 ], [ ... ]     ; ← 操作数是 merge6，不是 then1
```

### 最容易走错的一步：先发射跳转，还是先编译表达式

考虑下面这个**错误**的写法（顺序颠倒了）：

```python
fn.start(then_block)
fn.branch_placeholder(merge_ref)         # ← 先发射跳转
then_val = self.compile_expr(fn, env, then_expr)   # ← 再编译表达式
```

这看起来「更整齐」（先结束块，再编译内容），但它**是错的**。因为 `compile_expr` 会：
1. 把 `current` 移到一个新的块（嵌套 `if` 的 `merge6`）；
2. 在那里的 `phi` 之后留下 `current`。

于是 `branch_placeholder` 施加到了 `then1` 上，而 `then_val` 却在 `merge6` 里算出来 —— `merge6` 永远跳不到外层的 `merge3`。LLVM 给出了这个报错：

```
llvm-as-18: assembly parsed, but does not verify as correct!
PHI node entries do not match predecessors!
  %t5 = phi i32 [ %t2, %then1 ], [ %t4, %else2 ]
label %else2
label %merge6
Instruction does not dominate all uses!
  %t4 = phi i32 [ 0, %then4 ], [ 1, %else5 ]
  %t5 = phi i32 [ %t2, %then1 ], [ %t4, %else2 ]
```

### 逐句解读这个报错

**第一段：**

```
PHI node entries do not match predecessors!
  %t5 = phi i32 [ %t2, %then1 ], [ %t4, %else2 ]
label %else2
label %merge6
```

读法：

- `%t5` 这个 `phi` 声称它的前驱是 `%then1` 和 `%else2`；
- 验证器说：「不对，`%else2` 的真实前驱是 `%else2` 和 `%merge6`」；
- 也就是：**`%then1` 根本不会跳到 `%t5` 所在的块**（跳过去的是 `%merge6`）。

**第二段：**

```
Instruction does not dominate all uses!
  %t4 = phi i32 [ 0, %then4 ], [ 1, %else5 ]
  %t5 = phi i32 [ %t2, %then1 ], [ %t4, %else2 ]
```

读法：`%t4` 定义在 `%merge6` 块里，但 `%t5` 声称它从 `%else2` 能拿到 `%t4`。**从 `%else2` 出发的路径不经过 `%merge6`，所以 `%t4` 在那里根本没有被定义。** 这违反了「定义必须支配使用」（第 14 章）。

### 修复

修复就是**把 `branch` 移到编译表达式之后**，并且用 `fn.current` 而不是 `then_block` 作为 `phi` 的操作数：

```python
fn.start(then_block)
then_val = self.compile_expr(fn, env, then_expr)
then_end = fn.current                  # ← 编译完才知道落在哪个块
fn.branch_placeholder(merge_ref)       # ← 现在才发射跳转
```

```python
return fn.emit_value(
    then_val.ty,
    f"phi {then_val.ty} [ {then_val.name}, %{then_end.label} ], "
    f"[ {else_val.name}, %{else_end.label} ]",
)
```

修复后的输出（这一节开头那段）通过了验证。

### 这个陷阱的教训

> **「当前块」是一个会被子编译过程修改的隐式状态。**

编译一个表达式**不保证**回到原来的块。任何试图在编译子表达式前后「保持块不变」的假设都是错的。

**这个问题的通用形式**在很多编译器里都出现过。经典的解决方案有两种：

1. **显式传递并返回「当前块」**（我们的做法：用 `fn.current` 读回，而不是假设）；
2. **不共享可变状态**，让 `compile_expr` 返回 `(value, end_block)`。

我们用第 1 种，因为它更小。但**无论如何，你必须意识到「编译子表达式会移动插入点」这件事** —— 第 14 章把插入点列为第一原则，这就是原因。

## 18.3 编译 `while`

```python
def op_while(self, fn, env, expr):
    """(while c body...) -- 循环；产出 0。

    因为每个可变局部变量都住在栈槽里，循环完全不需要 phi：
    栈槽就是 phi。这正是 clang -O0 做的取舍，也是 -O0 输出
    里充满 load/store 的原因。
    """
    if len(expr) < 2:
        raise IRError("while needs a condition")
    _, cond_expr, *body = expr
    cond_block = fn.new_block("while.cond")
    body_block = fn.new_block("while.body")
    end_block = fn.new_block("while.end")

    fn.branch(cond_block)

    fn.start(cond_block)
    cond = self.to_i1(fn, self.compile_expr(fn, env, cond_expr))
    fn.cond_branch(cond, body_block, end_block)

    fn.start(body_block)
    for form in body:
        self.compile_expr(fn, env, form)
    fn.branch(cond_block)

    fn.seal_block(cond_block)
    fn.start(end_block)
    return Value(I32, "0")
```

**比 `op_if` 简单得多**，因为它**不需要 `phi`**！

为什么？因为条件里的变量（`i`、`s`）住在**栈槽**里。循环体 `store` 新值，下一次迭代的 `load` 自然读到新值。

实测：

```lisp
(defn sum_to (n)
  (let ((i 1) (s 0))
    (while (<= i n)
      (set s (+ s i))
      (set i (+ i 1)))
    s))
```

```llvm
define i32 @l_sum_to(i32 %n) {
entry0:
  %i.addr = alloca i32, align 4
  %s.addr = alloca i32, align 4
  store i32 1, ptr %i.addr, align 4
  store i32 0, ptr %s.addr, align 4
  br label %while.cond1
while.cond1:
  %t1 = load i32, ptr %i.addr, align 4
  %t2 = icmp sle i32 %t1, %n
  br i1 %t2, label %while.body2, label %while.end3
while.body2:
  %t3 = load i32, ptr %s.addr, align 4
  %t4 = load i32, ptr %i.addr, align 4
  %t5 = add i32 %t3, %t4
  store i32 %t5, ptr %s.addr, align 4
  %t6 = load i32, ptr %i.addr, align 4
  %t7 = add i32 %t6, 1
  store i32 %t7, ptr %i.addr, align 4
  br label %while.cond1
while.end3:
  %t8 = load i32, ptr %s.addr, align 4
  ret i32 %t8
}
```

**零个 `phi`。** 循环结构完整，但跨迭代的状态传递完全靠内存。

### 一个有意思的对比

看循环体里 `set i (+ i 1)` 生成的代码：

```llvm
  %t6 = load i32, ptr %i.addr, align 4
  %t7 = add i32 %t6, 1
  store i32 %t7, ptr %i.addr, align 4
```

读 → 算 → 写。而在纯 SSA 版本里（第 5 章 `mem2reg` 的输出）：

```llvm
  %7 = add nsw i32 %.0, 1     ; 直接用 phi 的值
```

**一条指令 vs 三条指令。** 这就是 `mem2reg` 的价值。第 20 章我们会完整地跑一遍这个过程。

### `seal_block` 是干什么的

```python
fn.seal_block(cond_block)
```

我们的 `ir.py` 实现了「密封块」（sealed block）算法的一个简化版本。它的用途是：**当一个块的前驱集合确定下来之后，通知 SSA 构造器可以完成 `phi` 了。**

在我们的编译器里，由于**所有可变变量都在内存里**，`seal_block` 实际上几乎不做任何事 —— 因为 `_read_variable` 只会被调用在 SSA 值（参数）上，而参数不会有多个版本。

**那为什么保留它？** 因为 `ir.py` 是一个**通用的** IR 构建器（第 15 章说过，它不知道 Lisp 的存在）。如果将来有人要用它做纯 SSA 的代码生成，`seal_block` 就是必需的。这是**为未来留的接口**。

**诚实地说明**：在我们当前的编译器里，`ir.py` 里那套 `phi`/`seal_block`/`_read_variable` 机制**基本没有被用到**（`op_if` 是手工发射 `phi` 的）。这是一个真实的工程现象：**框架提供了比当前需求更多的能力**。我在第 20 章会说明哪些部分是「活代码」、哪些是「备用机制」。

## 18.5 嵌套循环

```lisp
(defn mult_table (n)
  (let ((i 1) (total 0))
    (while (<= i n)
      (let ((j 1))
        (while (<= j n)
          (set total (+ total (* i j)))
          (set j (+ j 1))))
      (set i (+ i 1)))
    total))
```

```c
printf("%d\n", mult_table(4));
```

实际输出：

```
100
```

（1×1+1×2+1×3+1×4 + 2×1+...+4×4 = 100。）

嵌套 `while` 生成的 IR 有 **7 个基本块**：外层循环的 `entry0` / `while.cond1` / `while.body2` / `while.end3`，内层循环的 `while.cond4` / `while.body5` / `while.end6`。

**但 `phi` 是 0 个** —— 因为内层和外层的循环变量（`i`、`total`、`j`）全都在内存里，跨迭代的状态通过 `load`/`store` 传递，不需要 `phi`。这正是 [附录 C.2](23-附录C-编译器实现笔记.md#c2-为什么-if-能手工发射-phiwhile-不能) 讲的取舍：**一旦变量住在栈槽里，循环就不需要 `phi`。**

## 18.6 一个反例：什么时候我们**必须**用 `phi`

我们的语言里，**只有 `if` 需要 `phi`，因为只有 `if` 是「产出值的分支」**。

对比：

| 构造 | 有值吗 | 需要 `phi` 吗 |
|---|---|---|
| `if` | 有（两个分支的值二选一） | **需要** |
| `while` | 无（我们定义为返回 0） | 不需要 |
| `let` | 有（最后一个 body 表达式的值） | 不需要（没有分支） |
| `set` | 有（赋的值） | 不需要（不产生分支） |

**如果 `while` 要返回值**（比如「循环结束时的累加器」），那么循环的出口就需要 `phi`：

```llvm
while.end:
  %result = phi i32 [ %s, %while.cond ]    ; 循环结束时 s 的值
  ret i32 %result
```

第 15 章的练习 15.4 让你思考过这个问题。**我们把它定义为返回 0，正是为了避开这个复杂度** —— 这是又一个「减法」的例子。

## 18.8 小结

- `if` 需要 `phi`，因为它**产出值**且**有分支**。
- 条件必须用 `to_i1` 规约成 `i1`（第 4 章的「`i1` 暴政」）。
- **merge 块应该「预留」而不是「先创建」** —— 这样块顺序和源码结构一致，且 `phi` 的位置好维护。
- **`phi` 的操作数必须是「分支实际所在的块」**，而那不一定是你 `start` 的那个块 —— 因为编译子表达式会移动插入点。
- 编译表达式的**副作用是移动插入点**。这是第 14 章「插入点」原则最尖锐的体现。
- `while` **不需要 `phi`**，因为变量在内存里。
- 我们只在 `if` 里手工发射 `phi`；`ir.py` 里那套通用的 SSA 构造机制是为将来的纯 SSA 前端准备的备用设施。
