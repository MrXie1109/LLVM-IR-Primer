# 第 17 章 代码生成：表达式、变量与调用

## 17.1 回指：第 2 章「为什么变量住在内存里」

第 2 章我们第一次看到 `-O0` 的 `mul_add`，当时有个疑难：

```llvm
%4 = alloca i32, align 4
%5 = alloca i32, align 4
%6 = alloca i32, align 4
store i32 %0, ptr %4, align 4
...
```

**为什么参数要复制到栈上？** 当时的答案是「服务调试器」，第 14 章又补上了第二个理由「**用内存换掉支配分析**」。

本章我们**亲手做同样的选择**，而且你会看到它带来的好处有多大：我们的整个变量处理逻辑只有几十行，却能正确处理 `let`、`set`、循环、嵌套作用域 —— **因为我们把 SSA 构造这个难题外包给了 `mem2reg`**。

同时，本章会讲一个我真实踩过的坑：**LLVM 的编号规则**。第 8 章预告过它，这里给出完整复盘。

## 17.2 编译器的整体结构

```python
class Compiler:
    def __init__(self):
        self.module = Module()
        self.sigs = {}        # 函数名 -> FunctionSig
        self.globals = {}     # 全局变量名 -> (IR 名字, 类型)

    def compile_program(self, text):
        forms = read_all(text)
        # 第一遍：收集所有签名和全局变量
        for form in forms:
            self.collect(form)
        # 第二遍：生成函数体
        for form in forms:
            self.emit_top(form)
        return self.module
```

**两遍扫描是必需的**，因为**前向引用**和**递归**：

```lisp
(defn outer (x) (inner (+ x 1)))     ; outer 引用了还没定义的 inner
(defn inner (y) (* y 10))
```

如果只有一遍，编译 `outer` 时 `inner` 还不存在，`compile_call` 就找不到它的签名。

同样的理由也适用于递归：

```lisp
(defn fact (n) (if (<= n 1) 1 (* n (fact (- n 1)))))
```

`fact` 在自己的函数体里引用自己 —— 如果不等签名收集完就编译函数体，`fact` 对自己也是未定义的。

**这个模式和 C 的「先声明后使用」是同一个问题**，只是 Lisp 没有声明语法，所以我们用两遍扫描代替。

## 17.3 值的表示

```python
class Value:
    """一个 SSA 值：命名局部变量、常量，或全局量。"""
    __slots__ = ("ty", "name")

    def __init__(self, ty, name):
        self.ty = ty          # "i32" / "i1"
        self.name = name      # "%t1" / "42" / "@g"

    def __repr__(self):
        return f"Value({self.ty}, {self.name})"
```

**关键洞察：`name` 只是一个字符串**，可以是：

- `%t1`（SSA 临时值）；
- `%n`（参数）；
- `42`（常量！注意没有 `%` 前缀）；
- `@g_counter`（全局变量）。

**常量也表示为 `Value`**，这让代码生成变得非常统一：

```python
def compile_expr(self, fn, env, expr):
    if isinstance(expr, int):
        return Value(I32, str(expr))          # 整数常量就是它自己
```

于是 `(+ x 1)` 生成 `add i32 %x, 1` —— 第二个操作数直接是 `1`，**不需要先"加载"一个常量**。这正是第 3 章讲的「常量可以直接作为操作数」。

## 17.4 变量的两种表示

这是本章最重要的设计决策。

```python
class Var:
    """一个 Lisp 变量，要么是 SSA 值，要么是栈槽。"""

    __slots__ = ("ir_name", "ty", "slot", "mutable")

    def __init__(self, ir_name, ty, slot, mutable=False):
        self.ir_name = ir_name
        self.ty = ty
        self.slot = slot
        self.mutable = mutable
```

两种形态：

| | `slot=False`（SSA 值） | `slot=True`（栈槽） |
|---|---|---|
| 存储 | 一个 SSA 名字 | 一个 `alloca` 出来的地址 |
| 读取 | 直接用那个名字 | 生成 `load` |
| 写入 | **不允许** | 生成 `store` |
| 用在哪 | 函数参数 | `let` 绑定的局部变量 |

**为什么参数用 SSA 值？** 因为参数**在 `-O0` 下不一定要存到栈上**（虽然 clang 那么做了）。参数在函数入口处是确定的、不可变的，直接用它的 SSA 名字最简单：

```llvm
define i32 @l_mul_add(i32 %x, i32 %y, i32 %z) {
entry0:
  %t1 = mul i32 %x, %y            ; ← 直接使用 %x、%y
  %t2 = add i32 %t1, %z
  ret i32 %t2
}
```

**为什么 `let` 变量用栈槽？** 因为它们**可变**（我们的 `set` 可以修改它们），而可变的东西在 SSA 里很麻烦。这正是 17.6 节要讲的。

### 读取变量

```python
def read_var(self, fn, var):
    """把一个 Var 变成当前程序点的 SSA Value。"""
    if var.slot:
        # 读栈槽就是一次 load；类型由栈槽携带。
        return fn.emit_value(
            var.ty, f"load {var.ty}, ptr {var.ir_name}, align 4"
        )
    return Value(var.ty, var.ir_name)
```

只有 7 行，但它统一了两种情况：无论变量住在哪里，调用者都得到一个 `Value`。

### 求值符号

```python
if isinstance(expr, Sym):
    var = env.lookup(expr.name)
    if var is not None:
        return self.read_var(fn, var)
    if expr.name in self.globals:
        ir_name, ty = self.globals[expr.name]
        return fn.emit_value(ty, f"load {ty}, ptr {ir_name}, align 4")
    raise IRError(f"unbound variable {expr.name!r}")
```

查找顺序是：**局部变量 → 全局变量 → 报错**。局部变量遮蔽全局变量，这与大多数语言一致。

### 作用域

```python
class Frame:
    """一个词法作用域：把 Lisp 名字映射到 Var 对象。"""

    def __init__(self, parent=None):
        self.parent = parent
        self.vars = {}

    def lookup(self, name):
        frame = self
        while frame is not None:
            if name in frame.vars:
                return frame.vars[name]
            frame = frame.parent
        return None

    def define(self, name, var):
        self.vars[name] = var
```

一个链式作用域，`lookup` 沿着父链向上找。这对应 Lisp 的词法作用域规则。

## 17.5 编译 `let`

```python
def op_let(self, fn, env, expr):
    """(let ((v e) ...) body...) -- 引入局部变量。

    每个绑定都存进栈槽而不是 SSA 寄存器，因为在这个方言里
    `let` 绑定是可变的（见 `set`）。第 20 章会展示 `mem2reg`
    如何把它们变回寄存器。
    """
    if len(expr) < 3:
        raise IRError("let needs a binding list and a body")
    _, bindings, *body = expr
    if not isinstance(bindings, list):
        raise IRError("let bindings must be a list of pairs")

    inner = Frame(env)
    for pair in bindings:
        if not isinstance(pair, list) or len(pair) != 2:
            raise IRError(f"bad let binding {unparse(pair)}")
        name = pair[0]
        if not isinstance(name, Sym):
            raise IRError("let binding name must be a symbol")
        val = self.compile_expr(fn, inner, pair[1])
        slot = fn.alloca_slot(I32, hint=f"{name.name}")
        fn.emit(f"store i32 {val.name}, ptr {slot.name}, align 4")
        inner.define(name.name, Var(slot.name, I32, slot=True, mutable=True))

    result = Value(I32, "0")
    for form in body:
        result = self.compile_expr(fn, inner, form)
    return result
```

三个要点：

1. **新建一个 `Frame(env)`** —— 这就是词法作用域的实现。绑定结束（`let` 的 body 执行完）后，这个 frame 被丢弃，名字自然「离开作用域」。
2. **顺序绑定**：`inner` 在循环中逐步填充，所以后面的绑定能看到前面的（第 15 章承诺过）。
3. **每个绑定一个 `alloca` + 一个 `store`**。初始值算出来后立刻存进槽位。

实测 `(let ((a 1) (b (+ a 1))) (+ a b))`：

```llvm
%a.addr = alloca i32, align 4
%b.addr = alloca i32, align 4
store i32 1, ptr %a.addr, align 4
%t1 = load i32, ptr %a.addr, align 4
%t2 = add i32 %t1, 1
store i32 %t2, ptr %b.addr, align 4
%t3 = load i32, ptr %a.addr, align 4
%t4 = load i32, ptr %b.addr, align 4
%t5 = add i32 %t3, %t4
ret i32 %t5
```

`b` 的初始值确实是 `load %a.addr` 之后再 `+1` —— **顺序绑定生效了**。

### `alloca_slot` 的细节

```python
def alloca_slot(self, ty, hint="slot"):
    """在入口块里预留一个栈槽，返回它的指针。"""
    name = f"%{hint}.addr"
    n = 1
    while any(name in a for a in self.entry_allocas):
        name = f"%{hint}.addr{n}"
        n += 1
    self.entry_allocas.append(f"  {name} = alloca {ty}, align {self._align(ty)}")
    return Value("ptr", name)
```

两个设计点：

**第一，`alloca` 存在 `entry_allocas` 里，最后统一插到入口块开头。** 第 6 章讲过 clang 也这么做。为什么？

因为**如果 `alloca` 出现在循环体里，每次迭代都会分配一块新的栈空间**，栈会无限增长。把 `alloca` 全部提到入口块，就保证了「一次分配，整个函数生命周期有效」。这正是 `alloca` 的语义 —— 它的生命周期是函数级的。

**第二，名字冲突处理。** 如果同一个 `let` 里有 `(a 1)` 和 `(a 2)`（遮蔽），或者两个不同的 `let` 都有 `a`，它们的槽位名会撞车。这个 `while` 循环通过加数字后缀解决。

实测一个遮蔽的例子：

```lisp
(defn f (x)
  (let ((a 1))
    (let ((a 2))
      a)))
```

```llvm
%a.addr = alloca i32, align 4
%a.addr1 = alloca i32, align 4       ; ← 后缀消除冲突
store i32 1, ptr %a.addr, align 4
store i32 2, ptr %a.addr1, align 4
%t1 = load i32, ptr %a.addr1, align 4   ; ← 内层遮蔽外层
ret i32 %t1
```

## 17.6 编译 `set`：为什么用内存换 SSA

```python
def op_set(self, fn, env, expr):
    """(set v e) -- 给已有的局部变量赋值。"""
    if len(expr) != 3:
        raise IRError("set takes a variable and a value")
    _, target, value_expr = expr
    if not isinstance(target, Sym):
        raise IRError("set target must be a symbol")
    var = env.lookup(target.name)
    if var is None:
        raise IRError(f"set of unbound variable {target.name!r}")
    if not var.slot:
        raise IRError(
            f"cannot assign to {target.name!r}: it is an SSA value, "
            "not a local slot"
        )
    val = self.compile_expr(fn, env, value_expr)
    fn.emit(f"store i32 {val.name}, ptr {var.ir_name}, align 4")
    return val
```

注意那条 `cannot assign to ... it is an SSA value` 检查：**函数参数不能被 `set`**。这不是缺陷，是一个有意的限制（和很多 Lisp 方言一样），而且它让错误信息清晰。

现在来看**核心问题**：如果不把变量放在内存里，`set` 该怎么编译？

考虑这个循环：

```lisp
(let ((i 1) (s 0))
  (while (<= i n)
    (set s (+ s i))
    (set i (+ i 1)))
  s)
```

如果 `i` 和 `s` 是 SSA 值，那么循环体里「修改」它们意味着**产生新的 SSA 名字**：

```llvm
; 假设的纯 SSA 版本（需要 phi）
while.cond:
  %i = phi i32 [ 1, %entry ], [ %i.next, %while.body ]
  %s = phi i32 [ 0, %entry ], [ %s.next, %while.body ]
  %c = icmp sle i32 %i, %n
  br i1 %c, label %while.body, label %while.end
while.body:
  %s.next = add i32 %s, %i
  %i.next = add i32 %i, 1
  br label %while.cond
```

**要生成这个，编译器必须：**

1. 知道 `while.cond` 的所有前驱（这样 `phi` 的操作数才对）；
2. 在循环头部插入 `phi`；
3. 在循环体的末尾把新值「回送」给 `phi`。

而第 1 条在**顺序生成**的编译器里很难做到 —— 你生成 `while.cond` 的时候，循环体的回边还没生成，你**不知道**循环体会不会真的回跳。

**这就是我们选择内存的原因。** 用 `alloca` 之后：

```llvm
while.cond1:
  %t1 = load i32, ptr %i.addr, align 4
  %t2 = icmp sle i32 %t1, %n
  br i1 %t2, label %while.body2, label %while.end3
while.body2:
  %t3 = load i32, ptr %s.addr, align 4
  %t4 = load i32, ptr %i.addr, align 4
  %t5 = add i32 %t3, %t4
  store i32 %t5, ptr %s.addr, align 4
  ...
  br label %while.cond1
```

**没有 `phi`，没有支配分析，没有前驱信息。** 每个 `load` 读到的都是「内存里当前的值」，这个值是**当前块里新定义**的，天然支配自己的使用。

**代价**是运行时的多余读写。**但 `mem2reg` 会把它们消掉**（第 5 章、第 20 章实测）。于是我们得到了一个漂亮的工程结果：

> **我们用「冗余的内存操作」换来了「生成器不需要做支配分析」，然后让 LLVM 的 `mem2reg` 免费地帮我们把冗余消掉。**

这就是第 2 章那个「臃肿的 `-O0` IR」存在的**全部理由**。clang 这么干，我们也这么干。

### 但我们的策略其实是混合的

上面这段话容易让人以为「我们的编译器什么都不用 `phi`」。**这是不对的。** 在往下读之前，必须把真实的策略说清楚，否则你会对生成的 IR 形成错误的心智模型。

我们的编译器对三类东西用了**三种不同的**表示：

| 东西 | 表示 | 为什么 |
|---|---|---|
| 函数参数 | **SSA 值**（`%x`） | 不可变，直接用 |
| `let` 绑定的局部变量 | **栈槽**（`alloca`） | 可被 `set` 修改 |
| **`if` 的返回值** | **手工发射的 `phi`** | 两个分支的前驱**已知**，可以手工写 |

实测这张表（我用同一个编译器跑五个不同形状的函数）：

```
alloca=0  phi=0   (defn f (x) x)                                          ; 只有参数
alloca=0  phi=1   (defn f (x) (if (< x 0) 1 2))                           ; 只有 if
alloca=1  phi=0   (defn f (x) (let ((y 1)) (+ x y)))                      ; 只有 let
alloca=1  phi=0   (defn f (n) (let ((i 0)) (while (< i n) (set i (+ i 1))) i))  ; 只有 while
alloca=1  phi=1   (defn f (x) (let ((y 1)) (if (< x 0) (set y 2) (set y 3)) y))  ; 两者都有
```

所以：

- `fib` 只有参数和 `if` → **零个 `alloca`，但有 `phi`**（第 19 章那个例子）；
- `sum_to` 有 `let` 和 `while` → **三个 `alloca`，零个 `phi`**（本章的例子）。

**这两种形状并存，都是对的。**

### 为什么 `if` 能手工发射 `phi`，而 `while` 不能

这是理解全部取舍的关键：

**`if` 的两个分支在编译时都已经结束**，所以：
- 我知道 then 分支最后落在哪个块（`then_end`，第 18 章）；
- 我知道 else 分支最后落在哪个块；
- 于是我可以**当场**写下 `phi i32 [ then值, %then_end ], [ else值, %else_end ]`。

**`while` 不行**，因为循环的回边是「未来」的事：
- 我在编译 `while.cond` 块时，循环体**还没生成**；
- 所以我不知道 `while.cond` 会有几个前驱 —— 现在只有入口块，但马上会多出一个来自循环体末尾的回边；
- 如果此时发射 `phi`，我会漏掉那个还没出现的前驱，**验证器会报「PHI node entries do not match predecessors」**（第 18 章那个 bug 的同类）。

**这正是「sealed block」问题**：一个块的 `phi` 只有在它所有前驱都确定之后才能完成。`if` 的 merge 块在编译完两个分支后前驱就确定了；`while` 的 cond 块要等循环体编译完。

### 所以我们做了两个不同的选择

| 情形 | 前驱是否已知 | 我们的做法 |
|---|---|---|
| `if` 的 merge | **编译时已知** | 手工发射 `phi` |
| `while` 的 cond | **编译时未知**（回边未来才出现） | 把变量放栈槽，**根本不需要 `phi`** |

**这个划分不是随意的，它精确地对应于「前驱是否已知」。** 第 18 章会详细讲这个判断，以及我在 `op_if` 里搞错它时验证器给出的报错。

> **顺便说清 `ir.py` 里的那套 SSA 机制。** `ir.py` 的文档字符串说它实现了 Braun 等人的 sealed-block 算法，「从不需要分配栈槽」。那套机制是**通用的、完整的**，但它在我们这条管线里**没有被使用**（第 19.5 节会用一个插桩实验证明）。原因是：真的把它用起来需要一套「延迟完成 `phi`」的簿记，而我们选择了更简单的路线 —— **需要 `phi` 的地方只有一个（`if`），手工写三行就够了**。
>
> 这是一个真实的工程现象：**框架提供了比当前需求更多的能力**。我在第 19.5 节会诚实列出哪些代码是活的、哪些是闲置的。

## 17.7 编译函数

```python
def compile_function(self, form):
    _, name, params, *body = form
    param_names = [p.name for p in params]
    sig = self.sigs[name.name]
    fn = Function(
        sig.name,
        sig.ret_ty,
        sig.param_types,
        [f"%{p}" for p in param_names],
    )

    entry = fn.new_block("entry")
    fn.start(entry)

    env = Frame()
    for lisp_name, ir_name in zip(param_names, fn.param_names):
        env.define(lisp_name, Var(ir_name, I32, slot=False))

    # 函数体是隐式的 (do ...)：求值每个表达式，返回最后一个。
    result = Value(I32, "0")
    for expr in body:
        result = self.compile_expr(fn, env, expr)
    fn.set_term(f"ret i32 {result.name}")
    fn.seal_block(entry)
    return fn
```

三个要点：

1. **参数绑定为 SSA 值**（`slot=False`），直接用 `%x`、`%y` 这样的名字。
2. **`entry` 有名字**（第 8 章讲过：命名块不占编号）。
3. **函数体是隐式的 `do`**：依次求值，返回最后一个表达式的值。

实测：

```lisp
(defn mul_add (x y z) (+ (* x y) z))
```

```llvm
define i32 @l_mul_add(i32 %x, i32 %y, i32 %z) {
entry0:
  %t1 = mul i32 %x, %y
  %t2 = add i32 %t1, %z
  ret i32 %t2
}
```

**只有 3 条指令，没有 `alloca`。** 对比第 2 章 clang `-O0` 的 12 条 —— 我们的编译器在这里生成了更接近 `-O2` 的代码，因为参数直接是 SSA 值，没有可变的局部变量。

（顺便注意块名是 `entry0` 而不是 `entry`。因为 `new_block("entry")` 会给标签加计数器后缀以避免冲突。这是 `ir.py` 的实现细节。）

## 17.8 编译调用

```python
def compile_call(self, fn, env, expr):
    head = expr[0].name
    sig = self.sigs[head]
    args = [self.compile_expr(fn, env, a) for a in expr[1:]]
    if len(args) != len(sig.param_types):
        raise IRError(
            f"{head} expects {len(sig.param_types)} arguments, "
            f"got {len(args)}"
        )
    arg_text = ", ".join(
        f"{ty} {a.name}" for ty, a in zip(sig.param_types, args)
    )
    return fn.emit_value(
        sig.ret_ty, f"call {sig.ret_ty} @{sig.name}({arg_text})"
    )
```

注意 **`@{sig.name}`**，而不是 `@{head}`。这是**符号修饰**（name mangling）：

```python
SYMBOL_PREFIX = "l_"

def mangle(name):
    return SYMBOL_PREFIX + name
```

### 为什么必须修饰符号

Lisp 允许你写：

```lisp
(defn double (x) (* x 2))
(defn abs (x) (if (< x 0) (- 0 x) x))
```

但 `double` 是 C 的关键字，`abs` 是 `<stdlib.h>` 里的函数！如果直接把 Lisp 名字用作 IR 符号名，**生成的模块就没法和 C 代码链接**：

```
error: cannot combine with previous 'int' declaration specifier
    int double(int);
        ^
```

一个直接声明 `int double(int);` 的 C 驱动会立刻编译失败：

加前缀 `l_` 之后：

```llvm
define i32 @l_double(i32 %x) { ... }
define i32 @l_abs(i32 %x) { ... }
```

**冲突消失。** 这是所有真实编译器都要做的事 —— C++ 的 Itanium ABI 修饰、Rust 的 legacy/`v0` mangling，本质都是同一个问题：**源语言的命名空间和目标文件的命名空间不一样，需要一个映射。**

（我们的 `l_` 前缀极度简单，不做类型编码，所以不支持重载。但对我们的语言来说够了。C++ 那种把 `void f(int)` 修饰成 `_Z1fi` 的方案，是为了支持重载和命名空间 —— 我们没有这些特性。）

## 17.9 那个真实的坑：编号值

现在讲第 8 章预告过的那个坑。它很容易踩到，而且踩到之后报错信息很难懂。

### 天真实现

```python
class Function:
    def __init__(self):
        self.temp_counter = 0

    def new_temp(self):
        self.temp_counter += 1
        return f"%{self.temp_counter}"        # ← 用编号值
```

生成器的想法是：「我自己数着，第一个临时值叫 `%1`，第二个叫 `%2`……」

**这会失败。** 因为第 8 章讲过，LLVM 的编号计数器是**参数、匿名基本块、有结果的指令**三者共享的。而生成器在生成过程中会插入大量基本块：

```python
then_block = fn.new_block("then")     # 生成器以为这只是个名字
```

`ir.py` 里我们的 `new_block` 用的是**命名标签**（`then1`、`else2`），所以不占编号。**但如果生成器用编号标签，或者用 `%{counter}` 做临时值，计数器就会和 LLVM 的真实计数器脱节。**

### 真实的报错

报错是这样的：

```llvm
; numfail.ll
define i32 @l_ack(i32 %m, i32 %n) {
entry:
  %1 = icmp eq i32 %m, 0
  br i1 %1, label %2, label %3
2:
  %6 = add i32 %n, 1
  ret i32 %6
3:
  %4 = sub i32 %m, 1        ; ← 编号从 %6 倒退到 %4
  ret i32 %4
}
```

```bash
$ llvm-as-18 numfail.ll -o /dev/null
llvm-as-18: numfail.ll:8:1: error: label expected to be numbered '7' or greater
3:
^
```

（源文件：`code/part2-ir/numfail.ll`。）

读法的含义：生成器以为「下面该轮到 `%4` 了」，但 LLVM 的计数器已经涨到 12 了。

### 为什么这个 bug 特别难查

因为它**不是每次都报错**。回到第 8 章的规则：

> **编号值必须单调递增，但允许跳号。**

所以生成器的计数器**偏小**时会报错（如上），但**偏大**时**不会报错**：

```llvm
define i32 @f(i32 %x) {
entry:
  %5 = add i32 %x, 1       ; 跳过了 %1..%4，LLVM 接受
  ret i32 %5
}
```

**这通过了验证。** 但问题是：编号和实际结构脱节了，你以后想在某处插入一条指令时，会发现「没有号码可用」—— 因为在它前后都已经有更大的编号了。

**更糟的情况**：如果你的生成器混用编号标签和命名标签，有些函数能过、有些不能，报错位置还指向你没写过的地方。

### 解决方案：全用命名值

我们在第 14 章就已经这么做了：

```python
def new_temp(self):
    """分配一个新的*命名*临时值。"""
    self.temp_counter += 1
    return f"%t{self.temp_counter}"
```

生成：

```llvm
define i32 @l_fib(i32 %n) {
entry0:
  %t1 = icmp slt i32 %n, 2
  br i1 %t1, label %then1, label %else2
```

**参数是命名值，临时值是命名值，块标签是命名值 —— 没有任何编号值，规则完全不适用。**

### 这个坑的教训

> **不要和你不完全理解的隐式规则打交道。**

我们可以花时间去精确模拟 LLVM 的编号规则（哪些指令占号、匿名块如何影响计数器），但那是一个**没有必要**的负担。命名值稍长几个字符，换来的是：

- 不可能因为计数器脱节而失败；
- 生成的 IR 可读性更好（`%t1` 比 `%7` 有意义吗？至少它明确标记了「这是我的临时值」）；
- 调试时能一眼看出哪个值是谁生成的。

**这不是「绕过」规则，而是在理解规则之后做出的工程选择。**

## 17.11 小结

- 编译分两遍：**先收集所有签名，再生成函数体** —— 这是为了前向引用和递归。
- 常量也表示为 `Value`（名字就是数字本身），所以操作数统一。
- 变量有两种表示：**参数用 SSA 值**（不可变），**`let` 变量用栈槽**（可变）。
- **`let` 变量放内存是为了支持 `set`** —— 纯 SSA 的 `set` 需要在前驱未知的循环头部插入 `phi`，这对顺序生成的编译器是不可行的。
- **`alloca` 统一提到入口块**，因为它的生命周期是函数级的；放在循环里会导致栈无限增长。
- **符号修饰 `l_` 是必需的**：Lisp 名字会撞上 C 的 `double`、`abs` 等。
- **不要用编号值生成 IR。** 编号计数器由「参数 + 匿名块 + 有结果的指令」共享，模拟它的成本远高于收益，而且跳号合法让错误难以发现。用 `%t1` 这样的命名值。
