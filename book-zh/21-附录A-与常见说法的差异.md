# 附录 A 与常见说法的差异

## A.0 这个附录是给谁的

正文里凡是「某个流传的说法其实不对」「某个语法细节容易写错」的内容，都集中到了这个附录。

**为什么不让它们留在正文？** 因为对第一次学 LLVM IR 的人来说，那些内容全是噪音 —— 你还没建立起正确的直觉，先去记「哪种写法是错的」只会分散注意力。正文只讲**对的、够用的**那一套。

**那什么时候读这个附录？** 三种情况：

1. 你照着某本教程或某个博客写 `.ll`，`llvm-as` 报了一个你看不懂的错；
2. 你发现自己的输出和本书（或别的资料）对不上，想知道谁对；
3. 你已经能顺畅地读写 IR 了，想看看有哪些细节坑。

下面每一条都给出**实测命令和真实输出**。环境是 **LLVM 18.1.3**。

> **一条通用建议**：本书正文和这个附录都可能过时（LLVM 每半年一个大版本）。**遇到分歧时，先运行命令，再看文档。** 这不是客套话 —— 本附录里的大部分条目，最初都是因为「书上说的」和「终端说的」不一致才被发现的。

## A.1 手写 `.ll` 时最容易写错的语法

这一节最重要。**如果你只读附录的一节，读这节。** 因为下面每一条都是「照着直觉写就会报错」的类型。

### A.1.1 整数常量没有裸十六进制，也没有二进制

**直觉写法（错）：**

```llvm
i32 0x2A          ; ← 被拒绝
i32 0b101010      ; ← 被拒绝
```

**实测：**

```bash
$ for lit in 42 -1 0x2A 0b101010 052 u0x2A s0x2A; do
    printf 'define i32 @f() {\n  %%a = add i32 %s, 1\n  ret i32 %%a\n}\n' "$lit" > t.ll
    printf "%-10s => " "$lit"
    llvm-as-18 t.ll -o /dev/null 2>/dev/null && echo ACCEPTED || llvm-as-18 t.ll -o /dev/null 2>&1 | head -1 | sed 's/.*error: //'
  done
42         => ACCEPTED
-1         => ACCEPTED
0x2A       => floating point constant invalid for type
0b101010   => expected ',' in arithmetic operation
052        => ACCEPTED
u0x2A      => ACCEPTED
s0x2A      => ACCEPTED
```

**正确写法：**

```llvm
i32 42            ; 十进制
i32 -1            ; 负数
i32 052           ; 八进制（前导 0，和 C 一样）
u0x2A             ; 十六进制必须带 u（无符号）或 s（有符号）前缀
s0x2A             ; 有符号十六进制
```

**为什么 `0x2A` 的报错提到「浮点」？** 因为在 LLVM 语法里，`0x...` 是**浮点数的十六进制位模式**（例如 `double 0x4014000000000000` 表示 1.0）。解析器看到 `0x2A` 就按浮点解析，然后发现类型是 `i32`，于是报 `floating point constant invalid for type`。

**这个报错极具误导性** —— 它让你以为是类型问题，实际上是你写了一个不属于整数语法的字面量。记住 `u0x`/`s0x`。

**LLVM IR 里没有二进制字面量。** 二进制常量请写成十进制或 `u0x` 十六进制。

### A.1.2 全局变量的可见性是前缀，不是逗号属性

**直觉写法（错）：**

```llvm
@v = global i32 1, visibility protected     ; ← 被拒绝
```

**实测：**

```bash
$ llvm-as-18 v.ll
llvm-as-18: v.ll:1:20: error: unknown global variable property!
@v = global i32 1, visibility protected
                   ^
```

**正确写法：**

```llvm
@v = protected global i32 1
@h = hidden global i32 2
```

**规则**：`hidden` / `protected` 写在 `global` / `constant` **之前**，和 `private`、`internal`、`external` 这些链接属性在同一位置。而 `, align 4`、`, section ".x"` 这类才是逗号后面的属性。

clang 的输出可以印证：

```c
__attribute__((visibility("hidden"))) int hg = 1;
__attribute__((visibility("protected"))) int pg = 2;
```

```llvm
@hg = hidden global i32 1, align 4
@pg = protected global i32 2, align 4
```

### A.1.3 `trunc` 不接受任何标志位

**直觉写法（错）：**

```llvm
%r = trunc nsw i32 %x to i8      ; ← 被拒绝
%r = trunc nuw i32 %x to i8      ; ← 被拒绝
%r = trunc exact i32 %x to i8    ; ← 被拒绝
```

**实测：**

```bash
$ llvm-as-18 tr.ll
llvm-as-18: tr.ll:2:14: error: expected type
  %r = trunc nsw i32 %x to i8
             ^
```

报错是 `expected type` —— 解析器在 `trunc` 之后**直接期待一个类型**，根本没打算接受标志位。

**支持 `nsw`/`nuw` 的只有 `add`、`sub`、`mul`、`shl`**（见正文第 11 章）。`zext` 另有一个 `nneg` 标志（表示源值非负）。

### A.1.4 `atomicrmw` 没有 `smax`/`smin`

**直觉写法（错）：**

```llvm
%r = atomicrmw smax ptr %p, i32 1 seq_cst    ; ← 被拒绝
```

**实测：**

```bash
$ for op in xchg add sub and nand or xor max min umax umin smax smin uinc_wrap udec_wrap; do ... done
xchg         => OK
add          => OK
sub          => OK
and          => OK
nand         => OK
or           => OK
xor          => OK
max          => OK
min          => OK
umax         => OK
umin         => OK
smax         => expected binary operation in atomicrmw
smin         => expected binary operation in atomicrmw
uinc_wrap    => OK
udec_wrap    => OK
```

**规则**：`max` / `min` **本身就是有符号版本**，无符号版本是 `umax` / `umin`。**不存在** `smax` / `smin`。

（注意这和 `icmp` 的命名规则不同 —— 那里确实是 `slt`/`ult`。`atomicrmw` 的历史遗留让它没有 `s` 前缀。）

### A.1.5 命名值和编号值**可以**混用

**常见说法（错）：** 「同一个函数里，命名值 `%name` 和编号值 `%0` 不能混用。」

**实测：**

```llvm
define i32 @h(i32 %x) {
entry:
  %0 = add i32 %x, 1     ; 编号值
  %s = add i32 %0, 1     ; 命名值
  ret i32 %s
}
```

```bash
$ llvm-as-18 mixed.ll -o /dev/null; echo $?
0
```

**合法。** 反过来的顺序也合法。

**真正的规则是**：有一个共享的计数器，编号值必须**单调递增**；跳号合法，**倒退非法**。

```llvm
define i32 @f(i32 %x) {
entry:
  %5 = add i32 %x, 1
  %2 = add i32 %5, 1     ; ← 倒退，报错
  ret i32 %2
}
```

```bash
$ llvm-as-18 back.ll -o /dev/null
llvm-as-18: back.ll:4:3: error: instruction expected to be numbered '%6' or greater
  %2 = add i32 %5, 1
  ^
```

计数器的初始值等于**参数个数**；**匿名基本块和有结果的指令都占号**，`store`/`br`/`ret` 不占号。详细展开见正文第 8 章。

### A.1.6 类型相等不是「结构相等」

**常见说法（错）：** 「LLVM 的类型相等是结构相等，命名类型只是别名。」

**实测：**

```llvm
%A = type { i32, i32 }
%B = type { i32, i32 }

define %A @f(%B %x) {
  ret %A %x
}
```

```bash
$ llvm-as-18 structeq.ll -o /dev/null
llvm-as-18: structeq.ll:4:10: error: '%x' defined with type '%B = type { i32, i32 }' but expected '%A = type { i32, i32 }'
  ret %A %x
         ^
```

**`%A` 和 `%B` 是两个不同的类型**，尽管字段完全一样。

**规则**：每个 `= type` 定义创建一个**独特的命名类型**，命名类型只和「同一个名字」相等。**字面量**类型（直接写 `{ i32, i32 }`）之间才按结构比较。命名类型和同形状的字面量之间也**不**相等：

```llvm
%A = type { i32, i32 }
define %A @f({ i32, i32 } %x) {
  ret %A %x                     ; ← 同样报错
}
```

**实践建议**：一旦给结构体起了名字，就在所有地方用同一个名字。

### A.1.7 缺终结指令和多余指令，报的是同一个错

两种截然不同的错误，`llvm-as` 给的信息**完全一样**：

```llvm
; 情形一：块没有终结指令
define i32 @f(i32 %a) {
entry:
  %x = add i32 %a, 1
}
```

```llvm
; 情形二：终结指令之后还有指令
define i32 @g() {
entry:
  ret i32 0
  %x = add i32 1, 2
}
```

```bash
$ llvm-as-18 no_term.ll -o /dev/null
llvm-as-18: no_term.ll:4:1: error: expected instruction opcode
}
^

$ llvm-as-18 after_term.ll -o /dev/null
llvm-as-18: after_term.ll:5:1: error: expected instruction opcode
}
^
```

**提示**：看到 `expected instruction opcode`，要同时怀疑这两种可能。自己写的生成器最好在内部断言里把两者区分开（正文第 14.7 节）。

## A.2 版本差异（LLVM 18 相对旧版本）

这些不是「说法错误」，而是**旧资料在 LLVM 18 上不适用**。

### A.2.1 `opt` 的旧式 pass 语法已被移除

```bash
$ opt-18 -mem2reg -S input.ll
The `opt -passname` syntax for the new pass manager is not supported, please use `opt -passes=<pipeline>` (or the `-p` alias for a more concise version).
See https://llvm.org/docs/NewPassManager.html#invoking-opt for more details on the pass pipeline syntax.
```

**必须写 `-passes=`**（或 `-p`）：

```bash
opt-18 -passes=mem2reg -S input.ll -o out.ll
opt-18 -p mem2reg -S input.ll -o out.ll          # 等价
```

### A.2.2 指针统一为 `ptr`（opaque pointer）

旧资料写 `i32*`、`%struct.Point*`。LLVM 18 一律是 `ptr`：

| 位置 | 旧写法（≤14） | LLVM 18 |
|---|---|---|
| 结构体字段 | `getelementptr %struct.P, %struct.P* %p, i32 0, i32 1` | `getelementptr inbounds %struct.P, ptr %p, i32 0, i32 1` |
| 加载 | `load i32, i32* %p` | `load i32, ptr %p, align 4` |
| 函数指针 | `i32 (i32, i32)*` | `ptr` |

**有意思的是**：LLVM 18 对旧写法仍然**宽容** —— 它会静默地帮你升级：

```bash
$ cat > typedptr.ll <<'EOF'
define i32 @f(i32* %p) {
  %v = load i32, ptr %p
  ret i32 %v
}
EOF
$ llvm-as-18 typedptr.ll -o /dev/null && echo ACCEPTED
ACCEPTED
$ opt-18 -passes=verify -S typedptr.ll
; ModuleID = 'typedptr.ll'
source_filename = "typedptr.ll"

define i32 @f(ptr %p) {          ; ← 已经被改写成 ptr
  %v = load i32, ptr %p, align 4
  ret i32 %v
}
```

**所以「老写法也能跑」不等于「老写法是对的」** —— 你写 `i32*`，读回来是 `ptr`。

### A.2.3 `disp` 类型相等规则的严格化

见 A.1.6。旧版本 LLVM 的类型相等规则更宽松，一些「结构相同即相等」的代码在 18 上会报错。

### A.2.4 浮点常量的打印格式

**旧资料常见**：`0.1` 会打印成 `0x3FB999999999999A`。

**LLVM 18 实测**：能精确往返的十进制会优先用十进制。

```llvm
define dso_local double @dbl_tenth() #0 {
  ret double 1.000000e-01          ; ← 不是 0x3FB999999999999A
}
```

只有十进制无法精确表示时才回退到十六进制位模式：

```llvm
ret double 0x3FBF9ADD3746F65F      ; 0.1234567890123456789
ret float 0x3FB99999A0000000       ; 0.1f
```

**规则**：LLVM 尝试用十进制打印；如果该十进制串能解析回完全相同的位模式，就用十进制，否则用十六进制。

## A.3 元数据与属性：查表容易记错的几项

### A.3.1 模块标志的行为值

`!llvm.module.flags` 里每一项是 `!{行为, "名字", 值}`。行为值的完整对照（来自 LLVM 18 的 `llvm/IR/Module.h`）：

| 值 | 名称 | 含义 |
|---|---|---|
| 1 | `Error` | 两个模块的值不一致就报错 |
| 2 | `Warning` | 不一致就警告，取第一个模块的值 |
| 3 | `Require` | 要求另一个 flag 在链接后存在且为指定值 |
| 4 | `Override` | 用本模块的值，忽略对方 |
| 5 | `Append` | 追加（两个值都必须是元数据节点） |
| 6 | **`AppendUnique`** | 追加并**去重** |
| 7 | `Max` | 取最大值（值必须是整数） |
| 8 | `Min` | 取最小值（值必须是整数） |

**注意没有「Modulo」这个行为**（有的资料会写错）。枚举的合法范围就是 1–8，写 9 或更大验证器会拒绝。

实测中你最常见到的是：

```llvm
!0 = !{i32 1, !"wchar_size", i32 4}      ; Error 级：wchar_t 必须是 4 字节
!1 = !{i32 8, !"PIC Level", i32 2}       ; Min：位置无关代码级别
!4 = !{i32 7, !"frame-pointer", i32 2}   ; Max：帧指针模式
```

### A.3.2 函数属性的两处容易混淆

| 属性 | 易混点 |
|---|---|
| `norecurse` | 它和 `noreturn` 无关；表示「不直接递归」。旧名是 `norecurse`（现代 LLVM 一度叫过 `norecurse`，现已统一） |
| `nounwind` | 表示「不抛异常」，与「不返回」（`noreturn`）是两件事 |
| `willreturn` | 「一定会返回」，与 `noreturn` 语义相反 |

### A.3.3 `-print-after-all` 的输出格式

旧资料里常见的写法是 `*** IR Dump After Mem2Reg ***`。

LLVM 18 的实际格式是 **`; *** IR Dump After <类名>Pass on <函数名或 [module]> ***`**，注意**行首有 `; `**（它是注释），而且用的是 **pass 的类名**：

```
; *** IR Dump After PromotePass on sum_to ***
```

**`mem2reg` 的类名是 `PromotePass`** —— 命令里写 `-passes=mem2reg`，dump 里显示 `PromotePass`。这就是为什么按 pass 名去 grep 往往什么都找不到：

```bash
opt-18 -passes='default<O2>' -print-after-all -S in.ll -o /dev/null 2> trace.txt
grep -n "IR Dump After" trace.txt | head
```

## A.4 关于「三行 IR」的说法

这是关于 LLVM IR 最广为流传的一句话：

> `int mul_add(int x, int y, int z) { return x*y + z; }` 会变成 `mul`、`add`、`ret` 三行 IR。

**在 `-O0` 下这不成立。** 真实的 `-O0` 输出函数体里有 **12 条指令**：

```llvm
define dso_local i32 @mul_add(i32 noundef %0, i32 noundef %1, i32 noundef %2) #0 {
  %4 = alloca i32, align 4
  %5 = alloca i32, align 4
  %6 = alloca i32, align 4
  store i32 %0, ptr %4, align 4
  store i32 %1, ptr %5, align 4
  store i32 %2, ptr %6, align 4
  %7 = load i32, ptr %4, align 4
  %8 = load i32, ptr %5, align 4
  %9 = mul nsw i32 %7, %8
  %10 = load i32, ptr %6, align 4
  %11 = add nsw i32 %9, %10
  ret i32 %11
}
```

**「三行」描述的是优化后的结果**（`-O2` 才是那三行）：

```llvm
define dso_local i32 @mul_add(i32 noundef %0, i32 noundef %1, i32 noundef %2) local_unnamed_addr #0 {
  %4 = mul nsw i32 %1, %0
  %5 = add nsw i32 %4, %2
  ret i32 %5
}
```

**为什么 `-O0` 这么啰嗦？** 两个原因：

1. **服务调试器** —— 参数存进栈里，gdb 才能在函数执行的任意时刻看到它们；
2. **把可变变量翻译成 SSA** —— 内存是可变的，SSA 值不是。变量放栈上是最省事的做法。

正文第 2 章完整展开了这一点，也是全书的起点。这里重复一次，是因为它太常见了。

## A.5 一份自检清单

当你发现「我的输出和教程对不上」时，按顺序检查：

1. **工具版本**：`clang-18 --version` 是不是 18.1.3？本书所有输出都基于它。
2. **优化级别**：`-O0` 和 `-O2` 的输出差异可以非常大。教程说的「三行」是哪个级别？
3. **`optnone`**：如果你在对 `-O0` 的 IR 跑 `opt` 却毫无变化，检查函数属性里有没有 `optnone` —— 它会**静默地**让所有 pass 失效（正文第 13.6 节）。
4. **`opt` 语法**：是不是用了被移除的 `-mem2pass` 式旧语法？改 `-passes=`。
5. **datalayout 与 triple**：手写的 `.ll` 如果没有这两行，LLVM 会用宿主默认值，`getelementptr` 算出的偏移可能不同。
6. **报错原文**：`llvm-as` 的报错有时会在**两个不同的原因**下给出同一句话（见 A.1.7）。不要只看一句话就下结论。

## A.6 记住「直觉」与「实际」的落差

把这一节放在最后，是因为它比任何单条语法都重要。

本附录收录的每一条，本质上都是同一个模式：

> **你的直觉告诉你应该这样写，但 LLVM 要你那样写。**

- 十六进制看起来应该是 `0x2A`，实际是 `u0x2A`；
- 可见性看起来应该跟在逗号后面，实际要写在前面；
- `trunc` 看起来应该像 `add` 一样能带 `nsw`，实际不能；
- 原子操作看起来应该叫 `smax`（因为 `icmp` 就叫 `slt`），实际叫 `max`。

**这些落差不是 LLVM 的缺陷，而是它几十年演进的沉积层。** 每一处不一致背后都有一段历史：某个语法先被设计成 A，后来发现 B 更合适，但 A 已经不能改了（会破坏兼容性）。

所以你不可能通过「把规则背下来」来避免踩坑 —— 规则本身就自相矛盾。**唯一可靠的办法是：写完就验证。**

```bash
llvm-as-18 yourfile.ll -o /dev/null && echo OK
```

这一条命令能挡掉本附录里绝大多数的坑，而且它只需要一秒钟。

**最后再强调一次**：如果你在本附录里读到某条，而你的终端给出了不同结果，**以你的终端为准**，然后检查工具版本。本书基于 LLVM 18.1.3，而 LLVM 每半年一个大版本。
