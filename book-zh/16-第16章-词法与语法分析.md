# 第 16 章 词法分析与语法分析

## 16.1 回指：第 8 章「符号 vs 整数」的区分

第 8 章讲了标识符的两类形式：命名值 `%name` 和编号值 `%0`。当时强调过一点：

> **命名值不能以数字开头，否则会被解析成编号值。**

这个坑在**我们自己的语言**里也有一个完全对应的版本。看这两个表达式：

```lisp
(+ x 1)
(+ x -1)
```

第一个 `1` 是整数。第二个 `-1` 呢？它可能是：
- 整数「负一」；
- 也可能是符号 `-` 后面跟着整数 `1`（即 `(- 1)`，一个减法）。

**这个歧义必须在词法分析阶段就解决。** 我们的规则是：

> **`-` 后面紧跟数字时，它是一个负整数；否则它是减法符号。**

这和第 8 章 LLVM 的 `%1abc` 问题是同一类问题：**词法层的切分规则决定了语法层的结构**。本章就来写这个切分器。

## 16.2 整体架构：两遍扫描

```
源码文本
   │
   │  ① lexer.py：字符 → token
   ▼
token 流：[Token(punct,"("), Token(sym,"+"), Token(int,1), ...]
   │
   │  ② reader.py：token → S-表达式
   ▼
S-表达式：[Sym(+), 1, 2]
   │
   │  ③ compiler.py（第 17-19 章）
   ▼
LLVM IR
```

**为什么分两遍？** 因为这两遍做的判断**性质不同**：

- 词法分析只关心**局部字符模式**（「这几个字符是一个数字」）；
- 语法分析关心**嵌套结构**（「这个 `)` 匹配哪个 `(`」）。

混在一起写（扫描时直接建树）是可行的，但会让错误报告变难，并且让「区分符号与整数」这类判断无处安放。分开之后，每一遍都可以单独测试。

## 16.3 词法分析：`lexer.py`

### Token 的表示

```python
class Token:
    __slots__ = ("kind", "value", "line", "col")

    def __init__(self, kind, value, line, col):
        self.kind = kind      # "int" | "sym" | "punct" | "eof"
        self.value = value
        self.line = line
        self.col = col
```

只有四种 token：

| `kind` | `value` | 例子 |
|---|---|---|
| `"int"` | Python `int` | `42`、`-7` |
| `"sym"` | 字符串 | `defn`、`+`、`fib` |
| `"punct"` | `"("`、`")"`、`"'"` | `(` |
| `"eof"` | `None` | 输入结束标记 |

**为什么要记录 `line` 和 `col`？** 因为错误信息必须能指向源码的准确位置。这是「用户体验」在编译器里的第一个体现：

```
line 3, col 12: unclosed '('
```

比 `SyntaxError: something went wrong` 有用一百倍。

### 主循环

```python
def tokenize(text):
    tokens = []
    i = 0
    line = 1
    col = 1
    n = len(text)

    def advance(k=1):
        nonlocal i, line, col
        for _ in range(k):
            if i < n and text[i] == "\n":
                line += 1
                col = 1
            else:
                col += 1
            i += 1

    while i < n:
        ch = text[i]

        if ch in " \t\r\n":          # 空白：跳过
            advance()
            continue

        if ch == ";":                # 注释：跳到行尾
            while i < n and text[i] != "\n":
                advance()
            continue

        if ch in PUNCTUATION:        # 括号和引号：单字符 token
            tokens.append(Token("punct", ch, line, col))
            advance()
            continue

        if ch.isdigit() or (ch == "-" and i + 1 < n and text[i + 1].isdigit()):
            # 整数（可能是负数）
            ...

        if ch.isalpha() or ch in "_+-*/%=<>!?":
            # 符号
            ...

        raise LispSyntaxError(f"unexpected character {ch!r}", line, col)

    tokens.append(Token("eof", None, line, col))
    return tokens
```

### 关键点一：负数的识别规则

这是本章开头那个歧义的处理：

```python
if ch.isdigit() or (ch == "-" and i + 1 < n and text[i + 1].isdigit()):
    start = i
    if ch == "-":
        advance()                    # 吃掉负号
    while i < n and text[i].isdigit():
        advance()
    tokens.append(Token("int", int(text[start:i]), start_line, start_col))
```

**核心条件**：`ch == "-" and 下一个字符是数字`。

- `-1` → 负号后面是 `1`，识别为整数 `-1`；
- `-` 单独出现 → 后面不是数字，落到符号分支，识别为符号 `-`；
- `a-1` → 在 `a` 那里就已经把 `a-1` 整体吃成符号了（见下一节）。

实测：

```python
>>> from reader import read_one, unparse
>>> unparse(read_one('(- 5 3)'))
'(- 5 3)'                      # '-' 是符号，5 和 3 是整数
>>> read_one('-7')
-7                             # 负整数
```

### 关键点二：符号字符集

```python
if ch.isalpha() or ch in "_+-*/%=<>!?":
    start = i
    while i < n and not text[i].isspace() and text[i] not in PUNCTUATION + ";":
        advance()
    tokens.append(Token("sym", text[start:i], start_line, start_col))
```

**起始字符**必须是字母或 `_+-*/%=<>!?` 之一。这防止了「数字开头」的符号（第 8 章的教训）。

**后续字符**则宽松得多：只要不是空白、括号或分号就行。所以 `sum_to`、`<=`、`!=` 都能正确识别。

**注意 `-` 也是合法的符号起始字符。** 这很必要，因为 `(- a b)` 里的 `-` 需要被识别成符号。上面的负数规则会优先处理「`-` 后跟数字」的情况，剩下的 `-` 才走符号分支。

### 关键点三：注释

```python
if ch == ";":
    while i < n and text[i] != "\n":
        advance()
    continue
```

注释直接跳过，不产生 token。**注意注释以换行结束**，而不是以某个结束符。

### 错误报告

```python
raise LispSyntaxError(f"unexpected character {ch!r}", line, col)
```

`LispSyntaxError` 把位置信息格式化成可读的消息：

```python
class LispSyntaxError(Exception):
    def __init__(self, message, line, col):
        super().__init__(f"line {line}, col {col}: {message}")
        self.message = message
        self.line = line
        self.col = col
```

实测：

```python
>>> from reader import read_one
>>> read_one('(foo bar')
LispSyntaxError: line 1, col 1: unclosed '('
>>> read_one(')')
LispSyntaxError: line 1, col 1: unexpected ')'
```

## 16.4 语法分析：`reader.py`

### S-表达式的内存表示

我们用**普通的 Python 值**表示 S-表达式：

```
Lisp 写法      Python 表示
42        →    int 42
foo       →    Sym("foo")
(+ 1 2)   →    [Sym("+"), 1, 2]
(quote x) →    [Sym("quote"), Sym("x")]
```

**为什么不用自定义的 AST 节点类？** 因为 S-表达式本身就是嵌套列表，用 Python `list` 表示是**零阻抗**的。这与「因为 Lisp 语法简单所以选它」的理由一脉相承 —— 不引入不必要的抽象。

**但符号必须用专门的类型**（`Sym`）而不是 `str`。原因：

```python
"foo" == "foo"      # 字符串比较内容
Sym("foo") == Sym("foo")   # 也需要比较身份
```

如果符号用 `str`，代码里就分不清「符号 `foo`」和「字符串常量 `"foo"`」。**我们的语言没有字符串常量，但代码生成器里会有很多字符串（IR 文本、错误消息），这个区分很重要。**

`Sym` 用**驻留**（interning）实现，所以相同名字的符号是同一个对象，可以用 `is` 比较：

```python
class Sym:
    __slots__ = ("name",)
    _table = {}

    def __new__(cls, name):
        existing = cls._table.get(name)
        if existing is not None:
            return existing
        self = super().__new__(cls)
        self.name = name
        cls._table[name] = self
        return self
```

实测：

```python
>>> from reader import Sym
>>> Sym("foo") is Sym("foo")
True
```

### 递归下降读取

```python
class Reader:
    def __init__(self, text):
        self.tokens = tokenize(text)
        self.pos = 0

    def peek(self):
        return self.tokens[self.pos]

    def next(self):
        tok = self.tokens[self.pos]
        self.pos += 1
        return tok

    def read(self):
        """读取恰好一个表达式，并要求输入被耗尽。"""
        expr = self.read_expr()
        tok = self.peek()
        if tok.kind != "eof":
            raise LispSyntaxError(
                f"unexpected {tok.value!r} after expression", tok.line, tok.col
            )
        return expr

    def read_expr(self):
        tok = self.next()

        if tok.kind == "int":
            return tok.value

        if tok.kind == "sym":
            return Sym(tok.value)

        if tok.kind == "eof":
            raise LispSyntaxError("unexpected end of input", tok.line, tok.col)

        if tok.value == "(":
            items = []
            while True:
                nxt = self.peek()
                if nxt.kind == "eof":
                    raise LispSyntaxError("unclosed '('", tok.line, tok.col)
                if nxt.kind == "punct" and nxt.value == ")":
                    self.next()
                    return items
                items.append(self.read_expr())

        if tok.value == ")":
            raise LispSyntaxError("unexpected ')'", tok.line, tok.col)

        if tok.value == "'":
            return [Sym("quote"), self.read_expr()]

        raise LispSyntaxError(f"cannot read {tok.value!r}", tok.line, tok.col)
```

**这就是全部的语法分析器。** 它只有 40 行，因为 S-表达式的语法就是「括号嵌套」—— 没有运算符优先级，没有歧义，不需要回溯。

对比一下：如果要解析 C 的 `a + b * c`，你需要一个优先级表或者分层文法。而在 Lisp 里 `(+ a (* b c))` 的嵌套结构**已经**表达了优先级。

### 出错时的处理：为什么 `unclosed '('` 指向开头

注意这一行：

```python
raise LispSyntaxError("unclosed '('", tok.line, tok.col)
```

它报的是**那个没有闭合的左括号**的位置（`tok` 是最初读到的 `(`），而不是文件结尾的位置。

这是有意的：**当括号不匹配时，用户想知道「哪个括号开的头」，而不是「文件在哪结束」。**

实测：

```python
>>> read_one('(foo bar')
LispSyntaxError: line 1, col 1: unclosed '('
```

指向 col 1，也就是那个 `(`。如果指向文件末尾，用户还得自己往回找。

### 顶层接口

```python
def read_all(text):
    """读取文本中的每一个顶层表达式。"""
    reader = Reader(text)
    forms = []
    while reader.peek().kind != "eof":
        forms.append(reader.read_expr())
    return forms
```

`read_all` 用于一个文件里含多个 `defn` 的情况。

## 16.5 完整的往返测试

来验证一下整个前端：

```python
>>> from reader import read_all, read_one, unparse
>>> unparse(read_one('(+ 1 2)'))
'(+ 1 2)'
>>> unparse(read_one('(defn add (x y) (+ x y))'))
'(defn add (x y) (+ x y))'
>>> read_one('(defn f (x) (* x -3))')
[defn, f, [x], [*, x, -3]]        # 注意 -3 是整数
>>> unparse(read_one("(if (< a 0) 'neg 'pos)"))
"(if (< a 0) (quote neg) (quote pos))"
```

最后一条展示了 `'` 的展开：`'neg` 变成 `(quote neg)`。

再测试一个真实的 Lisp 文件：

```lisp
; Recursive Fibonacci
(defn fib (n)
  (if (< n 2)
      n
      (+ (fib (- n 1)) (fib (- n 2)))))
```

```python
>>> from reader import read_all
>>> forms = read_all(open('examples/fib.lisp').read())
>>> len(forms)
1
>>> forms[0]
[defn, fib, [n], [if, [<, n, 2], n, [+, [fib, [-, n, 1]], [fib, [-, n, 2]]]]]
```

**读进来了。** 注意 `-` 在 `(- n 1)` 里是符号，而 `2` 是整数 —— 词法层的规则正确工作。

## 16.6 一个设计讨论：为什么不在 `reader` 里做语义检查

`reader` 只检查**语法**：

- 括号是否匹配；
- 是否有非法字符。

它**不**检查：

- `defn` 的参数是不是符号；
- `if` 有没有三个参数；
- 符号是不是已定义。

这些留给了 `compiler.py`。**为什么这样分？**

因为语法和语义的错误**性质不同**：

| | 语法错误 | 语义错误 |
|---|---|---|
| 例子 | 括号不匹配 | `if` 少一个分支 |
| 能否仅从文本判断 | 能 | 不能（需要符号表、上下文） |
| 在哪里检查 | `reader` | `compiler` |

如果 `reader` 去做语义检查，它就必须知道 `defn` 的语法规则，于是 `reader` 和语言定义耦合在一起。**分层是为了让每层只关心一件事。**

不过，`compiler.py` 里确实有一批「形状检查」（第 17-19 章会看到），比如：

```python
@staticmethod
def _check_defn_shape(form):
    if len(form) < 4:
        raise IRError("defn needs a name, a parameter list and a body")
    if not isinstance(form[1], Sym):
        raise IRError("defn name must be a symbol")
    if not isinstance(form[2], list):
        raise IRError("defn parameter list must be a list")
    for p in form[2]:
        if not isinstance(p, Sym):
            raise IRError(f"parameter must be a symbol, got {unparse(p)}")
```

这些检查在 `compiler.collect` 阶段（第一遍扫描）就执行，**在任何 IR 被生成之前**。这样用户不会得到「一半 IR + 一个异常」。

**这个原则和第 14.7 节讲的一样**：在抽象的层次上尽早断言，而不是让非法状态流到下游。

这个错误**基本友好**：它指出了出问题的符号名。但它没有给出**位置**（第几行第几列），因为我们只在 token 上记录了位置，而 `Sym` 没有携带它。

## 16.8 小结

- 前端分两遍：**词法分析**（字符 → token）和**语法分析**（token → S-表达式）。
- 词法分析的关键歧义是 `-`：**后面跟数字就是负整数，否则是减法符号**。这与第 8 章 LLVM 的 `%1abc` 是同一类问题。
- Token 记录行列号，让错误信息能指向源码位置。
- 符号用**驻留的 `Sym`** 表示，与 Python 字符串区分开。
- `reader` 只有 40 行 —— 因为 S-表达式没有优先级和歧义。
- `unclosed '('` 报的是**左括号**的位置，而不是文件末尾 —— 这是有意的可用性设计。
- **语法检查在 `reader`，语义检查在 `compiler`。** 分层让每层只关心一件事。
