# 第 13 章 优化管线与 `opt`

## 13.1 回指：第 2 章那个「什么都没发生」的实验

第 2 章我们做过这个实验：

```bash
clang-18 -S -emit-llvm -O0 mul_add.c -o mul_add.O0.ll
opt-18 -passes=mem2reg -S mul_add.O0.ll -o -
```

**结果什么都没变。** 当时我们找到了原因：函数头上有 `optnone`，任何 pass 见到它都会跳过。

本章把这个实验推到底：我们会看清 `-O0`/`-O1`/`-O2`/`-O3` 各自对应的**真实管线**，学会用 `opt` 逐 pass 调试，并理解为什么「clang `-O2` 的输出」和「用 `opt -O2` 处理 clang `-O0` 的输出」**不是一回事**。

## 13.2 `opt` 的新旧语法

**LLVM 18 已经移除了旧的 pass 语法。** 如果你按老教程写：

```bash
$ opt-18 -mem2reg -S input.ll
The `opt -passname` syntax for the new pass manager is not supported, please use `opt -passes=<pipeline>` (or the `-p` alias for a more concise version).
See https://llvm.org/docs/NewPassManager.html#invoking-opt for more details on the pass pipeline syntax.
```

必须用 `-passes=`（或短的 `-p`）：

```bash
$ opt-18 -passes=mem2reg -S input.ll -o output.ll
$ opt-18 -p mem2reg -S input.ll -o output.ll          # 等价
```

**这是 LLVM 18 与老教程最容易冲突的地方之一。**

## 13.3 管线的语法

`-passes=` 接受一个**管线字符串**，语法相当灵活：

### 单个 pass

```bash
opt-18 -passes=mem2reg -S in.ll -o -              # 一个 pass
opt-18 -passes=instcombine -S in.ll -o -          # 另一个
```

### 逗号分隔的序列

```bash
opt-18 -passes='instcombine,simplifycfg' -S in.ll -o -
```

**注意要加引号**，因为 shell 会解释某些字符。

### 嵌套：指定作用域

```bash
opt-18 -passes='function(instcombine,mem2reg)' -S in.ll -o -
opt-18 -passes='module(function(instcombine))' -S in.ll -o -
opt-18 -passes='cgscc(inline)' -S in.ll -o -
opt-18 -passes='loop(licm)' -S in.ll -o -
```

| 作用域 | 含义 |
|---|---|
| `module(...)` | 模块级 pass（能看到整个模块） |
| `cgscc(...)` | 调用图 SCC 级（内联等） |
| `function(...)` | 函数级 |
| `loop(...)` | 循环级 |
| `loop-mssa(...)` | 需要 MemorySSA 的循环 pass |

**理解作用域很重要**：`mem2reg` 是**函数级** pass，它看不到别的函数；`inline` 是 **SCC 级**，因为它需要调用图信息。

### 预定义管线：`default<Ox>`

```bash
opt-18 -passes='default<O2>' -S in.ll -o out.ll
opt-18 -passes='default<O3>' -S in.ll -o out.ll
opt-18 -passes='default<O1>' -S in.ll -o out.ll
```

这就是 `clang -O2` 用的那套管线（的后端部分）。

## 13.4 看清真实管线

想知道 `-O2` 到底包含哪些 pass：

```bash
opt-18 -passes='default<O2>' --print-pipeline-passes /dev/null
```

输出很长，但它就是**优化器的完整工作清单**。两个最有价值的观察：

1. **`default<O0>` 里没有 `mem2reg`，`default<O1>` 里有。** 这解释了为什么 `-O0` 的输出布满 `alloca` —— 那不是优化器的遗留，而是 clang 前端主动生成的。
2. **`-O1`/`-O2`/`-O3` 的前半部分几乎一样**，差别主要在循环优化和向量化上（`-O3` 多出 `loop-unroll<O3>` 和 `loop-vectorize`）。

完整的管线对比、各级别的差异清单、以及管线字符串的作用域语法（`function(...)`、`cgscc(...)` 等），见 [附录 B.5](22-附录B-优化入门.md#b5-看清优化管线)。

> **一个实用提醒**：如果你对 `-O0` 生成的 IR 跑 `opt` 却毫无变化，先找 `optnone` —— 它会**静默地**让所有 pass 失效。原因见 [附录 B.2](22-附录B-优化入门.md#b2-为什么跑-opt-没反应optnone)。

## 13.5 一个必须澄清的误区

**「`clang -O2` 的输出」≠「对 `clang -O0` 的输出跑 `opt -O2`」。**

实测：

```bash
clang-18 -S -emit-llvm -O0 abs_v.c -o abs_v.O0.ll
opt-18 -passes='default<O2>' -S abs_v.O0.ll -o -
```

```llvm
define dso_local i32 @abs_v(i32 noundef %0) local_unnamed_addr #0 {
  %2 = alloca i32, align 4
  %3 = alloca i32, align 4
  store i32 %0, ptr %3, align 4
  %4 = load i32, ptr %3, align 4
  %5 = icmp slt i32 %4, 0
  br i1 %5, label %6, label %9
  ...
```

**完全没有优化！** 因为 `optnone` 还在，整个 `default<O2>` 管线对这个函数视而不见。

去掉 `optnone`：

```bash
sed 's/ optnone//' abs_v.O0.ll > abs_v.nooptnone.ll
opt-18 -passes='default<O2>' -S abs_v.nooptnone.ll -o -
```

```llvm
define dso_local i32 @abs_v(i32 noundef %0) local_unnamed_addr #0 {
  %.0 = tail call i32 @llvm.abs.i32(i32 %0, i1 true)
  ret i32 %.0
}
```

这次成功了，而且结果和 `clang -O2` 直接生成的一致（都变成 `llvm.abs` 内建）。

### 这个误区的三个层次

1. **`optnone` 会静默地让整条管线失效。** 不是报错，不是警告 —— 就是什么都不做。
2. **`clang -O2` 不只是「前端 + opt 管线」。** clang 在前端就会做一些优化（比如常量折叠、简单的模式匹配），这些不在 `opt` 管线里。
3. **顺序有关。** 有些优化在 `-O0` 风格的 IR 上效果不好（比如内联决策），因为它们依赖前面 pass 的清理结果。

**所以：想研究优化，请从 `-O0` IR 出发、手动去掉 `optnone`、然后逐步加 pass。** 这是最可控的方式，也是本章推荐的工作流。

## 13.6 调试技巧：`-print-after-all`

当你想知道「到底是哪个 pass 改变了我的代码」时：

```bash
opt-18 -passes='default<O2>' -print-after-all -S in.ll -o /dev/null 2> trace.txt
```

`trace.txt` 会包含**每个 pass 执行后的完整 IR**，每段前面有一行标注。格式是 `; *** IR Dump After <类名>Pass on <函数名或 [module]> ***`：

```
; *** IR Dump After PromotePass on sum_to ***
define dso_local i32 @sum_to(i32 noundef %0) #0 {
...
; *** IR Dump After InstCombinePass on sum_to ***
define dso_local i32 @sum_to(i32 noundef %0) #0 {
...
```

**注意两点**：

1. 标注的是 **pass 的类名**，不一定等于你在 `-passes=` 里写的名字。例如 `mem2reg` 的类名是 **`PromotePass`**；
2. 模块级的 pass 显示 `on [module]`，函数级的显示具体函数名。

所以 grep 时用「函数名」或「`IR Dump`」来定位，而不是用你输入的那个 pass 名：

```bash
grep -n "IR Dump After" trace.txt | head -40      # 看看跑了哪些 pass
grep -n "PromotePass on sum_to" trace.txt         # 定位 mem2reg 之后的状态
```

想看那个 pass 之后的完整 IR：

```bash
grep -A 30 "PromotePass on sum_to" trace.txt
```

相关选项：

| 选项 | 作用 |
|---|---|
| `-print-after-all` | 每个 pass 之后打印 |
| `-print-before-all` | 每个 pass 之前打印 |
| `-print-after=<passname>` | 指定 pass 之后打印 |
| `-print-changed` | 只在 IR **发生变化**时打印（输出量小得多） |
| `-print-module-scope` | 总是打印整个模块，而不是当前函数 |
| `-verify-each` | 每个 pass 之后都运行验证器 |

**`-print-changed` 特别有用**，因为 `-print-after-all` 在 `-O2` 下会产生几 MB 的输出，而大部分 pass 什么都没改。

## 13.7 用 `opt` 做验证

`opt` 也可以单纯用来验证 IR：

```bash
opt-18 -passes=verify -S in.ll -o /dev/null && echo "IR is valid"
```

或者让它验证并规范化输出（有些细节会被重写）：

```bash
opt-18 -passes=verify -S in.ll -o -
```

**这不是多余的**：`llvm-as` 会验证，但你如果只想检查、不想生成 `.bc`，`opt -passes=verify` 更直接。

## 13.8 其他常用工具

| 工具 | 用途 |
|---|---|
| `llvm-as-18` | `.ll` → `.bc`，**并验证** |
| `llvm-dis-18` | `.bc` → `.ll` |
| `opt-18` | 跑优化管线 |
| `llc-18` | `.ll`/`.bc` → 目标汇编 |
| `lli-18` | 直接解释执行 `.bc` |
| `llvm-link-18` | 链接多个模块 |
| `llvm-nm-18` | 查看符号表 |
| `llvm-objdump-18` | 反汇编 |
| `llc-18 -filetype=asm` | 生成汇编 |
| `llc-18 -filetype=obj` | 生成目标文件 |

一个完整的流程：

```bash
# Lisp/C → IR 文本
clang-18 -S -emit-llvm -O2 prog.c -o prog.ll

# IR → 汇编
llc-18 prog.ll -o prog.s

# IR → 目标文件
llc-18 -filetype=obj prog.ll -o prog.o

# 直接执行 IR（需要 main）
lli-18 prog.ll

# 看 IR 编译成了什么汇编
llc-18 -O2 prog.ll -o - | head -30
```

### `llc` 的一个实用技巧

想知道「某个 IR 构造会变成什么汇编」，可以写一小段 IR，直接让 `llc` 编译：

```bash
$ cat > t.ll <<'EOF'
define i32 @f(i32 %a, i32 %b) {
  %r = mul i32 %a, %b
  ret i32 %r
}
EOF
$ llc-18 -O2 t.ll -o - | grep -v "^\s*\."
f:                                      # @f
	movl	%edi, %eax
	imull	%esi, %eax
	retq
```

读这段汇编：x86-64 的 System V 调用约定把第一个参数放在 `%edi`，第二个放在 `%esi`。

- `movl %edi, %eax` —— 把 `a` 复制到返回值寄存器 `%eax`；
- `imull %esi, %eax` —— 计算 `%eax = %eax * %esi`，即 `a * b`；
- `retq` —— 返回，结果已经在 `%eax` 里。

**注意 `imul` 是两操作数指令**：`imull %esi, %eax` 的意思是「`%eax = %eax * %esi`」，结果必须写回其中一个操作数。这就是为什么后端要先把 `a` 挪到 `%eax`。

这也解释了第 2 章 `mul_add` 在 `-O2` 下操作数顺序为什么会「反过来」：

```llvm
%4 = mul nsw i32 %1, %0
```

**指令选择阶段已经在考虑 `imul` 的编码约束了**，所以优化器把操作数排成了对后端更友好的顺序。

## 13.9 动手练习

**练习 13.1** 用 `--print-pipeline-passes` 打印 `default<O1>`、`default<O2>`、`default<O3>` 的管线，把三者都保存到文件，然后用 `diff` 找出差异。

一个可直接运行的版本：

```bash
opt-18 -passes='default<O1>' --print-pipeline-passes /dev/null 2>/dev/null | tr ',' '\n' | sort -u > o1.txt
opt-18 -passes='default<O3>' --print-pipeline-passes /dev/null 2>/dev/null | tr ',' '\n' | sort -u > o3.txt
comm -13 o1.txt o3.txt        # 只在 -O3 出现的 pass
```

实测结果（节选）：

```
aggressive-instcombine
argpromotion
constraint-elimination
correlated-propagation
dse
early-cse<>
gvn<>
jump-threading
loop-unroll<O3>
loop-vectorize<no-interleave-forced-only;no-vectorize-forced-only;>
```

**`loop-unroll<O3>` 和 `loop-vectorize` 是 `-O3` 的核心增量**：更激进的循环展开和自动向量化。这也解释了为什么 `-O3` 有时会让代码变慢 —— 它为了吞吐量牺牲了代码体积和指令缓存命中率。

**练习 13.2** 取 `abs_v` 的 `-O0` IR，**不要**去掉 `optnone`，直接跑 `opt-18 -passes='default<O2>'`。解释为什么没有变化。

**练习 13.3** 对同一个函数，逐步执行 `mem2reg` → `instcombine` → `simplifycfg`，记录每一步后的 IR。哪一步消除了 `alloca`？哪一步消除了死代码？

**练习 13.4** 用 `-print-changed` 跑 `default<O2>`，数一数有多少个 pass 真的改变了 IR。

**练习 13.5** 写一个含循环的 C 函数，用 `-print-after-all` 找出是哪个 pass 把循环优化掉的（提示：找 `loop-idiom`、`indvars`、`loop-delete`）。

**练习 13.6** 用 `llc-18` 把一个手写的 `mul` 函数编译成汇编，观察乘法是怎么变成 `imull` 的。

**练习 13.7（思考题）** 为什么 `-O0` 的管线里几乎什么都没有，但 `clang -O0` 的输出里却有大量的内存操作？这两件事分别是谁负责的？

## 13.10 小结

- LLVM 18 **必须**用 `opt -passes=...`，旧语法会报错。
- 管线语法支持逗号序列和 `function(...)`/`module(...)`/`loop(...)` 等作用域嵌套。
- `default<O0|O1|O2|O3>` 是预定义管线；`--print-pipeline-passes` 能看到完整清单。
- **`-O0` 的管线几乎是空的**，但它仍然需要「清理」性质的 pass（如协程）。
- **`optnone` 会静默地让整条管线失效** —— 这是理解 `-O0` 输出时最关键的一点。
- **「`clang -O2`」≠「`opt -O2` 处理 `clang -O0` 的输出」**，因为 `optnone` 和前端自身的优化都会造成差异。
- 调试优化用 `-print-after-all`、`-print-changed`、`-print-after=<pass>`。
- `opt -passes=verify` 可以单纯做验证。
