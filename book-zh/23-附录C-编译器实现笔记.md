## C.1 混合策略：参数用 SSA、`let` 用栈槽、`if` 用手工 `phi`

**这是理解本书编译器的第一件事**，正文第 17.6 节讲了一部分，这里给完整版本。

我们的编译器对三类东西用了**三种不同的**表示：

| 东西 | 表示 | 为什么 |
|---|---|---|
| 函数参数 | **SSA 值**（`%x`） | 不可变，直接用 |
| `let` 绑定的局部变量 | **栈槽**（`alloca`） | 可被 `set` 修改 |
| **`if` 的返回值** | **手工发射的 `phi`** | 两个分支的前驱**已知**，可以手工写 |

实测这张表（同一个编译器，五个不同形状的函数）：

```
alloca=0  phi=0   (defn f (x) x)                                               ; 只有参数
alloca=0  phi=1   (defn f (x) (if (< x 0) 1 2))                               ; 只有 if
alloca=1  phi=0   (defn f (x) (let ((y 1)) (+ x y)))                          ; 只有 let
alloca=1  phi=0   (defn f (n) (let ((i 0)) (while (< i n) (set i (+ i 1))) i)) ; 只有 while
alloca=1  phi=1   (defn f (x) (let ((y 1)) (if (< x 0) (set y 2) (set y 3)) y)) ; 两者都有
```

所以：

- **`fib` 只有参数和 `if`** → 零个 `alloca`，但**有** `phi`（第 19 章的例子）；
- **`sum_to` 有 `let` 和 `while`** → 三个 `alloca`，零个 `phi`（第 18 章的例子）。

**这两种形状并存，都是对的。**

## C.2 为什么 `if` 能手工发射 `phi`，`while` 不能

这是全部取舍的关键。

### `if`：前驱在编译时已知

```
        entry
        /    \
     then    else      ← 这两个块编译完时，它们的「结束块」就确定了
        \    /
        merge          ← 此时两个前驱都已知，可以当场写下 phi
```

编译 `then` 分支时，我知道它最后落在哪个块（`then_end`）；编译 `else` 时同样知道 `else_end`。所以到了 merge 块，我可以**立刻**写下：

```llvm
%r = phi i32 [ %then值, %then_end ], [ %else值, %else_end ]
```

### `while`：回边是「未来」

```
    entry
      ↓
   while.cond  ←──────┐   编译这个块时，回边还不存在
      ↓  ↑            │
   while.body ────────┘   （循环体还没生成）
```

编译 `while.cond` 的时候，循环体**还没生成**。所以：

- 此刻 `while.cond` 看起来只有一个前驱（入口块）；
- 但循环体末尾马上会加一条回边，使它变成两个前驱；
- **如果此时发射 `phi`，就会漏掉那个还没出现的前驱** —— 验证器会报 `PHI node entries do not match predecessors!`

**这正是「sealed block」问题**：一个块的 `phi` 只有在它**所有前驱都确定**之后才能完成。`if` 的 merge 块在编译完两个分支后前驱就确定了；`while` 的 cond 块要等循环体编译完。

### 我们的两个选择

| 情形 | 前驱是否已知 | 做法 |
|---|---|---|
| `if` 的 merge | **编译时已知** | 手工发射 `phi` |
| `while` 的 cond | **编译时未知** | 把变量放栈槽，**根本不需要 `phi`** |

**这个划分不是随意的，它精确对应「前驱是否已知」。**

### 顺带说说那个真实的报错

如果把 `phi` 的操作数写成「分支入口块」而不是「分支结束块」，就会踩到下面这个坑。

看一个容易写错的版本（`branch` 和 `compile_expr` 的顺序颠倒了）：

```python
fn.start(then_block)
fn.branch_placeholder(merge_ref)                    # ← 先发射跳转
then_val = self.compile_expr(fn, env, then_expr)    # ← 再编译表达式
```

这看起来「更整齐」（先结束块，再编译内容），但它**是错的**。因为 `compile_expr` 会：

1. 把 `current` 移到一个新块（嵌套 `if` 的 `merge6`）；
2. 在那里的 `phi` 之后留下 `current`。

于是 `branch_placeholder` 施加到了 `then1` 上，而 `then_val` 却在 `merge6` 里算出来 —— `merge6` 永远跳不到外层的 `merge3`。验证器给出：

```
llvm-as-18: assembly parsed, but does not verify as correct!
PHI node entries do not match predecessors!
  %t5 = phi i32 [ %t2, %then1 ], [ %t4, %else2 ]
label %else2
label %merge6
Instruction does not dominate all uses!
  %t4 = phi i32 [ 0, %then4 ], [ 1, %else5 ]
  %t5 = phi i32 [ %t2, %then1 ], [ %t4, %else2 ]
```

**修复**：把 `branch` 移到编译表达式**之后**，并用 `fn.current` 而不是 `then_block` 作为 `phi` 的操作数：

```python
fn.start(then_block)
then_val = self.compile_expr(fn, env, then_expr)
then_end = fn.current                  # ← 编译完才知道落在哪个块
fn.branch_placeholder(merge_ref)       # ← 现在才发射跳转
```

### 教训

> **「当前块」是一个会被子编译过程修改的隐式状态。**

编译一个表达式**不保证**回到原来的块。任何「编译前后块不变」的假设都是错的。

这个问题的通用解法有两种：

1. **显式读回当前块**（我们的做法：`fn.current`）；
2. **不共享可变状态**，让 `compile_expr` 返回 `(value, end_block)`。

## C.3 `ir.py` 里那套闲置的 SSA 机制

`ir.py` 的实现比当前需要更通用。具体来说，下面这些代码**没有被用到**：

| 代码 | 状态 |
|---|---|
| `Function.var(name, ty)` | 未调用（编译器直接用 `read_var`） |
| `Function.set_var(name, ty, v)` | 未调用 |
| `Function._read_variable` | 只被 `var` 调用 |
| `Function._add_phi_operand` | 同上 |
| `Function._complete_phi` | 只被 `seal_block` 调用 |
| `Function.seal_block` | `op_while` 里调用了，但变量都在内存里，它无事可做 |
| `Function.materialize_phis` | 被 `render` 调用，但块里没有通过这套机制产生的 `phi` |
| `Phi` 类 | 同上 |

这套代码实现的是完整的 **sealed-block SSA 构造算法**（Braun 等人，*Simple and Efficient Construction of Static Single Assignment Form*）。如果把它用起来，前端可以让每个变量都走 `var`/`set_var`，从而**完全不需要 `alloca`**。

### 验证它确实闲置

在 `materialize_phis` 里加一行打印：

```python
def materialize_phis(self):
    for block in self.blocks:
        phis = [
            (name, entry)
            for name, entry in block.bindings.items()
            if isinstance(entry, Phi)
        ]
        if not phis:
            continue
```

在 `if not phis: continue` 之前插入 `print("phi found", block.label)`，然后编译 `fib`、`classify`、`sum_to`：

```bash
$ python3 compiler.py examples/fib.lisp > /dev/null   # 无输出
```

**没有任何输出。** 因为 `fib` 里唯一的 `phi` 是 `op_if` 手工发射的**文本**，不在 `bindings` 里。

### 为什么保留它

1. **它展示了完整的 SSA 构造算法。** 读者如果要做纯 SSA 的前端，这里是起点。
2. **`op_if` 本来可以用它。** 如果把 `if` 的两个分支值也纳入变量表，就不用手工发射 `phi` 了。手工发射让流程**看得更清楚**，通用机制则更可扩展。
3. **诚实的架构应该允许未使用的抽象。** 一个把所有代码都用上的设计，往往意味着抽象层次被压得太低。

**但重要的是：书里明确告诉你了。** 否则你读代码时会以为 `seal_block` 是关键路径，花时间去理解一套其实没跑起来的逻辑。

## C.4 我们的 IR 经 `-O2` 后为什么和 clang 不完全一样

正文第 20 章对比过一个结果：我们生成的 `sum_to` 经 `-O2` 后，**循环还在**；而 clang 的 `-O2` 输出**把循环消掉了**，变成了闭式公式。

### 差异的根源：属性，而不是指令

看我们的生成器产出的函数头：

```llvm
define i32 @l_sum_to(i32 %n) {
```

**什么属性都没有。** 而 clang 的：

```llvm
define dso_local i32 @sum_to(i32 noundef %0) local_unnamed_addr #0 {
```

```llvm
attributes #0 = { mustprogress nofree norecurse nosync nounwind willreturn memory(none) uwtable ... }
```

关键在于 **`mustprogress`**。

### `mustprogress` 是什么

它的意思是：

> **这个函数一定会在有限步内返回，不会无限循环。**

这个承诺是**把循环替换成公式的必要前提**。因为「循环会不会终止」如果本身不确定，那么「循环执行多久」就是程序的可观测行为，优化器不能改变它。

**C11 标准引入了 forward progress 保证**，所以 clang 可以放心地给函数加 `mustprogress`。而我们的 Lisp 编译器没有加任何属性 —— 于是 LLVM 必须保守地认为「循环可能不终止」，从而放弃公式化。

### 验证这个诊断

给我们的 IR 手工加上属性：

```bash
sed 's/^define i32 @l_sum_to(i32 %n) {/define i32 @l_sum_to(i32 %n) mustprogress nounwind willreturn {/' sum.ll > sum_mp.ll
opt-18 -passes='default<O2>' -S sum_mp.ll | sed -n '/define/,/^}/p'
```

```llvm
define i32 @l_sum_to(i32 %n) local_unnamed_addr #0 {
entry0:
  %t2.not4 = icmp slt i32 %n, 1
  br i1 %t2.not4, label %while.end3, label %while.body2.preheader

while.body2.preheader:                            ; preds = %entry0
  %0 = add nuw i32 %n, 1
  %smax = tail call i32 @llvm.smax.i32(i32 %0, i32 2)
  %1 = shl nuw i32 %smax, 1
  %2 = add nsw i32 %smax, -2
  %3 = zext nneg i32 %2 to i33
  %4 = add nsw i32 %smax, -3
  %5 = zext i32 %4 to i33
  %6 = mul i33 %3, %5
  %7 = lshr i33 %6, 1
  %8 = trunc i33 %7 to i32
  %9 = add i32 %1, %8
  %10 = add i32 %9, -3
  br label %while.end3

while.end3:                                       ; preds = %while.body2.preheader, %entry0
  %s.addr.0.lcssa = phi i32 [ 0, %entry0 ], [ %10, %while.body2.preheader ]
  ret i32 %s.addr.0.lcssa
}
```

**循环没了，`i33` 出现了** —— 和 clang 的形状一致。而且它算得对：

```bash
$ opt-18 -passes='default<O2>' -S sum_mp.ll -o sum_mp_o2.ll
$ llvm-as-18 sum_mp_o2.ll -o sum_mp_o2.bc
$ clang-18 -w driver.c sum_mp_o2.bc -o t && ./t
0 55 500500
```

（`0 55 500500` 正是 `sum_to(0)`、`sum_to(10)`、`sum_to(1000)` 的正确答案。）

### 这个发现的普遍意义

**只差一个属性。**

它精确地展示了前端和后端的责任边界：

| 关注点 | 谁负责 |
|---|---|
| 语义正确（算得对） | **前端** |
| 把可变量提升为 SSA | LLVM（`mem2reg`） |
| **告诉 LLVM「循环一定终止」** | **前端**（加 `mustprogress`） |
| 循环公式化、向量化、内联 | LLVM |

**`mustprogress` 是源语言语义的信息**，只有前端知道。LLVM 无法自己推断它 —— 因为一个允许无限循环的语言**不能**声明 `mustprogress`。

**那我们的编译器应该加上它吗？** 不应该。因为我们的语言规范**没有**说循环必须终止，加上它就是在撒谎。诚实的做法有两条：

1. **在语言规范里加上**「所有循环必须在有限步内终止，否则行为未定义」—— 和 C11 的 forward progress 一样；或者
2. **保持沉默**，接受优化机会的损失。

本书选择第 2 条，并在这里明确记录这个权衡。

### 所以我们的编译器到底做到了什么

**做到的**（已实测）：

- 生成的 IR **通过 LLVM 验证器**（22/22 端到端测试）；
- `mem2reg` 后，`sum_to` 的内存操作全部消失，产生**和 clang 同构的 `phi` 结构**；
- 生成的程序在 `-O1`/`-O2`/`-O3` 下**行为正确**；
- 加上 `mustprogress` 后，能达到**和 clang 相同的优化结果**。

**没做到的**：

- **默认不生成任何函数属性**，所以 LLVM 的优化比 clang 保守；
- 不做类型推断、不做内联提示、不生成 `noundef` 等属性。

**但这不影响核心结论**：

> **一个约 500 行的前端，把语义正确地翻译成 IR，就能让 LLVM 的优化器完成绝大部分工作。** 剩下的一点点差距，是**源语言语义信息**的缺失，而不是 IR 生成质量的差距。

## C.5 编号值那个坑的完整复盘

正文第 8 章讲过 LLVM 的编号规则，第 17 章提过「不要用编号值」。这里给完整版本。

### 天真的实现

```python
class Function:
    def __init__(self):
        self.temp_counter = 0

    def new_temp(self):
        self.temp_counter += 1
        return f"%{self.temp_counter}"        # ← 用编号值
```

想法是：「我自己数着，第一个临时值叫 `%1`，第二个叫 `%2`……」

### 为什么会失败

因为编号计数器是**参数、匿名基本块、有结果的指令**三者**共享**的（正文第 8 章）。而生成器在生成过程中会插入大量基本块：

```python
then_block = fn.new_block("then")     # 生成器以为这只是个名字
```

如果生成器用了**编号标签**，或者用 `%{counter}` 做临时值，计数器就会和 LLVM 的真实计数器脱节。报错长这样：

```llvm
; numfail.ll
define i32 @l_ack(i32 %m, i32 %n) {
entry:
  %1 = icmp eq i32 %m, 0
  br i1 %1, label %2, label %3
2:
  %6 = add i32 %n, 1
  ret i32 %6
3:
  %4 = sub i32 %m, 1        ; ← 编号从 %6 倒退到 %4
  ret i32 %4
}
```

```bash
$ llvm-as-18 numfail.ll -o /dev/null
llvm-as-18: numfail.ll:8:1: error: label expected to be numbered '7' or greater
3:
^
```

源文件位于 `code/part2-ir/numfail.ll`（与其它"故意写错"的示例放在一起）。

读法：生成器以为「下面该轮到 `%4` 了」，但 LLVM 的计数器已经涨到 12 了。

### 为什么这个 bug 特别难查

因为它**不是每次都报错**。编号值的规则是「必须单调递增，**允许跳号**」。所以：

- 生成器的计数器**偏小**时会报错（如上）；
- **偏大**时**不会报错**：

```llvm
define i32 @f(i32 %x) {
entry:
  %5 = add i32 %x, 1       ; 跳过了 %1..%4，LLVM 接受
  ret i32 %5
}
```

**这通过了验证。** 但编号和实际结构脱节了，以后想在某处插入指令时会发现「没有号码可用」。

**更糟的是**：如果生成器混用编号标签和命名标签，有些函数能过、有些不能，报错位置还指向你没写过的地方。

### 解决方案：全用命名值

```python
def new_temp(self):
    """分配一个新的*命名*临时值。"""
    self.temp_counter += 1
    return f"%t{self.temp_counter}"
```

生成：

```llvm
define i32 @l_fib(i32 %n) {
entry0:
  %t1 = icmp slt i32 %n, 2
  br i1 %t1, label %then1, label %else2
```

**参数是命名值，临时值是命名值，块标签是命名值 —— 没有任何编号值，规则完全不适用。**

### 教训

> **不要和你不完全理解的隐式规则打交道。**

花时间精确模拟 LLVM 的编号规则是**没有必要**的负担。命名值稍长几个字符，换来的是：

- 不可能因为计数器脱节而失败；
- 生成的 IR 可读性更好（`%t1` 明确标记了「这是前端产生的临时值」）；
- 调试时能一眼看出哪个值是谁生成的。

**这不是「绕过」规则，而是在理解规则之后做出的工程选择。**
