# 第 15 章 目标语言设计与项目骨架

## 15.1 回指：第 14 章那个 100 行的骨架

第 14 章我们写出了这个：

```python
def generate_add():
    fn = Function("add", "i32", ["i32", "i32"], ["%a", "%b"])
    entry = fn.new_block("entry")
    fn.start(entry)
    r = fn.emit_value("i32", "add i32 %a, %b")
    fn.terminate(f"ret i32 {r}")
    return fn.render()
```

它生成了一段能通过 `llvm-as-18` 验证、能被 `lli-18` 执行、能算出 42 的 IR。

**本章的任务是回答一个设计问题**：要把这 100 行扩展成一个真正的编译器，我们该做哪些取舍？

因为编译器可以无限复杂。如果没有清晰的边界，第三部分会变成一本讲编译原理的千页巨著，而你想学的是 **LLVM IR**。所以本章最重要的一节是 **15.3：我们不做哪些事**。

## 15.2 为什么选 Lisp

本书的源语言是一个 Lisp 方言。理由很具体：

**理由一：S-表达式的语法可以在一小时内讲完。**

我们的完整语法只需要一页纸（15.4 节）。如果把源语言换成 C 的子集，第 16 章就要花掉几十页讲类型声明、运算符优先级、指针声明符的读法（`int (*f)(int)` 到底是什么？），而**这些内容跟 LLVM IR 毫无关系**。

**理由二：S-表达式让「语法树」和「源码」几乎同构。**

```lisp
(+ (* x y) z)
```

读进内存后就是 `[Sym(+), [Sym(*), Sym(x), Sym(y)], Sym(z)]` —— 一个嵌套列表。你不需要设计 AST 节点类，不需要 Visitor 模式。整个第 16 章可以压到很短。

**理由三：Lisp 的表达力足够写出真实的测试程序。**

我们可以写递归（`fib`）、循环（`sum_to`）、相互递归（`even?`/`odd?`）。这些足以覆盖 IR 生成的全部难点：`br`、`phi`、`alloca`、`call`。

**理由四：Lisp 和 SSA 有一个共同的深层特征 —— 都是「值导向」的。**

Lisp 的每个表达式都**产出值**；SSA 的每条指令也**产出值**。这种一致性让「表达式编译」变得自然：编译一个表达式，就返回一个 `Value`。

## 15.3 我们实现什么，不实现什么

这是本章最重要的一节。**一个诚实的设计文档首先要说明边界。**

### 我们实现的

| 特性 | 语法 | 对应 IR |
|---|---|---|
| 函数定义 | `(defn name (params...) body...)` | `define` |
| 外部函数声明 | `(declare name (params...))` | `declare` |
| 全局变量 | `(defg name init)` | `@name = global i32 init` |
| 局部绑定 | `(let ((v e)...) body...)` | `alloca` + `store` |
| 赋值 | `(set v e)` | `store` |
| 条件 | `(if cond then else)` | `br` + `phi` |
| 循环 | `(while cond body...)` | `br` + 回边 |
| 四则运算 | `(+ - * / %)` | `add`、`sub`、`mul`、`sdiv`、`srem` |
| 比较 | `(< <= > >= = !=)` | `icmp` |
| 函数调用 | `(f args...)` | `call` |
| 整数常量 | `42`、`-7` | `i32 42` |
| 注释 | `;` 到行尾 | 无（编译期丢弃） |

### 我们不实现的 —— 以及为什么

这份清单和上面那份同等重要。

#### 1. 不做闭包（closure）

```lisp
; 这个我们不支持
(defn make_adder (n)
  (fn (x) (+ x n)))      ; ← 内层函数捕获了 n
```

**为什么不支持？** 闭包需要**堆分配的环境记录**：

```llvm
%env = call ptr @malloc(i64 8)      ; 分配环境
store i32 %n, ptr %env              ; 把 n 存进去
; 然后每个内层函数都要接收一个 %env 参数
```

这就引入了 `malloc`、内存布局设计、以及「谁负责释放」。这些是**运行时系统**的问题，不是 **IR 生成**的问题。本书的每一章都应该为「理解 IR」服务，而闭包会让我们花三章讲内存管理。

**代价**：我们只能用顶层函数和递归，不能做高阶函数。

#### 2. 只做顶层函数，不做嵌套函数

```lisp
(defn outer (x)
  (defn inner (y) ...)    ; ← 不支持函数内定义函数
  ...)
```

**为什么？** 嵌套函数在没有闭包的情况下只是「作用域嵌套」，价值不大；而一旦支持，就要处理名字捕获和 `internal` 链接属性。**收益小，成本高。**

**代价**：所有函数都是顶层、全局可见的。

#### 3. 不做动态类型

Lisp 家族的传统是动态类型：一个变量可以先是整数、再是字符串。**我们不做。**

我们的规则是：

> **每个表达式都产出 `i32`；比较运算产出 `i1`（但会被自动提升）。**

**为什么？** 静态单类型让「编译表达式」这个函数有一个**确定的返回类型**：

```python
def compile_expr(self, fn, env, expr) -> Value:
    """编译一个表达式，返回一个 i32 类型的 SSA 值。"""
```

如果要做动态类型，每个值都得是「标签联合」（tagged union）：

```llvm
%value = type { i32, i64 }    ; { 标签, 载荷 }
```

然后每次运算前都要检查标签、失败时调用运行时错误处理。这会淹没 IR 生成的逻辑。

**代价**：没有字符串、没有列表、没有浮点。只有 `i32`。

#### 4. 不做垃圾回收，允许内存泄漏

我们的编译器**不产生任何堆分配**。

- 所有局部变量在栈上（`alloca`），函数返回时自动释放；
- 没有 `malloc`/`free` 的调用；
- 因此**没有内存泄漏的可能** —— 因为我们根本没有堆。

**等等，那这算什么「允许泄漏」？** 这里要说清楚：如果我们实现了闭包或者列表（需要 `malloc`），我们会**故意不做引用计数、不做 GC**，让内存泄漏。因为内存管理是运行时库的职责，把它塞进一本 IR 教材只会分散注意力。

**代价**：语言只能表达「栈上可算完」的问题 —— 但这恰好覆盖了我们想演示的全部 IR 特性。

#### 5. 不做尾调用优化

```lisp
(defn count_down (n)
  (if (= n 0)
      0
      (count_down (- n 1))))    ; ← 这是尾调用
```

Scheme 标准要求尾调用不消耗栈空间。**我们的编译器不做这个优化**，所以上面的函数在 `n` 很大时会栈溢出。

**为什么不做？** 尾调用优化需要**在编译期识别尾位置**，并把 `call` + `ret` 改写成 `musttail call` 或循环。这是**函数级**的变换，而我们的编译器是**表达式级**的 —— 它不回头看已经生成的指令。

**但这里有个好消息**：LLVM 自己会做尾调用优化。如果你在生成的 IR 上跑 `-O2`，`tailcallelim` pass 会尝试把尾递归变成循环。所以**我们把这个任务委托给了 LLVM** —— 这正是「自己写前端 + 复用 LLVM 后端」这个架构的价值所在。

**这个取舍是可以用实验验证的**，而且结果很有说服力。考虑一个尾递归的累加函数：

```lisp
(defn sum_acc (n acc)
  (if (= n 0)
      acc
      (sum_acc (- n 1) (+ acc n))))
```

我们的编译器生成的 `-O0` IR：

```llvm
define i32 @l_sum_acc(i32 %n, i32 %acc) {
entry0:
  %t1 = icmp eq i32 %n, 0
  br i1 %t1, label %then1, label %else2
then1:
  br label %merge3
else2:
  %t2 = sub i32 %n, 1
  %t3 = add i32 %acc, %n
  %t4 = call i32 @l_sum_acc(i32 %t2, i32 %t3)
  br label %merge3
merge3:
  %t5 = phi i32 [ %acc, %then1 ], [ %t4, %else2 ]
  ret i32 %t5
}
```

注意 `%t4 = call i32 @l_sum_acc(...)` 后面紧跟 `br label %merge3`，而 `merge3` 里直接 `ret`。**这是一个尾调用**，但我们的编译器看不出这一点 —— 它老老实实地生成了一次真正的 `call`，栈帧会一层层累积。

测一下（用一个 C 驱动调用它）：

```bash
$ clang-18 -w driver.c ta.bc -o ta0 && ./ta0
sum_acc(100,0)=5050
$ echo $?          # 只用小参数时是正常的
0
```

但把参数换成一百万：

```
$ ./ta0            # with l_sum_acc(1000000, 0)
段错误              # exit=139
```

**段错误。** 因为我们不做尾调用优化，一百万个栈帧把栈撑爆了。

现在把同一份 IR 交给 LLVM 的 `-O2`：

```bash
$ opt-18 -passes='default<O2>' -S ta.ll -o ta_o2.ll
```

```llvm
define i32 @l_sum_acc(i32 %n, i32 %acc) local_unnamed_addr #0 {
entry0:
  %t11 = icmp eq i32 %n, 0
  br i1 %t11, label %merge3, label %else2.preheader

else2.preheader:                                  ; preds = %entry0
  %0 = add i32 %n, -1
  %1 = mul i32 %0, %0
  %2 = zext i32 %0 to i33
  %3 = add i32 %n, -2
  %4 = zext i32 %3 to i33
  %5 = mul i33 %2, %4
  %6 = lshr i33 %5, 1
  %7 = trunc i33 %6 to i32
  %8 = add i32 %acc, %n
  %9 = add i32 %8, %1
  %10 = sub i32 %9, %7
  br label %merge3

merge3:                                           ; preds = %else2.preheader, %entry0
  %acc.tr.lcssa = phi i32 [ %acc, %entry0 ], [ %10, %else2.preheader ]
  ret i32 %acc.tr.lcssa
}
```

**没有 `call` 了。** 递归被彻底消除：`tailcallelim` 把它变成了循环，紧接着 `loop-idiom` 和 `indvars` 又把循环变成了闭式公式（注意那些 `i33` —— 又是第 11 章讲过的防溢出中间类型）。

而且请注意那个变量名 **`%acc.tr.lcssa`** —— `tr` 是 tail-recursion 的缩写，`lcssa` 是 **L**oop-**C**losed **S**SA **A** form。SSA 变量的名字泄露了优化器的处理过程。

运行它：

```
$ ./tao2
sum_acc(100,0)=5050 (expect 5050)
sum_acc(1000000,0)=1784293664 (expect 1784293664)
```

**正确，而且不再崩溃。** 同一个前端生成的两份 IR，经过 LLVM 优化后从「段错误」变成「结果精确正确」。

> **这个实验是本书第三部分的核心论点**：你的前端不需要什么都做。**把语义忠实地、笨拙地翻译成 IR，然后让 LLVM 去优化** —— 这是现代编译器架构最重要的分工。你省下的工作量，正是 LLVM 存在的意义。

**代价**：如果你**不**跑优化（就像 `-O0`），深递归会栈溢出。这是使用者需要知道的限制。

#### 6. 不做类型推断、不做宏、不做多返回值、不做异常

这些都要么需要类型系统，要么需要运行时支持。**一律不做。**

### 这份减法带来的结果

减到最后，我们的语言有：

- **一个类型**（`i32`，加上内部用的 `i1`）；
- **九种特殊形式/运算符**（`defn`、`defg`、`declare`、`let`、`set`、`if`、`while`，加上算术和比较）；
- **约 500 行代码生成器**。

**但它的输出是真正的 LLVM IR，能被 LLVM 的验证器接受，能被 LLVM 的优化器优化，能被 LLVM 的后端编译成机器码。** 这就够了 —— 因为本书要教的是 IR，不是「如何写一个完整的 Scheme」。

> **给读者的建议**：如果你读完之后想扩展它，最值得加的三个特性按难度排序是：
> 1. **浮点支持**（加 `double` 类型和 `fadd`/`fmul`/`fcmp`）—— 主要是把 `i32` 换成类型变量；
> 2. **数组与指针**（加 `getelementptr`）—— 需要引入「左值」概念；
> 3. **闭包** —— 需要堆分配和函数指针，工作量约等于重写一遍。
>
> 加第 1 项和第 2 项能让你把第一部分学到的 IR 全部亲手生成一遍，性价比最高。

## 15.4 语言的完整语法

这是完整的语法定义。只有一页。

```
program     ::= form*
form        ::= "(" defn ")" | "(" defg ")" | "(" declare ")" | expr

defn        ::= "defn" symbol "(" symbol* ")" expr+
defg        ::= "defg" symbol integer
declare     ::= "declare" symbol "(" type* ")"
type        ::= "i32"

expr        ::= integer
              | symbol
              | "(" let ")" | "(" set ")" | "(" if ")" | "(" while ")"
              | "(" op expr expr ")" | "(" call ")"

let         ::= "let" "(" "(" symbol expr ")" * ")" expr+
set         ::= "set" symbol expr
if          ::= "if" expr expr expr
while       ::= "while" expr expr*

op          ::= "+" | "-" | "*" | "/" | "%"
              | "<" | "<=" | ">" | ">=" | "=" | "!="

call        ::= symbol expr*
```

### 语义要点

**表达式都有值。** `if` 有值（两个分支的值合并），`let` 有值（最后一个 body 表达式的值），`while` 的值是 `0`。

**函数体是隐式的 `do`。** `(defn f (x) e1 e2 e3)` 依次求值，返回 `e3`。

**`let` 的绑定是顺序的**，后面的绑定能看到前面的：

```lisp
(let ((a 1) (b (+ a 1)))    ; b 能看到 a
  (+ a b))                   ; => 3
```

（这不是 `let*` 和 `let` 的区别问题 —— 我们就一种 `let`，它是顺序的。）

**`if` 必须有 else 分支。** 因为我们没有 `void` 类型，`if` 必须产出 `i32`。要表达「只有 then 分支」的副作用，用 `(if c e 0)`。

**`while` 的值是 `0`。** 它有副作用（通过 `set` 修改局部变量），但本身产出 `i32 0` 以保持「表达式都有值」的一致性。

**比较返回 `i1`，但会被自动提升。** 当比较的结果被用作算术操作数时（比如 `(+ (< a b) 1)`），编译器自动插入 `zext`：

```python
def to_i1(self, fn, val):
    """把一个值规约成 i1，因为 br 需要 i1。"""
```

### 一个完整例子

```lisp
; 计算 1 到 n 的和
(defn sum_to (n)
  (let ((i 1) (s 0))
    (while (<= i n)
      (set s (+ s i))
      (set i (+ i 1)))
    s))

; 递归阶乘
(defn fact (n)
  (if (<= n 1)
      1
      (* n (fact (- n 1)))))

; 声明一个外部 C 函数并使用它
(declare ext_abs (i32))
(defn abs_via_c (x) (ext_abs x))
```

## 15.5 项目骨架

```
code/part3-lispc/
├── lexer.py       词法分析：文本 → token 流
├── reader.py      语法分析：token 流 → S-表达式
├── ir.py          LLVM IR 构建器：插入点、基本块、SSA 变量
├── compiler.py    代码生成：S-表达式 → IR
├── tests.py       端到端测试（22 个用例）
└── examples/
    ├── fib.lisp        递归斐波那契
    ├── sum.lisp        while 循环 + 可变变量
    ├── countdown.lisp  尾递归（测试 LLVM 能否消除尾调用）
    └── tailacc.lisp    带累加器的尾递归
```

**依赖关系是单向的**，没有循环导入：

```
lexer.py  ←  reader.py  ←  compiler.py  →  ir.py
```

| 文件 | 行数 | 职责 |
|---|---|---|
| `lexer.py` | ~100 | 把文本切成 token，跟踪行列号 |
| `reader.py` | ~130 | 把 token 组成嵌套列表，区分符号与整数 |
| `ir.py` | ~430 | IR 构建器：`Block`、`Function`、`Module`；另含一套**未启用**的通用 SSA 构造机制（见 19.5 节） |
| `compiler.py` | ~490 | 代码生成：分派到各个 `op_*` 方法 |
| `tests.py` | ~400 | 端到端测试 |

**为什么把 `ir.py` 和 `compiler.py` 分开？**

因为它们是**两个不同的关注点**：

- `ir.py` 关心「如何把 IR 组织成一棵可渲染的结构」，它不知道 Lisp 的存在；
- `compiler.py` 关心「Lisp 的每个构造该怎么翻译」，它调用 `ir.py` 的 API。

这个分层的实际好处是：**`ir.py` 可以被复用来编译别的语言**。如果你想给这本书加一个 C 子集前端，`ir.py` 一行都不用改。

**这也是 LLVM 自己的架构**：前端（clang）和后端（LLVM Core）之间只通过 IR 通信。我们在小尺度上模仿了这个设计。

## 15.8 小结

- 选 Lisp 是因为它的语法可以一页讲完，让你把精力全放在 IR 生成上。
- **明确的不做清单和功能清单同等重要**：不做闭包、不做嵌套函数、不做动态类型、不做 GC、不做尾调用优化。
- 这些减法让我们得到一个约 500 行的代码生成器，**但它的输出是真正的、能被 LLVM 验证和优化的 IR**。
- 语言只有 `i32`（和内部的 `i1`）一个类型；每个表达式都产出值。
- 项目分四层：`lexer` → `reader` → `compiler` → `ir`，依赖单向。
- `ir.py` 与 Lisp 无关，可以复用 —— 这正是 LLVM「前后端通过 IR 通信」思想的小尺度体现。
