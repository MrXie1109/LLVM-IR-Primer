# 第 9 章 类型系统

## 9.1 回指：第 6 章那个 `%struct.Point = type { i32, i32 }`

第 6 章我们看到：

```llvm
%struct.Point = type { i32, i32 }
```

当时只说了「这是类型定义」。本章要把类型系统讲完整，并且解释：

- 为什么 C 的 `int` 变成 `i32`，而不是继续保持叫 `int`？
- 为什么 `struct Mixed { char c; int i; double d; }` 变成 `{ i8, i32, double }`，中间**没有**填充字节？
- `target datalayout` 那一长串 `e-m:e-p270:32:32-...` 到底在说什么？

## 9.2 三类类型

LLVM 的类型分三大类：

### 1. 基本类型（primitive）

| 类别 | 类型 | 说明 |
|---|---|---|
| 整数 | `i1`、`i8`、`i16`、`i32`、`i64`、`i128`、`iN` | **任意位宽**！`i3`、`i17`、`i100` 都合法 |
| 浮点 | `half`（16位）、`float`（32位）、`double`（64位）、`fp128`（128位）、`x86_fp80`（x86 80位）、`ppc_fp128` | |
| 指针 | `ptr` | LLVM 18 只有这一种指针类型 |
| 标签 | `label` | 基本块标签，只能用于 `br`/`switch` |
| 令牌 | `token` | 用于 `gc.statepoint` 等 |
| 元数据 | `metadata` | |
| void | `void` | 只能做返回类型 |

**整数位宽是任意的**，这一点和 C 很不一样。你可以写 `i3`（0~7 的三位整数）或 `i24`。优化器在把 `i8` 提升为 `i32` 运算时，会临时造出 `i33` 这样的类型。[附录 B.6](22-附录B-优化入门.md#b6-逐-pass-观察一个完整实验) 那个 `sum_to` 的 `-O2` 输出里就有：

```llvm
  %6 = zext nneg i32 %5 to i33
  %9 = mul i33 %6, %8
  %10 = lshr i33 %9, 1
  %11 = trunc i33 %10 to i32
```

`i33` 是为了在一次乘法里同时装下 32 位操作数和可能的溢出位。**这是 IR 比 C 更灵活的直接体现。**

### 2. 复合类型（aggregate）

| 类型 | 写法 | 对应 C |
|---|---|---|
| 数组 | `[10 x i32]` | `int[10]` |
| 结构体 | `{ i32, i8 }` | `struct` |
| 打包结构体 | `<{ i32, i8 }>` | `__attribute__((packed))`（无填充）|
| 向量 | `<4 x i32>` | SIMD 类型 |

**结构体默认有填充。** 看第 6 章的例子：

```c
struct Mixed { char c; int i; double d; };
```

```llvm
%struct.Mixed = type { i8, i32, double }
```

你可能会问：`i8` 后面不该有 3 字节填充吗？

**答案：填充不写在类型里，而是由 `datalayout` 的对齐规则计算。** 这样同一个类型定义在 32 位和 64 位平台上可以有不同的实际布局，而 IR 本身保持目标无关。

你可以用 `llvm-config` 或一个小测试程序验证实际大小：

```bash
$ cat > size.c <<'EOF'
#include <stdio.h>
struct Mixed { char c; int i; double d; };
int main(void) {
    printf("sizeof(struct Mixed) = %zu\n", sizeof(struct Mixed));
    printf("  c offset = %zu\n", offsetof(struct Mixed, c));
    printf("  i offset = %zu\n", offsetof(struct Mixed, i));
    printf("  d offset = %zu\n", offsetof(struct Mixed, d));
    return 0;
}
EOF
$ clang-18 -w size.c -o size && ./size
sizeof(struct Mixed) = 16
  c offset = 0
  i offset = 4
  d offset = 8
```

所以实际布局是 `c` 在 0，填充 3 字节，`i` 在 4，`d` 在 8，总共 16 字节。**这些填充来自 datalayout 的对齐规则，不是来自 `{ i8, i32, double }` 这个类型本身。**

### 3. 类型别名

```llvm
%struct.Point = type { i32, i32 }
%MyInt = type i32
```

`type` 定义的是**名字**，不是新类型。`%MyInt` 和 `i32` 完全等价。所以下面的代码是合法的：

```llvm
%MyInt = type i32

define %MyInt @f(i32 %x) {
  %r = add i32 %x, 1
  ret i32 %r            ; 返回 i32，类型是 %MyInt 的别名，OK
}
```

## 9.3 C 类型到 IR 类型的完整映射

这是一张你可以随时查的表。用实测生成：

```c
void f_char(char a) {}
void f_schar(signed char a) {}
void f_uchar(unsigned char a) {}
void f_short(short a) {}
void f_ushort(unsigned short a) {}
void f_int(int a) {}
void f_uint(unsigned a) {}
void f_long(long a) {}
void f_ulong(unsigned long a) {}
void f_ll(long long a) {}
void f_bool(_Bool a) {}
void f_float(float a) {}
void f_double(double a) {}
void f_ld(long double a) {}
void f_ptr(void *a) {}
void f_arr(int a[10]) {}
```

`clang-18 -S -emit-llvm -O0` 的实际输出：

```llvm
define dso_local void @f_char(i8 noundef signext %0) #0 {
define dso_local void @f_schar(i8 noundef signext %0) #0 {
define dso_local void @f_uchar(i8 noundef zeroext %0) #0 {
define dso_local void @f_short(i16 noundef signext %0) #0 {
define dso_local void @f_ushort(i16 noundef zeroext %0) #0 {
define dso_local void @f_int(i32 noundef %0) #0 {
define dso_local void @f_uint(i32 noundef %0) #0 {
define dso_local void @f_long(i64 noundef %0) #0 {
define dso_local void @f_ulong(i64 noundef %0) #0 {
define dso_local void @f_ll(i64 noundef %0) #0 {
define dso_local void @f_bool(i1 noundef zeroext %0) #0 {
define dso_local void @f_float(float noundef %0) #0 {
define dso_local void @f_double(double noundef %0) #0 {
define dso_local void @f_ld(x86_fp80 noundef %0) #0 {
define dso_local void @f_ptr(ptr noundef %0) #0 {
define dso_local void @f_arr(ptr noundef %0) #0 {
```

整理成表：

| C 类型 | IR 类型 | 参数属性 | 备注 |
|---|---|---|---|
| `char`、`signed char` | `i8` | `signext` | |
| `unsigned char` | `i8` | `zeroext` | |
| `short` | `i16` | `signext` | |
| `unsigned short` | `i16` | `zeroext` | |
| `int` | `i32` | 无 | |
| `unsigned` | `i32` | 无 | **注意：没有 `zeroext`** |
| `long`（Linux x86-64） | `i64` | 无 | |
| `long long` | `i64` | 无 | |
| `_Bool` | `i1` | `zeroext` | |
| `float` | `float` | | |
| `double` | `double` | | |
| `long double`（x86-64） | `x86_fp80` | | 目标相关！ |
| `void *` | `ptr` | | |
| `int[10]`（作参数） | `ptr` | | 数组退化为指针 |

### 关键观察一：符号性体现在 `signext`/`zeroext`

`char` 和 `unsigned char` 都是 `i8`。区别在于参数属性：

- `signext`：调用者/被调用者保证**符号扩展**到寄存器宽度；
- `zeroext`：保证**零扩展**。

这是 ABI 层面的要求。x86-64 的调用约定只规定了 32 位及以下的值放在寄存器低位，高位是否有效要由属性说清楚。

### 关键观察二：`unsigned` 没有 `zeroext`，但 `unsigned char` 有

这看起来不一致，其实有道理：`i32` 的参数**恰好占满**一个 32 位寄存器，不存在「高位没定义」的问题，所以不需要扩展属性。`i8`/`i16` 比寄存器窄，才需要说明高位怎么处理。

### 关键观察三：数组参数退化成 `ptr`

`int a[10]` 作为参数，IR 类型是 `ptr`，不是 `[10 x i32]`。这完全对应 C 的规则：**数组作参数时退化为指针**。

`[10 x i32]` 这个类型仍然存在，只是它出现在**局部变量**和**全局变量**上：

```llvm
@global_arr = global [10 x i32] zeroinitializer
```

### 关键观察四：`long double` 是目标相关的

`x86_fp80` 是 x86 特有的 80 位扩展精度格式。在 ARM 上，`long double` 可能是 `fp128` 或 `double`。

**这提醒我们：IR 并不完全目标无关。** 少数类型（`long double`、`va_list`、某些内建函数）会暴露目标细节。

## 9.4 结构体的实际布局：`getelementptr` 与填充的关系

第 6 章讲过 `getelementptr` 的字段索引。现在可以看清楚填充的作用了：

```llvm
%struct.Mixed = type { i8, i32, double }

; 访问 d 字段
%p = getelementptr inbounds %struct.Mixed, ptr %base, i32 0, i32 2
```

GEP 需要知道 `d` 在偏移 8 处。这个 8 是怎么算出来的？

```
i8 在偏移 0，占 1 字节
   下一个字段 i32 需要 4 字节对齐 → 填充到偏移 4
i32 在偏移 4，占 4 字节 → 结束于 8
   下一个字段 double 需要 8 字节对齐 → 已经在 8，无需填充
double 在偏移 8，占 8 字节 → 结束于 16
结构体总对齐 = max(1,4,8) = 8 → 16 是 8 的倍数，无需尾部填充
```

**所以 GEP 的「字段索引」到「字节偏移」的转换，依赖 datalayout 的对齐规则。** 这就是为什么 `datalayout` 必须写在模块里 —— 没有它，GEP 无法算出正确地址。

## 9.5 拆解 `target datalayout`

现在来看那一长串：

```
target datalayout = "e-m:e-p270:32:32-p271:32:32-p272:64:64-i64:64-i128:128-f80:128-n8:16:32:64-S128"
```

用 `-` 分隔，逐项解读：

| 段 | 含义 |
|---|---|
| `e` | **小端序**（little endian）。`E` 是大端。 |
| `m:e` | **名称修饰（mangling）**：ELF 风格（`e`），不加前缀下划线。 |
| `p270:32:32` | **指针地址空间 270** 的 ABI 对齐 32、首选对齐 32。 |
| `p271:32:32` | 地址空间 271，同上。 |
| `p272:64:64` | 地址空间 272，64 位对齐。 |
| `i64:64` | **`i64` 的 ABI 对齐是 64 位**（8 字节）。 |
| `i128:128` | `i128` 对齐 128 位（16 字节）。 |
| `f80:128` | `x86_fp80` 对齐 128 位。 |
| `n8:16:32:64` | **原生整数宽度**：8、16、32、64。 |
| `S128` | **栈对齐**：128 位（16 字节）。 |

那些 `p270`、`p271`、`p272` 是什么？它们是 x86-64 上特殊的**地址空间**：

- **270**：`__ptr32`（32 位指针，用于 x32 ABI）
- **271**：`__ptr64`
- **272**：`__ptr128`

这些是 Windows 风格的可选指针宽度扩展，在 Linux 上也会写进 datalayout。

**你要记住的只有几个：**

- **`e` 或 `E`**：字节序。这决定了 `i32` 在内存里是 `01 00 00 00` 还是 `00 00 00 01`。
- **`iN:align`**：各类整数的对齐。
- **`S128`**：栈对齐。

### 为什么 datalayout 很重要

因为**同一个 `getelementptr` 在不同 datalayout 下算出不同的地址**。考虑：

```llvm
%struct.Mixed = type { i8, i32, double }
%p = getelementptr inbounds %struct.Mixed, ptr %base, i32 0, i32 2
```

如果 `i32` 的对齐是 4（x86），`d` 在偏移 8。
如果 `i32` 的对齐是 8（某些平台），`d` 可能在偏移 16。

**这就是为什么 `llc` 需要 datalayout、而 `lli` 也需要它。** 如果你不写 datalayout，LLVM 会用目标默认值（由 `target triple` 推断）；如果你写了却和实际目标不符，生成的代码会读写错误的地址。

### 一个常见的坑

手写 `.ll` 时如果不写 `target datalayout` 和 `target triple`，LLVM 会：

1. 用**宿主**目标的默认布局（如果你用 `llc`/`lli`，就是编译 LLVM 时的目标）；
2. 在需要时打印警告。

`llvm-as-18` 对缺省是宽容的。但如果你用 `clang-18` 把 `.bc` 和 C 代码链接，你会看到：

```
warning: overriding the module target triple with x86_64-pc-linux-gnu
```

**所以：手写 IR 时，要么明确写上 `target triple` 和 `target datalayout`，要么明确知道你依赖默认值。**

## 9.6 类型相等的规则

这里有一个容易想当然的地方。先看两个字段完全一样的命名类型：

```llvm
%A = type { i32, i32 }
%B = type { i32, i32 }

define %A @f(%B %x) {     ; ← 这样行不行？
  ret %A %x
}
```

实测：

```bash
$ llvm-as-18 structeq.ll -o /dev/null
llvm-as-18: structeq.ll:4:10: error: '%x' defined with type '%B = type { i32, i32 }' but expected '%A = type { i32, i32 }'
  ret %A %x
         ^
```

**不行。** `%A` 和 `%B` 是**两个不同的类型**，即使它们的字段完全一样。

### 规则

> **每个 `= type` 定义创建一个独特的命名类型。命名类型只和「同一个名字」相等。字面量类型（直接写 `{ i32, i32 }` 而不给名字）之间才按结构比较。**

所以：

```llvm
; 字面量之间：结构相等，同一个类型
define { i32, i32 } @f({ i32, i32 } %x) {
  ret { i32, i32 } %x           ; ✓ 合法
}
```

```llvm
; 命名类型 vs 同形状的字面量：不相等
%A = type { i32, i32 }
define %A @f({ i32, i32 } %x) {
  ret %A %x                     ; ✗ 报错
}
```

```llvm
; 同一个命名类型：相等
%A = type { i32, i32 }
define %A @f(%A %x) {
  ret %A %x                     ; ✓ 合法
}
```

**为什么这样设计？** 因为命名类型提供了「不透明」的能力。C 里的 `struct Foo` 和 `struct Bar` 即使布局相同，也是不同的类型，把它们混用会被编译器拒绝。LLVM 的命名类型保留了这种区分，这对调试信息、类型安全检查和别名分析都有价值。

> **实践建议**：一旦你给一个结构体起了名字，就在**所有**地方用同一个名字。不要有时写 `%struct.Point`、有时写 `{ i32, i32 }` —— 那会被当成两个类型。

### 递归类型

在 LLVM 18 的 opaque pointer 世界里，递归结构体非常简单：

```llvm
%struct.Node = type { i32, ptr }        ; 链表节点：值 + 指向下一个的指针
```

因为指针不携带被指向的类型，`ptr` 天然打破循环（第 6 章讲过）。

而在 LLVM ≤14 里，你需要这样写：

```llvm
%struct.Node = type { i32, %struct.Node* }   ; 老版本：必须用名字引用
```

**这是 opaque pointer 带来的一个实实在在的简化。** 老版本里造一个链表节点类型需要仔细处理「类型还没定义完就引用自己」的问题；现在只需要 `ptr`。

## 9.7 `void`、`label` 与特殊类型

```llvm
define void @no_return_value() {
  ret void
}

define i32 @has_label(i1 %c) {
  br i1 %c, label %a, label %b
a:
  ret i32 1
b:
  ret i32 2
}
```

- **`void`** 只能用作返回类型，不能用作参数类型、变量类型。
- **`label`** 是基本块标签的类型。你在 `br i1 %c, label %a, label %b` 里看到 `label` 关键字，但**变量不能是 `label` 类型**。
- **`token`** 用于 `gc.statepoint` 这类特殊指令，日常几乎用不到。
- **`metadata`** 类型用于 `call` 元数据参数，如 `call void @llvm.dbg.value(metadata i32 %x, ...)`。

## 9.8 动手练习

**练习 9.1** 生成 `struct` 和 `union` 的 IR 类型定义，对比它们的差别。提示：

```c
struct S { char c; int i; };
union U { char c; int i; };
```

**练习 9.2** 生成 `packed` 结构体的 IR，观察类型写法的变化：

```c
struct __attribute__((packed)) P { char c; int i; };
```

实测结果：

```llvm
%struct.P = type <{ i8, i32 }>
```

注意那个尖括号：**`<{ ... }>` 是打包结构体**，表示「不加填充」。所以 `i32` 字段位于偏移 1，而不是偏移 4。对应的 GEP 仍然是 `getelementptr inbounds %struct.P, ptr %3, i32 0, i32 1` —— 索引方式没变，但算出的地址不同，因为布局规则变了。

这也再次说明 **GEP 的语义依赖类型定义**：同一个 `i32 0, i32 1` 在 `{ i8, i32 }` 和 `<{ i8, i32 }>` 上算出不同的地址。

**练习 9.3** 用手写的 `.ll` 定义一个 `i3` 类型的运算，验证 LLVM 支持任意位宽：

```llvm
define i3 @f(i3 %a, i3 %b) {
  %r = add i3 %a, %b
  ret i3 %r
}
```

**练习 9.4** 写一个 C 程序打印 `struct Mixed { char c; int i; double d; }` 的 `sizeof` 和各字段 `offsetof`，然后用手算的 datalayout 规则验证。改变字段顺序（比如 `{ double d; char c; int i; }`），重新验证。

**练习 9.5** 用 `llvm-as-18` 验证一个没有 `target datalayout` 的文件，然后用 `llc-18` 编译它，观察是否有警告。

**练习 9.6（思考题）** 为什么 LLVM 让整数位宽任意（`i3`、`i33`），而不是像 C 一样限定为 8/16/32/64？提示：想想第 5 章 `sum_to` 优化里的 `i33`。

## 9.9 小结

- 基本类型：任意位宽的 `iN`、若干浮点类型、统一的 `ptr`、`label`、`void`、`token`、`metadata`。
- 复合类型：`[N x T]`（数组）、`{ ... }`（结构体）、`<{ ... }>`（打包）、`<N x T>`（向量）。
- **结构体类型里不写填充**；填充由 `datalayout` 的对齐规则决定，GEP 依赖这些规则算地址。
- C 类型映射：`char`→`i8`、`short`→`i16`、`int`→`i32`、`long`→`i64`、`_Bool`→`i1`、`long double`→`x86_fp80`（目标相关）。
- **符号性不体现在整数类型上，而体现在 `signext`/`zeroext` 属性上**。
- `datalayout` 的关键字段：字节序（`e`/`E`）、整数对齐（`iN:align`）、栈对齐（`S`）。
- **类型相等不是结构相等**：每个 `= type` 定义是独特的命名类型，只和同名者相等；只有字面量类型之间才按结构比较。
- opaque pointer 让递归类型（链表等）的定义变得非常简单。
